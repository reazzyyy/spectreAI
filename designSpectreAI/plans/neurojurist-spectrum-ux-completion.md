## 1. Статус и назначение

**Статус: REG-07 утверждён пользователем, работа над макетом разрешена. Этап 0 закрыт для согласованного синтетического UX-scope; этапы 1/2/5/6 в работе (UI-01), остальные не завершены. Все 174 сценария не объявляются готовыми.**

Пользователь попросил зафиксировать согласованный в переписке план для последующей работы. Этот документ сохраняет маршрут работ, но не является разрешением немедленно менять интерфейс или утверждением всех открытых продуктовых решений.

Цель — комплект UX/UI-макетов, по которому frontend-разработчики смогут вручную реализовать продукт без самостоятельного придумывания экранов, состояний, ролей и переходов.

Дорабатывается макет, а не production-приложение. Качество демонстрационного кода не является основной целью. Реальные AI, email, загрузка на сервер, база данных и интеграция офисного редактора для завершения макета не нужны.

## 2. Постоянные ограничения

- Сохранять существующую визуальную систему, шрифты, палитру, компоненты и плотность интерфейса.
- Не применять случайно подключённый product overview про Interview Platform: это другой продукт. Не переходить из-за него на тёмную тему или другой стек.
- Иерархия: проект → чаты / документы / исследования / черновики. Документ без проекта не существует.
- Workspace находится внутри Organization; PERSONAL не является внешним личным хранилищем. Client/Matter самостоятельны: Client 0..1 на проект, Matter M:N. Чат принадлежит ровно одному Workspace и Organization.
- Разделять роли Workspace и организационные роли.
- OWNER/EDITOR/VIEWER подтверждены: VIEWER только читает; EDITOR создаёт/редактирует содержимое, но не управляет участниками, ownership, архивом или удалением Workspace. REG-03: название/описание/связи проекта меняет только OWNER; EDITOR удаляет лишь созданные им материалы, OWNER — любые доступные ему. PRIVATE ACL не расширяется.
- REG-03: инициатор с актуальным правом отменяет свои AI-задачи; OWNER также отменяет доступные ему задачи проекта, включая чужие. Другой EDITOR и VIEWER не отменяют чужую задачу; VIEWER не отменяет и свои. Доступ к PRIVATE не появляется из права отмены; детали stop/partial ещё открыты.
- REG-04 / DEC-03/O-012: Workspace удаляет текущий OWNER после двух последовательных подтверждений им самим; одобрение другого сотрудника не требуется. Это не меняет независимого approver для admin grant и не распространяет правило на любые удаления/необратимые действия.
- REG-05/06 / DEC-03: передача владения — предложение текущего OWNER → ожидание → принятие получателем → успешная смена единственного OWNER; прежний OWNER остаётся участником проекта как VIEWER, не EDITOR. До принятия он сохраняет владение при актуальном membership; исключения при уходе ещё открыты. Ожидающая и завершённая передача не откладывают обязательный отзыв доступа уволенному, не меняют org membership, PRIVATE/PERSONAL и admin grant.
- Org Admin и организационный Owner не получают автоматического чтения по своей org-роли. Org Admin может управлять membership без чтения материалов; остальные открытые org-права не расширять.
- Privileged access: независимый специально назначенный согласующий с `admin_grant:approve` (назначает Owner организации), конкретный scope, read-only, срок не более 60 минут, отзыв и обязательный аудит. Самосогласование и продление запрещены; новый доступ — новый запрос. Нет согласующего — нет grant; break-glass вне MVP.
- Вход по приглашению; первая Organization/Owner через контролируемый bootstrap. Публичный signup, гости, SSO/MFA и произвольные ACL на каждом документе вне MVP по Phase 2. Не добавлять их как недостающие обязательные экраны.
- PRIVATE и WORKSPACE чаты подтверждены; личный чат внутри TEAM не становится общим автоматически. Перед раскрытием истории требуется явное действие; обратное скрытие общего чата без политики не включать.
- Работать на синтетических данных. Не выдавать демонстрационное поведение за реальную интеграцию.
- До O-002 в целевом продукте только SyntheticAIProvider; OpenAI — целевой, модель O-001 OPEN. Никакой интеграции в рамках текущей задачи. D-008 описывает будущий Next.js/NestJS-стек, а не поручение менять React/Vite.
- Не добавлять без подтверждения совместное редактирование, полноценный офисный редактор, новые роли, дополнительные правила хранения/удаления, форматы экспорта или полноценную CRM.
- D-019–D-022 задают: удаление активных/производных ≤24 ч, бэкапы 35 дней, техническая цель аудита 1 год с юридической проверкой, RPO ≤24 ч/RTO ≤8 ч. Не обещать мгновенное удаление всех копий или восстановление по кнопке; детали lifecycle остаются открыты.
- REG-02 / DEC-12: пользователь отложил продуктовый экспорт за пределы MVP. RES-12/DRF-11 отложены, E2E-04 в MVP заканчивается сохранением/повторным открытием. Отложено не означает готово; исходный каталог и исходная цепочка с экспортом сохраняются.
- REG-02 / DEC-08: обязателен отдельный Draft с ручным редактированием/сохранением, AI-правками, AI-проверкой, автосохранением, историей и сравнением версий. Чат не заменяет этот workflow; детали autosave/версий/конфликтов ещё согласуются.
- REG-02 / DEC-01: после любого успешного входа всегда Главная при 0/1/нескольких проектах, включая повторный login после session expiry. Последний/единственный проект не открывается автоматически; обычная навигация и выбор tenant при нескольких Organization этим не определены.
- Сохранение плана не разрешает менять макет. Каждый рабочий пакет выполняется по запросу пользователя.
- При запросе только аудита работать read-only.
- Ранее пользователь исключал keyboard-only проверку. Не считать её выполненной и не расширять на неё работу автоматически; отдельно согласовать, если она потребуется для handoff.
- Не запускать второй dev server. Использовать существующий preview; для проверок следовать актуальным инструкциям репозитория.

## 3. Приоритеты и зависимости

Порядок HYP-01 согласован пользователем как **гипотеза**; это не измеренная частота использования. [Полный индекс и пакеты](neurojurist-spectrum-priority-queue.md) являются рабочей очередью поверх неизменных ID каталога. Номер этапа ниже — функциональная группировка, не указание выполнить весь этап до следующего.

| Приоритет | Значение |
|---|---|
| P0 | Вход/доступный проект → документы/обработка → Chat/проверяемые источники → продолжение; сквозные права, сохранность и ошибки |
| P1 | Основные рабочие результаты: Draft/Review, затем Research |
| P2 | Организация регулярной работы, команда, справочники и вспомогательные настройки |
| P3 | Расширение редких административных интерфейсов: grant, сложный lifecycle и org-настройки |
| Вне очереди | AUTH-05 — исключённый публичный bootstrap; RES-12 и DRF-11 — отложенный экспорт |

P1–P3 не означают исключение утверждённых модулей. Приоритет не переводит карточки в «Готово». Частота, ценность, риск и зависимости указаны отдельно; данных интервью/аналитики не выдумываем.

**Дальнейшая последовательность:** быстрая проверка предпосылок P0-A → ревизия и доведение P0-B/P0-C Documents → Chat → источники со сквозным P0-S → P1 Draft/Review → P1 Research → пакеты P2 → расширения P3. Уже проверенные функции не перепроектируются без выявленного пробела. Командный onboarding и административные исключения не вытесняют повседневную клиентскую цепочку.

Права, отсутствие утечек PRIVATE/PERSONAL, отзыв источников, сохранность текста и обязательный security-аудит остаются сквозными P0. Ошибка этих гарантий поднимается немедленно, даже если расширение соответствующего редкого интерфейса имеет P3. P0-S проверяется по месту текущего пакета; не нужно сначала заново строить все системные экраны.

Research и Draft строятся на проектном контексте, источниках и состояниях задач P0. Нужная для основного пути зависимость поднимается вместе с ним с явным основанием. Документ 20 описывает production-предложения, а не заменяет очередь HYP-01; REG-07 сохраняет утверждённый scope. Backend для макета не нужен.

## 7. Пакеты согласования и Definition of Done

### Пакеты

1. Основа: scope, роли, карта, термины и стартовая маршрутизация.
2. Вход и команда: auth, главная, проекты, участники.
3. Главный юридический путь: Documents → обработка → Chat/RAG → источники.
4. Подготовка результата: Research и Drafts.
5. Безопасность: организация, запросы, отзыв, аудит и удаление.
6. Завершение: дополнительные модули, адаптивность, состояния и handoff.

Правила безопасности согласовать в пакете 1, даже если подробные экраны идут в пакете 5.

### Готовность отдельного сценария

- [ ] Роль и условия начала определены.
- [ ] Есть вход, все действия и понятные результаты.
- [ ] Есть необходимые ошибки и альтернативы.
- [ ] Можно восстановиться после ошибки; нет тупика.
- [ ] Действия соответствуют роли.
- [ ] Сохранён контекст проекта и объекта.
- [ ] Сохранена существующая визуальная система.
- [ ] Проверены утверждённые размеры экрана.
- [ ] Есть связь с ID каталога.
- [ ] Допущения обозначены.
- [ ] Разработчику не нужно придумывать бизнес-логику.

Состояния на демопереключателе подходят для демонстрации ошибок, но не заменяют связанный основной пользовательский путь.

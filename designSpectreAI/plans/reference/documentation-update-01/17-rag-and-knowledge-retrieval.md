## 1. Цель

RAG (Retrieval-Augmented Generation) — подход, при котором приложение сначала находит релевантные данные, а затем передаёт их модели для подготовки ответа.

В нашем продукте RAG нужен для:

- ответов на вопросы по загруженным документам;
- анализа договоров;
- сравнения документов и их редакций;
- подготовки резюме;
- поиска условий, обязательств, сроков и рисков;
- работы с документами рабочего пространства;
- формирования ответов с проверяемыми ссылками на исходные материалы.

Основные требования:

1. Искать только по данным, доступным пользователю.
2. Учитывать организацию, рабочее пространство и другие ограничения доступа.
3. Сохранять связь найденного фрагмента с исходным документом и его редакцией.
4. Не выдавать похожий текст за доказательство юридического утверждения.
5. Не использовать удалённые или недействующие версии без явного основания.
6. Поддерживать обновление и удаление поискового индекса.
7. Контролировать размер контекста и стоимость AI-запросов.
8. Позволять диагностировать ошибки поиска независимо от ошибок генерации.

**Принцип:** поиск отвечает за то, какие данные попадут в контекст, а модель — за работу с этим контекстом. Модель не должна самостоятельно определять права доступа.

## 2. Что входит в RAG

RAG состоит из нескольких самостоятельных этапов:

1. Получение документов и их версий.
2. Извлечение текста.
3. Нормализация и сегментация текста.
4. Построение поискового индекса.
5. Обработка поискового запроса.
6. Отбор и ранжирование фрагментов.
7. Проверка прав доступа.
8. Формирование контекста для модели.
9. Генерация ответа.
10. Привязка утверждений к источникам и проверка ссылок.

Не следует объединять все эти этапы в один сервис или один большой метод. У них разные требования к нагрузке, надёжности и тестированию.

## 4. Области поиска

Не каждый запрос должен искать по всем документам пользователя.

Предлагается поддержать следующие области.

### 4.1. Один документ

Пользователь задаёт вопрос по конкретному документу.

Поиск ограничивается выбранным документом и редакцией, если сценарий не требует сравнения версий.

Примеры:

- «Какая предусмотрена неустойка?»
- «Какой срок уведомления установлен договором?»
- «Найди условия одностороннего расторжения».

### 4.2. Выбранные документы

Пользователь вручную выбирает несколько документов.

Система ищет только в выбранном наборе, одновременно проверяя актуальные права доступа.

Примеры:

- сравнить два договора;
- найти расхождения в договоре и приложении;
- сопоставить договор с дополнительным соглашением.

### 4.3. Рабочее пространство

Поиск выполняется по документам конкретного рабочего пространства.

Область поиска определяется сервером на основании членства и прав пользователя.

Примеры:

- найти все договоры с определённым контрагентом;
- найти положения о конфиденциальности;
- определить, в каких документах установлен определённый срок оплаты.

### 4.4. Общая база знаний организации

Этот сценарий допустим только при наличии соответствующей модели доступа.

Членство в организации не должно автоматически предоставлять доступ ко всем документам организации. Если в разных рабочих пространствах действуют разные права, поиск обязан их соблюдать.

### 4.5. Внешние правовые источники

Поиск по законодательству, судебным актам и другим публичным источникам следует рассматривать как отдельный источник данных.

Он отличается от поиска по загруженным документам требованиями к актуальности, происхождению, дате публикации и проверке юридических ссылок.

Внешний поиск может использоваться совместно с RAG по документам, но источники должны различаться в результате.

## 5. Технологический выбор для MVP

Рекомендуется не начинать с отдельной сложной векторной инфраструктуры без подтверждённой потребности.

Возможные варианты:

| Вариант | Преимущества | Ограничения |
|---|---|---|
| PostgreSQL + полнотекстовый поиск | Простота эксплуатации, знакомая инфраструктура | Слабее семантический поиск |
| PostgreSQL + pgvector | Векторный и обычный поиск в одной системе | Нужно оценить качество и производительность |
| Отдельная поисковая система | Гибкие возможности поиска и масштабирования | Дополнительная инфраструктура и эксплуатация |

**Подтверждённое решение D-018:** для MVP использовать PostgreSQL с полнотекстовым поиском и `pgvector`. До production проверить качество русскоязычного поиска, точность retrieval, фильтрацию по организации/пользователю и производительность на репрезентативном тестовом наборе. Embedding-модель остаётся отдельным открытым решением.

MVP должен опираться на подтверждённую связку PostgreSQL FTS + `pgvector` (**D-018**). Допустимо поэтапно включить векторный поиск после появления embeddings-модели, но **не** выбирать отдельную внешнюю vector DB без нового решения в журнале. Качество русскоязычного retrieval и производительность подлежат тестам.

## 6. Модель данных

Базовые сущности `Document`, `DocumentVersion`, `DocumentChunk` и `Embedding` описаны в `docs/06-data-model.md`.

Ниже — уточнения для RAG.

### 6.1. DocumentChunk

Каждый фрагмент должен быть связан с конкретной редакцией документа.

Предлагаемые поля:

- `id`;
- `organizationId`;
- `documentId`;
- `documentVersionId`;
- `chunkIndex`;
- `text`;
- `pageNumber`, если доступен;
- `sectionTitle`, если доступен;
- `startOffset`;
- `endOffset`;
- `tokenCount`;
- `contentHash`;
- `createdAt`.

Смещения и номера страниц должны сохранять связь с извлечённым текстом. Они не всегда соответствуют точным координатам в исходном PDF, поэтому интерфейс не должен обещать точное выделение фрагмента, если координаты не сохранены.

### 6.2. Embedding

Предлагаемые поля:

- `id`;
- `chunkId`;
- `modelId`;
- `modelVersion`, если доступна;
- `dimensions`;
- `vector`;
- `createdAt`.

Для одной модели и одного типа embeddings размерность и формат вектора должны быть согласованы со схемой индекса.

При смене embeddings-модели необходимо учитывать несовместимость векторов разных моделей. Нельзя без проверки смешивать в одном поисковом пространстве embeddings, полученные несовместимыми моделями.

### 6.3. Индексирование

Для каждого фрагмента должны быть доступны:

- полнотекстовое представление;
- embedding, если семантический поиск включён;
- метаданные источника;
- идентификатор версии документа;
- состояние индексации;
- контрольная сумма исходного содержимого.

Индексы и производные данные должны соответствовать жизненному циклу документа. После удаления документа поисковая система не должна продолжать возвращать его фрагменты.

## 7. Извлечение и нормализация текста

Качество RAG начинается до поиска.

Обработка должна учитывать:

- PDF с текстовым слоем;
- сканированные PDF и OCR;
- DOCX;
- TXT;
- заголовки и разделы;
- таблицы;
- списки;
- номера страниц;
- переносы строк;
- колонтитулы;
- повторяющиеся элементы;
- ошибки извлечения.

### 7.1. Сохранение структуры

Не следует превращать весь документ в неразличимый текстовый массив.

По возможности нужно сохранять:

- заголовки разделов;
- номера пунктов;
- структуру списков;
- содержание таблиц;
- нумерацию страниц;
- границы абзацев.

Например, условие «Срок оплаты — 10 рабочих дней» без названия раздела и контекста может быть понято неправильно, если в документе есть исключения или особые условия.

### 7.2. Таблицы

Таблицы необходимо обрабатывать так, чтобы значения оставались связанными с заголовками строк и столбцов.

Если извлечение таблицы не удалось, система должна по возможности сообщить об ограничении качества обработки, а не выдавать отсутствие найденного условия за доказательство его отсутствия в документе.

### 7.3. Контроль качества извлечения

Рекомендуется сохранять статус обработки и доступные метрики:

- количество извлечённых символов;
- количество страниц;
- количество пустых или подозрительно коротких страниц;
- факт использования OCR;
- ошибки извлечения;
- предупреждения о неполной обработке.

Эти данные помогут отличить ситуацию «условие отсутствует» от ситуации «условие не удалось извлечь».

## 8. Chunking — разделение документа на фрагменты

Поиск обычно работает не со всем документом целиком, а с небольшими фрагментами.

### 8.1. Предварительные параметры

Для первого эксперимента можно использовать:

- целевой размер: 500–800 токенов;
- перекрытие: 50–100 токенов;
- разбиение по абзацам и структуре документа;
- отдельную обработку заголовков и таблиц.

Это стартовые значения для тестирования, а не универсальный оптимум.

Для юридических текстов границы фрагментов особенно важны: нельзя бездумно разделять пункт договора, исключение, условие и его продолжение.

### 8.2. Предпочтительный порядок разбиения

1. Сохранить структуру документа.
2. Разделить текст по заголовкам и разделам.
3. Разделить слишком большие разделы по абзацам.
4. При необходимости объединить короткие соседние абзацы.
5. Применить ограничение размера.
6. Добавить небольшое перекрытие, если оно улучшает полноту поиска.
7. Сохранить ссылки на исходный текст и страницу.

### 8.3. Контекст заголовков

Для поиска можно добавлять к тексту фрагмента заголовок раздела или название документа.

При этом необходимо различать:

- исходный текст фрагмента;
- метаданные;
- дополнительный контекст, добавленный для поиска.

Нельзя выдавать добавленный заголовок за дословную цитату из исходного фрагмента, если он не входит в цитируемый текст.

### 8.4. Версионирование chunking

Изменение алгоритма разбиения может менять результаты поиска.

Поэтому желательно фиксировать версию алгоритма, например `chunkingVersion`, и иметь возможность переиндексировать документы при изменении логики.

## 9. Embeddings

Embedding — числовое представление текста, позволяющее находить смыслово похожие фрагменты.

Например, запрос «когда можно прекратить договор в одностороннем порядке» может быть связан с пунктом, содержащим формулировку «право на односторонний отказ от исполнения обязательств».

Однако семантическая близость не гарантирует юридическую релевантность.

### 9.1. Требования к embeddings-модели

Нужно проверить:

- качество на русском языке;
- способность работать с юридическими формулировками;
- максимальный размер входа;
- стоимость и задержку;
- доступность и стабильность модели;
- условия обработки данных;
- возможность self-hosting;
- совместимость размерности с поисковым индексом.

### 9.2. Изменение модели

При переходе на новую embeddings-модель:

1. Создать отдельную версию индекса.
2. Построить embeddings для тестовой выборки.
3. Сравнить качество поиска.
4. Провести переиндексацию.
5. Проверить отсутствие пропусков.
6. Переключить поиск на новую версию.
7. Удалить старые embeddings согласно политике хранения.

Не следует незаметно менять модель в рабочем индексе без оценки совместимости и качества.

### 9.3. Конфиденциальность

Если embeddings создаются внешним сервисом, текст документа фактически передаётся этому сервису.

Наличие вектора вместо исходного текста не означает, что обработка автоматически безопасна или анонимна.

Перед использованием внешней embeddings-модели применяются те же требования к согласованию провайдера, региона, договора и политики передачи данных, что и для остальных AI-вызовов.

## 10. Гибридный поиск

Рекомендуется рассмотреть сочетание полнотекстового и векторного поиска.

### 10.1. Полнотекстовый поиск

Особенно полезен для:

- точных формулировок;
- номеров статей и пунктов;
- реквизитов;
- названий сторон;
- терминов;
- номеров договоров;
- точных юридических выражений.

### 10.2. Векторный поиск

Полезен для:

- смысловых переформулировок;
- поиска похожих положений;
- запросов на естественном языке;
- обнаружения фрагментов с близким смыслом, но другой формулировкой.

### 10.3. Объединение результатов

Предлагаемый алгоритм:

1. Выполнить полнотекстовый поиск.
2. Выполнить векторный поиск, если он включён.
3. Объединить результаты.
4. Удалить дубликаты.
5. Применить ограничения по доступу и версии.
6. Объединить ранги, например с помощью Reciprocal Rank Fusion (RRF).
7. При необходимости применить reranker.
8. Передать лучшие фрагменты в Context Builder.

RRF — один из возможных методов объединения рангов. Его следует сравнить с более простыми вариантами на тестовой выборке.

Не следует напрямую складывать несопоставимые оценки разных поисковых систем без нормализации.

## 11. Фильтрация по правам доступа

Это обязательное требование безопасности.

Каждый поисковый запрос должен иметь явно определённый scope — область поиска, доступную пользователю.

Пример:

```ts
type RetrievalScope = {
  organizationId: string;
  userId: string;
  workspaceIds?: string[];
  documentIds?: string[];
  allowedDocumentVersionIds?: string[];
};
```

Это иллюстративный тип. Фактический контракт должен соответствовать существующей модели авторизации.

### 11.1. Проверка до поиска

По возможности поисковая система должна применять фильтры по организации, рабочему пространству, документам и состоянию версии до передачи результатов в прикладной контекст.

Если используется PostgreSQL, фильтрация должна быть частью запроса к индексу и его метаданным.

Если используется отдельный поисковый сервис, его возможности фильтрации и изоляции необходимо проверить отдельно.

### 11.2. Повторная проверка

После поиска сервер повторно проверяет доступ к выбранным фрагментам и актуальность документов перед формированием контекста.

Это защищает от ситуаций, когда права изменились между поиском и использованием результатов.

### 11.3. Запрещённые подходы

Нельзя:

- искать по всем документам организации, а затем просить модель игнорировать чужие;
- доверять `organizationId` или `workspaceId`, переданным клиентом, без серверной проверки;
- считать UUID документа подтверждением доступа;
- кэшировать результаты поиска только по тексту запроса;
- отдавать пользователю фрагменты из недоступных документов через цитаты или метаданные.

## 12. Актуальность версий и удаление

Поиск должен учитывать жизненный цикл документа.

### 12.1. Новая редакция документа

При загрузке новой версии необходимо определить, должна ли она автоматически становиться основной для обычного поиска.

Рекомендуемое правило:

- обычный поиск использует текущую актуальную версию;
- сравнение редакций может явно включать старые версии;
- исторический поиск требует явного указания периода или версии;
- результат фиксирует версии источников, на которых он основан.

Старые редакции нельзя физически удалять только из-за появления новой версии, если они нужны для истории и доступны по политике хранения. Но их нельзя незаметно подмешивать в поиск актуальных условий.

### 12.2. Удаление документа

При удалении:

- запретить новые поисковые запросы к документу;
- исключить его фрагменты из поискового индекса;
- удалить или поставить на удаление embeddings;
- удалить производные поисковые данные;
- инвалидировать соответствующие кэши;
- учесть активные AI-задачи;
- обеспечить выполнение политики удаления из `docs/08-data-lifecycle-and-deletion.md`.

### 12.3. Переиндексация

Переиндексация должна быть идемпотентной и восстанавливаемой после сбоя.

Повторная обработка одного документа не должна создавать дублирующиеся активные фрагменты и embeddings.

Рекомендуется использовать версионированные индексы либо управляемое переключение активного набора данных, если это необходимо для безопасной переиндексации.

## 13. Query rewriting и уточнение запроса

Иногда исходный запрос слишком общий или содержит местоимения, которые понятны только из предыдущего диалога.

Пример:

- пользователь: «Проанализируй договор аренды»;
- затем: «А что с расторжением?»

Система может преобразовать второй запрос в самостоятельный поисковый запрос с учётом доступной истории диалога.

Однако:

- исходный запрос пользователя должен сохраняться;
- преобразование не должно добавлять неподтверждённые факты;
- доступ к истории диалога проверяется отдельно;
- преобразованный запрос не может расширять разрешённый scope;
- при неоднозначности система должна запросить уточнение, если оно существенно влияет на результат.

Query rewriting — вспомогательный этап, а не механизм авторизации.

## 14. Reranking

Reranker — модель или алгоритм, который повторно оценивает уже найденные фрагменты относительно запроса.

Он может улучшить порядок результатов, но добавляет задержку и стоимость.

Предлагаемый вариант:

1. Получить ограниченный набор кандидатов из гибридного поиска.
2. Применить reranker к кандидатам.
3. Выбрать подходящие фрагменты.
4. Проверить источники и права.
5. Сформировать контекст.

Для первого MVP reranker не обязателен. Его следует добавлять, если тесты показывают, что простое объединение поисковых результатов не обеспечивает достаточного качества.

Reranker не должен получать фрагменты, к которым у пользователя нет доступа.

## 15. Context Builder

Context Builder формирует контекст для модели из результатов поиска.

Он должен:

- ограничивать количество фрагментов;
- учитывать общий бюджет токенов;
- избегать дублирования;
- сохранять метаданные источников;
- по возможности учитывать взаимосвязанные пункты;
- не смешивать разные редакции без явного основания;
- маркировать недоверенные материалы;
- проверять доступ к источникам;
- сообщать о неполном извлечении текста, если это важно для задачи.

### 15.1. Размер контекста

Не следует отправлять все найденные фрагменты без ограничения.

Нужно учитывать:

- лимит модели;
- системные и сценарные инструкции;
- историю диалога;
- размер пользовательского запроса;
- бюджет ответа;
- стоимость обработки.

Если найдено слишком много материалов, нужно выбирать наиболее релевантные фрагменты или предлагать пользователю уточнить запрос.

### 15.2. Недостаток контекста

Если подходящих фрагментов нет, система должна различать:

- в доступных документах не найдено подтверждения;
- поиск завершился ошибкой;
- документ обработан не полностью;
- область поиска ограничена;
- данных недостаточно для уверенного ответа.

Нельзя автоматически превращать отсутствие результатов в утверждение, что соответствующее условие юридически не существует.

## 16. Ссылки на источники в ответе

Каждый выбранный фрагмент должен иметь стабильный внутренний идентификатор и связь с источником.

Рекомендуемые поля ссылки:

- `documentId`;
- `documentVersionId`;
- `chunkId`;
- `pageNumber`, если применимо;
- `quote` или другой проверяемый локатор;
- `sourceType`;
- дополнительные метаданные, необходимые интерфейсу.

Модель может предлагать ссылки на источники, но сервер должен проверять, что они соответствуют действительно переданному контексту.

### 16.1. Интерфейс

Пользователь должен иметь возможность:

- открыть исходный документ;
- перейти к нужной странице, если это поддерживается;
- увидеть цитируемый фрагмент;
- понять, какая редакция использовалась;
- отличить источник из документов пользователя от внешнего источника.

Если переход к точному месту невозможен, интерфейс должен открывать документ без ложного обещания точного позиционирования.

### 16.2. Цитата и вывод

Цитата подтверждает, что определённый текст присутствует в источнике. Она не гарантирует правильность вывода из него.

Для критических юридических выводов желательно показывать не только ссылку, но и объяснение связи между найденным условием и сформулированным риском.

## 17. Кэширование

Кэширование может уменьшить задержку и стоимость, но в юридическом сервисе требует особой осторожности.

### 17.1. Ключ кэша

Ключ должен учитывать все параметры, способные изменить допустимый результат:

- организацию;
- пользователя или набор разрешений, если это необходимо;
- область поиска;
- версии документов;
- нормализованный запрос;
- версию индекса;
- модель embeddings;
- параметры поиска;
- другие влияющие на результат фильтры.

Одного текста запроса недостаточно.

### 17.2. Инвалидация

Кэш нужно инвалидировать или ограничивать по времени при:

- изменении прав;
- удалении документа;
- появлении новой редакции;
- переиндексации;
- изменении области поиска;
- изменении конфигурации поиска.

Кэш не должен становиться обходным путём к уже недоступным данным. Перед выдачей результата необходимо проверять текущие права.

## 18. Производительность и нагрузка

Следует измерять:

- время полнотекстового поиска;
- время векторного поиска;
- время reranking;
- количество найденных кандидатов;
- количество фрагментов, переданных модели;
- размер контекста в токенах;
- долю пустых результатов;
- долю запросов с ошибками;
- задержку построения индекса;
- время от загрузки документа до его доступности для поиска.

Нужно отдельно контролировать индексирование и пользовательский поиск. Массовая переиндексация не должна необоснованно ухудшать интерактивные сценарии.

Параметры concurrency и очередей согласуются с `docs/15-ai-jobs-and-background-processing.md`.

## 19. Оценка качества поиска

Нельзя оценивать RAG только по тому, насколько убедительно звучит финальный ответ.

Нужно отдельно оценивать retrieval — качество поиска источников.

### 19.1. Тестовый набор

Для каждого примера желательно зафиксировать:

- пользовательский запрос;
- допустимую область поиска;
- ожидаемые релевантные документы;
- ожидаемые релевантные фрагменты;
- обязательные ограничения по версии;
- ожидаемое поведение при отсутствии ответа.

Тестовые данные не должны раскрывать конфиденциальные материалы между организациями.

### 19.2. Метрики

В зависимости от тестового набора можно использовать:

- **Recall@K** — доля ожидаемых релевантных фрагментов, найденных среди первых K результатов;
- **Precision@K** — доля релевантных фрагментов среди первых K;
- **MRR** — позиция первого релевантного результата;
- **nDCG@K** — качество ранжирования с учётом степени релевантности;
- долю запросов без результатов;
- долю фрагментов, не относящихся к выбранной версии;
- число нарушений доступа — целевой показатель ноль.

### 19.3. Юридические сценарии

В тестовый набор необходимо включать:

- поиск точной формулировки;
- смысловой поиск;
- поиск номера пункта;
- поиск условий с исключениями;
- поиск по таблицам;
- запросы по нескольким документам;
- запросы, где ответ отсутствует;
- документы с неполным OCR;
- несколько редакций одного документа;
- попытки prompt injection;
- запросы, при которых похожий фрагмент не отвечает на вопрос.

Результаты желательно проверять с участием специалиста, способного оценить юридическую релевантность.

## 20. Тестирование безопасности

Обязательные проверки:

- документ другой организации не попадает в результаты;
- недоступное рабочее пространство не используется при поиске;
- изменение прав блокирует дальнейшее использование источников;
- удалённый документ не возвращается из индекса;
- старые редакции не подмешиваются в обычный поиск без разрешения;
- ссылки на источники валидируются сервером;
- кэш не раскрывает результаты другому пользователю;
- модель не может расширить область поиска через prompt injection;
- повторная индексация не создаёт дубликаты;
- неуспешная переиндексация не делает недоступными все корректные данные;
- embeddings не передаются неразрешённому провайдеру.

## 21. Критерии готовности

RAG считается готовым для MVP, когда:

- [ ] определены поддерживаемые области поиска;
- [ ] документы индексируются асинхронно;
- [ ] каждый фрагмент связан с конкретной редакцией документа;
- [ ] реализованы идемпотентное индексирование и восстановление после ошибок;
- [ ] поисковые запросы фильтруются по правам доступа;
- [ ] предусмотрено исключение удалённых и недействующих версий;
- [ ] контекст ограничивается по размеру;
- [ ] источники сохраняются и проверяются;
- [ ] реализована обработка отсутствующих результатов;
- [ ] определён механизм удаления и переиндексации;
- [ ] есть тестовый набор качества поиска;
- [ ] тесты подтверждают отсутствие межорганизационных утечек;
- [ ] измеряются задержки и ошибки поиска;
- [ ] выбранные поисковые и embeddings-провайдеры соответствуют политике обработки данных.

## 23. Инструкции для реализации через Cursor

При реализации Cursor должен:

1. Изучить существующие модели документов, версий, фрагментов и embeddings.
2. Не создавать вторую несовместимую реализацию индексации.
3. Не добавлять новую базу/vector store без нового решения в журнале; для MVP использовать PostgreSQL + `pgvector` (**D-018**).
4. Обеспечить связь каждого фрагмента с исходной редакцией документа.
5. Применять серверную фильтрацию прав до формирования контекста.
6. Проверять актуальность доступа и версий перед передачей фрагментов модели.
7. Не считать семантическую близость доказательством юридической релевантности.
8. Не передавать конфиденциальные документы внешнему embeddings-провайдеру без одобренной политики.
9. Не выдавать сгенерированные ссылки за проверенные без серверной валидации.
10. Реализовать идемпотентную индексацию, обработку ошибок и переиндексацию.
11. Добавить тесты на удаление, смену версии, отзыв доступа и prompt injection.
12. Не смешивать несовместимые embeddings-модели в одном индексе.
13. Измерять качество поиска отдельно от качества генерации.
14. Не утверждать, что отсутствие результата доказывает отсутствие условия в документе.
15. Обновлять документацию после фактической реализации.

---

**Итог:** RAG в юридическом сервисе — это не просто векторный поиск. Это управляемая система индексирования, поиска, фильтрации прав, контроля редакций и проверки источников. Качество юридического ответа напрямую зависит от того, какие данные были найдены и переданы модели.

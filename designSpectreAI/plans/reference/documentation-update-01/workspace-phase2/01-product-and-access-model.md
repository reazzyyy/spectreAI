# Workspace Phase 2 — продуктовая модель и доступ

**Статус:** согласованные продуктовые решения `CONFIRMED`; детали, прямо отмеченные `PROPOSED`, требуют проверки.  
**Связанные документы:** `DECISIONS-ADDENDUM.md`, `docs/06-data-model.md`, `docs/07-access-control-matrix.md`, `docs/19-conversation-and-workspace-context.md`.

## 1. Назначение Workspace

Workspace — самостоятельное рабочее пространство юридической команды. Оно объединяет контекст и материалы конкретной работы:

- чаты и сообщения;
- документы и версии;
- исследования и найденные источники;
- черновики и версии черновиков;
- связи с Client и Matter;
- участников и настройки доступа.

Workspace не заменяет Organization, Client или Matter:

- `Organization` задаёт tenant boundary.
- `Client` представляет клиента юридической фирмы.
- `Matter` представляет юридическое дело.
- `Workspace` представляет рабочий контекст, в котором команда выполняет работу.

Workspace может существовать без Client и Matter. Client и Matter могут существовать без Workspace.

## 2. Типы Workspace

### 2.1 PERSONAL

Личное пространство сотрудника внутри его Organization.

- У пространства один `ownerUserId`.
- Владелец имеет полный доступ в рамках политики продукта.
- Другие участники организации не получают доступ к содержимому только из-за членства в Organization или роли Org Admin.
- Личное пространство имеет обязательный `organizationId`: личность пространства не означает личное хранилище вне tenant.
- Org Admin может выполнять разрешённые административные операции с метаданными/жизненным циклом, но не читать содержимое без admin grant.

### 2.2 TEAM

Командное пространство.

- Имеет одного текущего Workspace Owner.
- Остальные пользователи получают доступ через `WorkspaceMember`.
- Каждый участник имеет одну роль `EDITOR` или `VIEWER`; владелец представлен `ownerUserId` и не должен одновременно иметь конфликтующую member role.
- Членство в Organization само по себе не даёт доступ ко всем TEAM Workspace.
- Удаление пользователя из Workspace немедленно отзывает доступ к его содержимому.

## 3. Роли Workspace

### 3.1 Ролевые полномочия

| Действие | OWNER | EDITOR | VIEWER |
|---|---:|---:|---:|
| Читать доступное содержимое | Да | Да | Да |
| Создавать документы/черновики/исследования | Да | Да | Нет |
| Создавать личный чат | Да | Да | Нет |
| Создавать общий чат | Да | Да | Нет |
| Редактировать содержимое | Да | Да | Нет |
| Управлять участниками | Да | Нет | Нет |
| Менять роли участников | Да | Нет | Нет |
| Передавать владение | Да | Нет | Нет |
| Архивировать Workspace | Да | Нет | Нет |
| Запросить удаление Workspace | Да | Нет | Нет |

**PROPOSED — удаление контента:** безопасный стартовый вариант — EDITOR может удалять только созданные им объекты, OWNER может удалять любые объекты в Workspace. До реализации удаления чужого контента это правило нужно явно подтвердить. Не предоставлять EDITOR массовое удаление или удаление Workspace.

### 3.2 Org Admin — отдельная организационная роль

Org Admin не является ролью Workspace и не заменяет `OWNER`, `EDITOR` или `VIEWER`.

Org Admin может управлять организацией и членством/доступом к Workspace в рамках организационных полномочий. Это не даёт автоматического права читать документы, чаты, сообщения, исследования или черновики.

Доступ к содержимому — только через admin grant, описанный в `04-lifecycle-admin-grants-and-export.md`.

### 3.3 Матрица административного управления

| Действие | Workspace Owner | Org Admin |
|---|---:|---:|
| Добавить участника TEAM Workspace | Да | Да |
| Удалить участника TEAM Workspace | Да | Да |
| Изменить роль участника | Да | Да, в допустимых пределах |
| Управлять Organization membership | Нет | Да |
| Передать Workspace ownership | Инициирует/подтверждает | Может инициировать организационный процесс; не присваивает владение себе автоматически |
| Читать содержимое без grant | Только по обычному доступу Owner | Нет |
| Читать содержимое с одобренным grant | По обычному доступу | Только в пределах grant, read-only |

Org Admin не должен получать возможность назначать себе `admin_grant:approve` или одобрять собственный запрос. `admin_grant:approve` назначается Owner организации согласно D-016.

## 4. Чаты: личные и общие

Каждый Chat принадлежит ровно одному Workspace и одной Organization.

Предусмотреть видимость:

- `PRIVATE` — чат видит создавший его пользователь (и лица, которым явно предоставлен отдельный доступ по утверждённому процессу).
- `WORKSPACE` — чат видят участники Workspace с правом чтения.

Сообщения наследуют ACL чата. Нельзя получить Message напрямую, минуя проверку доступа к Chat и Workspace.

### 4.1 Ограничения

- Общий чат не становится доступен всем пользователям Organization.
- Личный чат не становится общим из-за того, что пользователь создал его внутри TEAM Workspace.
- Переключение `PRIVATE` → `WORKSPACE` — отдельное явное действие с предупреждением о раскрытии истории участникам.
- Переключение `WORKSPACE` → `PRIVATE` не должно лишать других участников доступа к сообщениям, на которые они уже законно опираются, без отдельной политики. Поэтому такой переход не включать в первую реализацию без решения.
- При уходе автора личного чата из Organization доступ автора прекращается. Сам чат не удаляется автоматически; дальнейшее назначение хранителя/доступа — отдельный workflow. Не выдавать Org Admin доступ к нему автоматически.

## 5. Client и Matter

- Workspace может быть связан с нулём или одним Client в MVP.
- Workspace ↔ Matter — M:N через отдельную join table.
- Каждая связь должна быть tenant-safe: Workspace, Client и Matter обязаны принадлежать одной Organization.
- Matter не должен содержать одиночный `workspaceId` как единственный источник связи после перехода на M:N.
- Удаление/архивирование Client или Matter не должно каскадно удалять Workspace или его содержимое.
- Нельзя автоматически включать в AI context документы всех связанных Matter. Контекст формируется по явному запросу и ACL каждого объекта.

## 6. Создание и первый доступ

- Первая Organization и первый Owner создаются через контролируемый seed/bootstrap.
- Свободная публичная регистрация не входит в MVP.
- Owner приглашает сотрудников в Organization по email.
- После принятия приглашения пользователь становится Organization member; это ещё не даёт доступ ко всем TEAM Workspace.
- В TEAM Workspace Owner или Org Admin отдельно назначает участника и роль.
- Неизвестный срок действия приглашения не фиксировать в коде до отдельного подтверждения; временный параметр должен быть конфигурируемым.

## 7. Жизненный цикл при потере членства

### 7.1 Увольнение / revoke Organization membership

В одной транзакционной бизнес-операции или в надёжном согласованном процессе:

1. Отозвать OrganizationMembership.
2. Отозвать сессии, привязанные к этой Organization, либо сделать их непригодными при следующей проверке membership.
3. Немедленно прекратить доступ к PERSONAL и TEAM Workspace этой Organization.
4. Отозвать доступ к личным и общим чатам, документам, черновикам, исследованиям, поисковым результатам и AIJob results.
5. Отменить/заблокировать ещё не начатые пользовательские AI-задачи либо повторно проверить actor membership до выполнения/выдачи результата.
6. Сохранить организационные данные; не запускать автоматическое физическое удаление.

### 7.2 Потеря Workspace membership

- Отозвать доступ к этому TEAM Workspace немедленно.
- Остальные участники продолжают работу.
- Удаление membership не удаляет созданные пользователем материалы.
- Дальнейшая судьба приватных чатов и материалов автора определяется правилами хранения/передачи, а не каскадным удалением.

### 7.3 Уход Workspace Owner

- TEAM Workspace не должен остаться без владельца.
- До отзыва/удаления membership назначить нового Owner либо перевести Workspace в ограниченное состояние, где управление передаётся уполномоченному процессу.
- PERSONAL Workspace не передаётся автоматически и не раскрывает личные чаты. Передача — явное действие с аудитом.
- Если допустимого нового Owner нет, Workspace сохраняется недоступным для остальных до решения, но не удаляется автоматически.

## 8. Что не входит в MVP

- Гостевые аккаунты клиентов и внешних консультантов.
- Публичная self-registration.
- SSO и MFA.
- Группы/команды внутри Organization с произвольным наследованием прав.
- Произвольные ACL на уровне каждого документа.
- Автоматическое открытие всех пространств Org Admin.
- Автоматическое объединение контекстов разных Workspace.
- Тарифные ограничения количества Workspace или документов.

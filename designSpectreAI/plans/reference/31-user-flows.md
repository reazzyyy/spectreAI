# 31. Полный каталог пользовательских сценариев

Я разделю его на 15 функциональных блоков. В каждом сценарии укажу последовательность действий и ожидаемый результат.

## Обозначения

- **MVP** — необходимый базовый сценарий продукта.
- **Расширение** — сценарий, который следует предусмотреть архитектурно или в последующих итерациях.
- **Уточнить** — поведение ещё требует продуктового решения. Figma не должна придумывать его самостоятельно.

## 1. Регистрация, авторизация и onboarding

Это первое взаимодействие пользователя с системой.

**MVP**

### AUTH-01. Вход в систему

1. Пользователь открывает сайт.
2. Попадает на страницу Login.
3. Вводит email и пароль.
4. Нажимает «Войти».
5. Система проверяет данные.
6. При успешной авторизации пользователь попадает в приложение.
7. Если у него несколько доступных Workspace, открывается последнее использованное пространство или предусмотренный экран выбора.
8. Если доступен только один Workspace, открывается он.

### AUTH-02. Неверные данные авторизации

1. Пользователь вводит неправильный пароль или email.
2. Нажимает «Войти».
3. Система показывает ошибку.
4. Поля остаются доступными для редактирования.
5. Пользователь может повторить попытку.

### AUTH-03. Восстановление пароля

1. Пользователь нажимает «Забыли пароль?».
2. Вводит email.
3. Получает письмо со ссылкой восстановления.
4. Переходит по ссылке.
5. Вводит новый пароль.
6. Подтверждает пароль.
7. Система сохраняет новый пароль.
8. Пользователь возвращается к авторизации или автоматически входит в систему.

### AUTH-04. Регистрация нового пользователя

1. Пользователь открывает регистрацию.
2. Вводит имя, email и пароль.
3. Подтверждает регистрацию.
4. Система проверяет email.
5. Пользователь получает письмо подтверждения, если такой механизм предусмотрен.
6. После успешной регистрации попадает в onboarding.

### AUTH-05. Создание первой организации

1. Пользователь регистрируется впервые.
2. Система предлагает создать организацию.
3. Пользователь вводит название юридической фирмы.
4. Организация создаётся.
5. Пользователь получает роль Org Admin.
6. Система предлагает создать первое рабочее пространство.

### AUTH-06. Приглашение пользователя в существующую организацию

1. Пользователь получает приглашение по email.
2. Открывает ссылку.
3. Если у него уже есть аккаунт — авторизуется.
4. Если аккаунта нет — проходит регистрацию.
5. Система связывает пользователя с организацией.
6. Пользователь получает предусмотренные приглашением права.
7. Он попадает в доступный Workspace или на экран выбора.

### AUTH-07. Истёкшее или отозванное приглашение

1. Пользователь открывает ссылку приглашения.
2. Система обнаруживает, что приглашение недействительно.
3. Показывает соответствующее сообщение.
4. Предлагает запросить новое приглашение у администратора.

### AUTH-08. Истёкшая сессия

1. Пользователь работает в системе.
2. Его сессия истекает.
3. При следующем действии система обнаруживает отсутствие действующей авторизации.
4. Перенаправляет на Login.
5. После входа пользователь возвращается к доступному экрану.

### AUTH-09. Выход из аккаунта

1. Пользователь открывает меню профиля.
2. Нажимает «Выйти».
3. Система завершает сессию.
4. Пользователь попадает на Login.

> **Уточнить.** Способ регистрации, подтверждение email, создание организации, приглашения и правила выбора стартового Workspace ещё нужно сверить с актуальной спецификацией авторизации.

## 2. Главная страница и навигация

Главная страница должна быть точкой входа в повседневную работу юриста.

**MVP**

### DASH-01. Первый вход в приложение

1. Пользователь успешно авторизуется.
2. Открывается Dashboard.
3. Пользователь видит доступные Workspace.
4. Видит последние проекты, чаты или документы, если они есть.
5. Может создать Workspace, начать чат или открыть существующий проект.

### DASH-02. Повторный вход

1. Пользователь авторизуется.
2. Система открывает последнее доступное рабочее пространство.
3. Пользователь видит последние действия и контекст работы.

### DASH-03. Пустое состояние Dashboard

1. Пользователь впервые вошёл в приложение.
2. У него ещё нет Workspace, чатов и документов.
3. Система показывает Empty State.
4. Предлагает создать первое пространство или начать работу.

### DASH-04. Быстрый переход к недавнему проекту

1. Пользователь открывает Dashboard.
2. Находит нужный Workspace в списке недавних.
3. Нажимает на него.
4. Открывается его рабочая область.

### DASH-05. Поиск по приложению

1. Пользователь открывает глобальный поиск.
2. Вводит название проекта, документа или чата.
3. Система показывает доступные результаты.
4. Пользователь выбирает результат.
5. Открывается соответствующая сущность.

### DASH-06. Уведомления

1. Пользователь открывает центр уведомлений.
2. Видит приглашения, изменения доступа, результаты обработки документов и другие события.
3. Нажимает на уведомление.
4. Переходит к соответствующему объекту.

> **Уточнить.** Глобальный поиск и центр уведомлений нужно сверить с MVP scope. Не следует автоматически считать их обязательными функциями первой версии.

## 3. Workspace / Projects

Это один из самых важных разделов. Именно здесь должна находиться основная рабочая среда юриста.

**MVP**

### WS-01. Создание личного Workspace

1. Пользователь нажимает «Создать проект».
2. Выбирает личное пространство.
3. Вводит название.
4. Подтверждает создание.
5. Система создаёт Workspace.
6. Пользователь становится OWNER.
7. Открывается новый Workspace.

### WS-02. Создание командного Workspace

1. Пользователь нажимает «Создать проект».
2. Выбирает командное пространство.
3. Вводит название и описание.
4. Подтверждает создание.
5. Система создаёт Workspace.
6. Пользователь становится OWNER.
7. Пользователь может пригласить участников.

### WS-03. Открытие Workspace

1. Пользователь открывает список пространств.
2. Выбирает нужный Workspace.
3. Система проверяет членство и права.
4. Открывает рабочую область.
5. Отображает чаты, документы, исследования и черновики, относящиеся к пространству.

### WS-04. Переименование Workspace

1. OWNER открывает настройки пространства.
2. Выбирает переименование.
3. Вводит новое название.
4. Сохраняет изменения.
5. Новое название отображается во всех связанных интерфейсах.

### WS-05. Редактирование описания

1. OWNER открывает настройки.
2. Изменяет описание.
3. Сохраняет изменения.

### WS-06. Переключение между Workspace

1. Пользователь открывает переключатель пространств.
2. Видит личные и доступные командные пространства.
3. Выбирает другое пространство.
4. Система переключает активный контекст.
5. Все последующие действия выполняются в новом Workspace.

### WS-07. Связывание Workspace с Client

1. Пользователь открывает настройки Workspace.
2. Переходит в раздел Client.
3. Выбирает существующего клиента или создаёт нового.
4. Подтверждает привязку.
5. Workspace связывается с Client.

### WS-08. Привязка Matter к Workspace

1. Пользователь открывает настройки Workspace.
2. Переходит к связанным делам.
3. Выбирает существующий Matter.
4. Подтверждает привязку.
5. Matter появляется в связанных делах Workspace.

### WS-09. Связывание одного Matter с несколькими Workspace

1. Пользователь открывает другой Workspace.
2. Выбирает привязку Matter.
3. Находит Matter, который уже связан с другим Workspace.
4. Подтверждает привязку.
5. Matter становится связанным с несколькими пространствами.

### WS-10. Удаление связи с Client или Matter

1. Пользователь открывает настройки Workspace.
2. Находит связанную сущность.
3. Выбирает «Отвязать».
4. Подтверждает действие.
5. Связь удаляется, сами сущности сохраняются.

### WS-11. Удаление Workspace

1. OWNER открывает настройки.
2. Выбирает удаление.
3. Система показывает предупреждение о последствиях.
4. Пользователь подтверждает удаление.
5. Система запрашивает дополнительное подтверждение.
6. После выполнения процесса Workspace становится недоступен.
7. Событие фиксируется в аудите.

> **Уточнить.** Сроки и точное поведение удаления, возможность восстановления, передача владения и обработка связанных сущностей должны соответствовать lifecycle-документации.

## 4. Участники Workspace и система ролей

В этом блоке особенно важно, чтобы Figma показала не только интерфейс владельца, но и интерфейсы остальных участников.

**MVP**

### MEM-01. Приглашение участника

1. OWNER открывает настройки Workspace.
2. Переходит в раздел «Участники».
3. Нажимает «Пригласить».
4. Вводит email сотрудника.
5. Выбирает роль EDITOR или VIEWER.
6. Отправляет приглашение.
7. Приглашение отображается в списке ожидающих.

### MEM-02. Принятие приглашения

1. Сотрудник получает приглашение.
2. Переходит по ссылке.
3. Авторизуется или регистрируется.
4. Принимает приглашение.
5. Получает доступ к Workspace.
6. Пространство появляется в его списке.

### MEM-03. Изменение роли участника

1. OWNER открывает список участников.
2. Выбирает сотрудника.
3. Меняет EDITOR на VIEWER или наоборот.
4. Подтверждает изменение.
5. Новые права начинают действовать.

### MEM-04. Удаление участника

1. OWNER открывает список участников.
2. Выбирает сотрудника.
3. Нажимает «Удалить из пространства».
4. Подтверждает действие.
5. Доступ сотрудника отзывается.
6. Данные Workspace сохраняются.

### MEM-05. Просмотр Workspace пользователем VIEWER

1. VIEWER открывает Workspace.
2. Видит доступные материалы.
3. Может просматривать разрешённые чаты, документы, исследования и черновики.
4. Не может выполнять действия, требующие прав редактирования.
5. При попытке недоступного действия интерфейс показывает ограничение доступа.

### MEM-06. Работа EDITOR

1. EDITOR открывает Workspace.
2. Создаёт чат, добавляет документы, проводит исследование.
3. Редактирует разрешённые материалы.
4. Не может управлять участниками и выполнять действия, зарезервированные за OWNER.

### MEM-07. Изменение участников Org Admin

1. Org Admin открывает панель организации.
2. Выбирает сотрудника.
3. Изменяет его организационное членство или доступ.
4. Подтверждает изменение.
5. Изменение применяется.
6. Это не предоставляет Org Admin автоматический доступ к содержимому Workspace.

### MEM-08. Увольнение сотрудника

1. Org Admin открывает список сотрудников.
2. Выбирает сотрудника.
3. Запускает процедуру удаления из организации.
4. Система отзывает его членство и доступы.
5. Пользователь теряет доступ к командным Workspace.
6. Его личные и командные данные не удаляются автоматически.
7. История действий сохраняется.

### MEM-09. Уход OWNER

1. OWNER инициирует передачу владения или выходит из организации.
2. Система должна обеспечить сохранение управляемости Workspace.
3. Назначается новый владелец в соответствии с предусмотренными правилами.

> **Уточнить.** Точная процедура передачи владения и поведение при отсутствии нового OWNER требуют отдельного продуктового решения.

## 5. AI Chat — основной рабочий сценарий

Это центральный инструмент взаимодействия юриста с AI.

**MVP**

### CHAT-01. Создание нового чата в Workspace

1. Пользователь открывает Workspace.
2. Нажимает «Новый чат».
3. Открывается интерфейс чата.
4. Пользователь вводит запрос.
5. Отправляет сообщение.
6. AI обрабатывает запрос.
7. Отображается ответ.
8. Чат сохраняется в Workspace.

### CHAT-02. Создание чата с Dashboard

1. Пользователь нажимает «Новый чат» на главной.
2. Выбирает Workspace, если это необходимо.
3. Открывается чат в выбранном контексте.
4. Пользователь отправляет запрос.
5. Получает ответ.

### CHAT-03. Продолжение существующего чата

1. Пользователь открывает список чатов.
2. Выбирает нужный диалог.
3. Загружается история сообщений.
4. Пользователь отправляет новое сообщение.
5. AI продолжает работу с учётом истории и доступного контекста.

### CHAT-04. Переименование чата

1. Пользователь открывает меню чата.
2. Выбирает переименование.
3. Вводит новое название.
4. Сохраняет изменения.

### CHAT-05. Удаление чата

1. Пользователь открывает меню чата.
2. Выбирает удаление.
3. Система показывает подтверждение.
4. Пользователь подтверждает.
5. Чат удаляется согласно правилам хранения данных.

### CHAT-06. Прикрепление документа к сообщению

1. Пользователь открывает чат.
2. Нажимает на прикрепление файла.
3. Выбирает документ.
4. Система проверяет формат и размер.
5. Документ загружается.
6. Пользователь вводит вопрос.
7. AI анализирует доступный документ.
8. Отображается ответ с привязкой к источнику, если такая информация доступна.

### CHAT-07. Запрос на анализ документа

1. Пользователь открывает чат.
2. Выбирает документ из Workspace.
3. Пишет «Проанализируй этот договор».
4. AI получает документ и запрос.
5. Выполняет анализ.
6. Возвращает структурированный ответ.

### CHAT-08. Уточнение ответа

1. AI отвечает на запрос.
2. Пользователь задаёт дополнительный вопрос.
3. AI использует предыдущий контекст.
4. Возвращает уточнённый ответ.

### CHAT-09. Ссылки на источники в ответе

1. AI возвращает юридический ответ.
2. В ответе присутствуют ссылки на источники.
3. Пользователь нажимает на цитату или ссылку.
4. Открывается источник либо его подробная карточка.
5. Пользователь может проверить фрагмент, документ и редакцию.

### CHAT-10. Копирование ответа

1. Пользователь наводит курсор на сообщение AI.
2. Нажимает «Копировать».
3. Ответ копируется в буфер обмена.

### CHAT-11. Повторная генерация

1. AI выдал ответ.
2. Пользователь нажимает «Повторить».
3. Система запускает повторную обработку.
4. Отображает новый результат.

### CHAT-12. Остановка генерации

1. AI генерирует ответ.
2. Пользователь нажимает «Остановить».
3. Генерация прекращается.
4. Интерфейс отображает доступную часть результата или состояние отмены.

### CHAT-13. Редактирование своего сообщения

1. Пользователь открывает меню отправленного сообщения.
2. Выбирает редактирование.
3. Меняет текст.
4. Повторно отправляет запрос.
5. AI обрабатывает обновлённый запрос.

> **Уточнить.** Наличие редактирования сообщений, повторной генерации и точное поведение остановки нужно сверить с workflow-спецификацией. Figma может показать их как предлагаемые UX-сценарии, но не должна считать подтверждёнными функциями.

### CHAT-14. Общий командный чат

1. OWNER или EDITOR создаёт чат в командном Workspace.
2. Чат становится доступен участникам с соответствующими правами.
3. Другой участник открывает его.
4. Просматривает историю.
5. Продолжает диалог, если ему разрешено редактирование.

### CHAT-15. Личный чат внутри командного Workspace

1. Пользователь находится в командном Workspace.
2. Создаёт личный чат.
3. Чат сохраняется в его личной области.
4. Другие участники Workspace не получают к нему доступ автоматически.

### CHAT-16. Переключение контекста чата

1. Пользователь открывает чат.
2. Проверяет, в каком Workspace находится.
3. Меняет контекст на другой доступный Workspace, если предусмотрено создание нового диалога в нём.
4. Система использует только разрешённые материалы нового контекста.

### CHAT-17. Запрос без достаточного контекста

1. Пользователь задаёт вопрос, требующий отсутствующего документа.
2. AI сообщает об ограничении контекста.
3. Пользователь может прикрепить документ или уточнить запрос.

### CHAT-18. Недостаточно прав на источник

1. Пользователь отправляет запрос.
2. Система обнаруживает, что необходимый документ недоступен пользователю.
3. Документ не используется при поиске.
4. AI не раскрывает его содержимое.
5. Интерфейс показывает понятное ограничение, если это уместно.

## 6. Documents — библиотека документов

Это отдельный полноценный модуль, а не просто кнопка прикрепления файла в чате.

**MVP**

### DOC-01. Открытие библиотеки

1. Пользователь открывает Workspace.
2. Переходит в Documents.
3. Видит список документов.
4. Может просматривать, искать и открывать доступные документы.

### DOC-02. Загрузка одного документа

1. Пользователь нажимает «Загрузить».
2. Выбирает файл.
3. Система проверяет формат.
4. Проверяет размер (максимум 25 МБ).
5. Начинает загрузку.
6. После завершения создаёт запись документа.
7. Запускает обработку.

### DOC-03. Массовая загрузка документов

1. Пользователь нажимает «Загрузить документы».
2. Выбирает несколько файлов.
3. Система проверяет каждый файл.
4. Принимает допустимые документы.
5. Отображает прогресс обработки каждого файла.

### DOC-04. Неподдерживаемый формат

1. Пользователь загружает файл неподдерживаемого формата.
2. Система отклоняет файл.
3. Показывает причину.
4. Предлагает выбрать другой файл.

### DOC-05. Превышение размера

1. Пользователь загружает файл больше 25 МБ.
2. Система отклоняет загрузку.
3. Показывает ограничение.

### DOC-06. Просмотр карточки документа

1. Пользователь нажимает на документ.
2. Открывается карточка.
3. Отображаются название, формат, размер, дата загрузки, статус обработки.
4. Пользователь может открыть доступные действия.

### DOC-07. Просмотр документа

1. Пользователь открывает документ.
2. Система отображает его содержимое или доступный preview.
3. Пользователь читает документ.
4. Может вернуться в библиотеку.

### DOC-08. Поиск документа

1. Пользователь открывает библиотеку.
2. Вводит название или поисковый запрос.
3. Система показывает доступные результаты.
4. Пользователь открывает нужный документ.

### DOC-09. Фильтрация документов

1. Пользователь открывает фильтры.
2. Выбирает формат, статус обработки или дату.
3. Список обновляется.

### DOC-10. Переименование документа

1. Пользователь открывает меню документа.
2. Выбирает переименование.
3. Вводит новое название.
4. Сохраняет.

### DOC-11. Повторная обработка

1. Пользователь открывает документ с ошибкой обработки.
2. Нажимает «Повторить обработку».
3. Система создаёт новую задачу.
4. Отображается её статус.
5. При успехе документ становится доступен для поиска.

### DOC-12. Удаление документа

1. Пользователь открывает меню документа.
2. Выбирает удаление.
3. Система показывает предупреждение.
4. Пользователь подтверждает.
5. Документ удаляется по установленным правилам.
6. Удаление отражается в аудите.

### DOC-13. Обработка документа в фоне

1. Пользователь загружает документ.
2. Закрывает библиотеку или переходит в чат.
3. Обработка продолжается в фоне.
4. Пользователь возвращается.
5. Видит актуальный статус.

### DOC-14. Ошибка OCR или извлечения текста

1. Документ успешно загружен.
2. Система не может извлечь текст.
3. Документ получает статус ошибки.
4. Пользователь видит причину или понятное сообщение.
5. Может повторить обработку или удалить файл.

### DOC-15. Повторная загрузка того же файла

1. Пользователь загружает документ, который уже есть в Workspace.
2. Система обнаруживает совпадение, если предусмотрена проверка дубликатов.
3. Показывает предупреждение или предлагает продолжить.

> **Уточнить.** Поддерживаемые форматы, OCR, версии документов, дубликаты и доступность preview должны быть сверены с документацией. Не стоит рисовать сложный редактор PDF или DOCX как подтверждённую функцию только на основании наличия загрузки.

## 7. RAG и поиск по знаниям Workspace

Этот модуль особенно важен для юридического продукта. Пользователь должен понимать, какие документы AI использовал и почему.

**MVP — базовый сценарий поиска**

### RAG-01. Вопрос по всем доступным документам Workspace

1. Пользователь открывает чат.
2. Задаёт вопрос по материалам проекта.
3. Система проверяет доступные документы.
4. Выполняет поиск релевантных фрагментов.
5. Передаёт найденные фрагменты AI.
6. AI формирует ответ.
7. Пользователь видит ответ и доступные ссылки на использованные источники.

### RAG-02. Поиск по конкретному документу

1. Пользователь выбирает документ.
2. Задаёт вопрос по нему.
3. Система ищет релевантные фрагменты только в выбранном документе.
4. AI формирует ответ.

### RAG-03. Поиск по нескольким выбранным документам

1. Пользователь открывает чат.
2. Выбирает несколько документов.
3. Задаёт вопрос.
4. Система ищет по выбранному набору.
5. AI формирует ответ с указанием источников.

### RAG-04. Просмотр источника ответа

1. Пользователь получает ответ AI.
2. Видит блок Sources / Sources used.
3. Нажимает на источник.
4. Открывается документ.
5. Показывается соответствующий фрагмент, если такая навигация реализована.

### RAG-05. Отсутствие подходящих документов

1. Пользователь задаёт вопрос по Workspace.
2. Система не находит релевантных фрагментов.
3. AI сообщает, что подходящей информации не обнаружено.
4. Пользователь может изменить запрос или добавить документы.

### RAG-06. Изменение документа после индексации

1. Пользователь загружает обновлённую версию документа.
2. Система запускает повторную обработку и индексацию.
3. Старый индекс заменяется или управляется в соответствии с правилами версий.
4. Новые запросы используют актуальные данные.

### RAG-07. Изменение прав доступа

1. OWNER удаляет участника из Workspace или меняет его роль.
2. Система обновляет доступ.
3. Последующие запросы пользователя не должны возвращать запрещённые документы.
4. Поиск и выдача результата повторно проверяют разрешения.

### RAG-08. Частично доступные результаты

1. Пользователь выполняет поиск.
2. Некоторые материалы недоступны.
3. Система исключает их.
4. Отображает только доступные результаты.

### RAG-09. Просмотр найденных фрагментов

1. Пользователь открывает результат поиска.
2. Видит найденный текстовый фрагмент.
3. Видит название документа.
4. Может перейти к исходному документу.

### RAG-10. Индексация документа ещё не завершена

1. Пользователь загружает документ.
2. Пытается выполнить поиск сразу после загрузки.
3. Система обнаруживает, что индексация ещё выполняется.
4. Показывает статус и предлагает дождаться завершения.

> **Уточнить.** Векторный поиск, полнотекстовый поиск, гибридное ранжирование и конкретный интерфейс управления поисковыми источниками — технические детали. Figma должна отобразить результат и состояния поиска, а не придумывать внутреннюю реализацию.

## 8. Legal Research — юридические исследования

6. Получает отфильтрованные результаты.

### RES-04. Просмотр конкретной статьи закона

3. Видит текст статьи.
4. Видит реквизиты документа.

### RES-05. Просмотр истории редакций

1. Пользователь открывает нормативный акт.
2. Переходит в историю редакций.
3. Выбирает нужную редакцию.
4. Система отображает текст соответствующей редакции.
5. Пользователь может сравнить редакции, если такая функция предусмотрена.

### RES-06. Проверка актуальности нормы

1. Пользователь открывает результат исследования.
2. Выбирает нормативную ссылку.
3. Система показывает дату редакции и сведения о действии нормы.
4. Пользователь проверяет актуальность источника.

### RES-07. Поиск судебной практики

1. Пользователь вводит юридический вопрос.
2. Выбирает поиск судебной практики.
3. Система отображает подходящие судебные акты.
4. Пользователь открывает конкретный документ.
5. Изучает обстоятельства дела, выводы суда и реквизиты.

### RES-08. Фильтрация судебной практики

1. Пользователь открывает результаты.
2. Выбирает фильтры: суд, период, категория дела и другие доступные параметры.
3. Список обновляется.
4. Пользователь открывает подходящий результат.

### RES-09. Просмотр источника исследования

1. Пользователь получает ответ.

4. Открывается источник.
5. Пользователь может проверить, действительно ли источник подтверждает вывод AI.

### RES-10. Сохранение исследования

1. Пользователь получает результат.
2. Нажимает «Сохранить».
3. Исследование сохраняется в Workspace.
4. Оно появляется в списке исследований.

### RES-11. Продолжение исследования

1. Пользователь открывает сохранённое исследование.
2. Задаёт дополнительный вопрос.
3. AI учитывает предыдущий контекст.
4. Результат дополняется.

### RES-12. Экспорт исследования

1. Пользователь открывает исследование.
2. Нажимает «Экспорт».
3. Выбирает доступный формат.
4. Система формирует документ.
5. Пользователь скачивает результат.

> **Уточнить.** Конкретные форматы экспорта, глубина поиска, поддержка сравнения редакций и доступность фильтров должны быть подтверждены продуктовой спецификацией.

### RES-13. Поиск не дал результатов

2. Система не находит подходящих источников.
3. Показывает пустой результат.
4. Предлагает изменить формулировку или фильтры.

1. Пользователь запускает исследование.
2. Источник недоступен или возвращает ошибку.
3. Система показывает частичный результат, если он есть.
4. Отмечает недоступные источники.
5. Позволяет повторить запрос.

### RES-15. Сохранение исследования как контекста чата

1. Пользователь открывает исследование.
2. Выбирает «Обсудить в чате».
3. Система создаёт или открывает чат в соответствующем Workspace.
4. Передаёт доступный контекст исследования.
5. Пользователь продолжает обсуждение.

## 11. Фоновые AI-задачи и обработка результатов

Пользователь не должен думать, что приложение зависло, если AI обрабатывает большой документ или выполняет исследование.

### JOB-03. Успешное выполнение

1. Задача переходит в succeeded.
2. Результат появляется в интерфейсе.
3. Пользователь может продолжить работу.

### JOB-04. Ошибка выполнения

1. Задача переходит в failed.
2. Пользователь видит сообщение об ошибке.
3. При возможности может повторить операцию.

### JOB-05. Отмена задачи

1. Пользователь нажимает «Отменить».
2. Система запрашивает отмену.
3. Задача переходит в cancelled.
4. Интерфейс отображает результат отмены.

### JOB-06. Превышение времени

1. Задача выполняется слишком долго.
2. Система фиксирует тайм-аут.
3. Задача получает timed_out.
4. Пользователь видит сообщение и доступные дальнейшие действия.

### JOB-07. Повторный вход во время обработки

1. Пользователь запускает задачу.
2. Закрывает браузер.
3. Через некоторое время снова открывает приложение.
4. Переходит к соответствующему чату или исследованию.
5. Видит актуальный статус и результат.

### JOB-08. Частичный результат

1. Система выполняет многоэтапное исследование.
2. Некоторые этапы завершаются успешно.
3. Другой этап завершается ошибкой.
4. Пользователь видит доступную часть результата и информацию о незавершённых этапах.

### JOB-09. Повторная обработка

1. Пользователь открывает завершившуюся с ошибкой задачу.
2. Нажимает «Повторить».
3. Система создаёт новую задачу или запускает предусмотренный механизм повторения.
4. Пользователь видит новый статус.

### JOB-10. Недоступность AI-провайдера

1. Пользователь отправляет запрос.
2. AI-провайдер недоступен.
3. Система показывает понятную ошибку.
4. Задача фиксируется в соответствующем состоянии.
5. Пользователь может повторить запрос после восстановления сервиса.

> **Важно.** На текущем этапе предусмотрен SyntheticAIProvider. Поэтому в интерфейсе не следует показывать, будто полноценная интеграция с реальным внешним AI-провайдером уже работает.

## 12. Организация, безопасность и административный доступ

Это один из самых важных блоков для юридического B2B-продукта. Здесь недостаточно просто нарисовать страницу настроек организации.

**MVP**

### SEC-01. Просмотр состава организации

1. Org Admin открывает настройки организации.
2. Переходит в раздел сотрудников.
3. Видит участников организации.
4. Видит их организационные роли и статусы.

### SEC-02. Приглашение сотрудника

1. Org Admin нажимает «Пригласить сотрудника».
2. Вводит email.
3. Отправляет приглашение.
4. Видит статус приглашения.

### SEC-03. Изменение организационной роли

1. Org Admin выбирает сотрудника.
2. Изменяет его организационную роль.
3. Система проверяет допустимость операции.
4. Изменение сохраняется.

### SEC-04. Запрос привилегированного доступа

1. Org Admin открывает раздел административного доступа.
2. Выбирает Workspace или необходимые данные.
3. Указывает причину.
4. Указывает требуемую область доступа.
5. Отправляет запрос.
6. Запрос получает статус ожидания согласования.

### SEC-05. Одобрение административного доступа

1. Уполномоченный сотрудник открывает список запросов.
2. Видит автора запроса.
3. Видит причину.
4. Видит запрашиваемую область доступа.
5. Проверяет обоснованность.
6. Одобряет или отклоняет запрос.
7. Решение фиксируется в аудите.

### SEC-06. Отклонение запроса

1. Уполномоченный сотрудник открывает запрос.
2. Проверяет его.
3. Отклоняет.
4. При необходимости указывает причину.
5. Автор запроса получает соответствующий статус.

### SEC-07. Использование одобренного доступа

1. Запрос одобрен.
2. Администратор получает доступ в пределах разрешённого scope.
3. Система фиксирует начало доступа.
4. Отображается срок действия.
5. Администратор выполняет разрешённые действия.

### SEC-08. Истечение административного доступа

1. Наступает время истечения разрешения.
2. Система автоматически отзывает доступ.
3. Администратор больше не может читать защищённые материалы.
4. Событие отражается в аудите.

### SEC-09. Досрочный отзыв доступа

1. Уполномоченный сотрудник открывает активные разрешения.
2. Выбирает нужное.
3. Нажимает «Отозвать».
4. Подтверждает действие.
5. Доступ немедленно прекращается.

### SEC-10. Просмотр истории запросов

1. Администратор открывает журнал административных запросов.
2. Видит историю.
3. Может отфильтровать запросы по статусу, сотруднику и дате.
4. Открывает конкретную запись.

### SEC-11. Просмотр аудита

1. Уполномоченный пользователь открывает Audit Log.
2. Видит события.
3. Фильтрует их.
4. Открывает детали события.
5. Видит автора, действие, время и объект операции в пределах разрешённых данных.

### SEC-12. Попытка доступа без разрешения

1. Org Admin пытается открыть содержимое чужого Workspace.
2. Система обнаруживает отсутствие прав.
3. Доступ блокируется.
4. Интерфейс сообщает об ограничении.
5. При необходимости предлагает отправить запрос на привилегированный доступ.

### SEC-13. Удаление сотрудника и отзыв доступа

1. Org Admin удаляет сотрудника из организации.
2. Система отзывает его доступ к командным пространствам.
3. Активные административные разрешения прекращаются.
4. Данные сохраняются.
5. Событие записывается в аудит.

### SEC-14. Удаление данных с подтверждением

1. Уполномоченный пользователь инициирует удаление.
2. Система показывает последствия.
3. Пользователь подтверждает намерение.
4. Система запрашивает дополнительное подтверждение.
5. Запускается процесс удаления.
6. Интерфейс показывает статус операции.
7. Результат фиксируется в аудите.

### SEC-15. Просмотр статуса удаления

1. Пользователь открывает историю операций.
2. Находит запрос удаления.
3. Видит текущий статус.
4. После завершения видит подтверждение.

> **Уточнить.** Нужно строго соблюдать актуальные правила privileged access: второй уполномоченный сотрудник, ограничение срока до 60 минут, конкретная область доступа и обязательный аудит. Нельзя проектировать автоматический доступ администратора ко всем документам.

## 14. Системные, ошибочные и пограничные состояния

Вот здесь часто обнаруживается большая часть недостатков макетов. Figma обычно рисует идеальный сценарий, но забывает, что пользователь может столкнуться с ошибками.

Каждый основной экран должен иметь предусмотренные состояния.

| ID | Сценарий | Что должно отображаться |
|---|---|---|
| SYS-01 | Загрузка страницы | Skeleton / Loader |
| SYS-02 | Нет данных | Empty State |
| SYS-03 | Ошибка сервера | Error State |
| SYS-04 | Нет подключения к интернету | Offline State |
| SYS-05 | Нет прав | Access Denied |
| SYS-06 | Сессия истекла | Session Expired |
| SYS-07 | Запрос выполняется | Processing |
| SYS-08 | Запрос завершён | Success |
| SYS-09 | Запрос завершился ошибкой | Failure |
| SYS-10 | Превышено время выполнения | Timeout |
| SYS-11 | Нет результатов поиска | No Results |
| SYS-12 | Частичный результат | Partial Success |
| SYS-13 | Конфликт сохранения | Save Conflict |
| SYS-14 | Действие необратимо | Confirmation Modal |
| SYS-15 | Действие невозможно | Disabled / Tooltip |
| SYS-16 | Недоступный источник | Source Unavailable |
| SYS-17 | Обработка ещё не завершена | Pending |
| SYS-18 | Доступ отозван | Permission Revoked |
| SYS-19 | Приглашение истекло | Invitation Expired |
| SYS-20 | Пользователь удалён из организации | Membership Revoked |

Отдельно нужно предусмотреть:

- Повторную отправку запроса после ошибки.
- Защиту от двойного нажатия.
- Сохранение введённого текста при временной ошибке.
- Подтверждение удаления.
- Уведомление об успешном сохранении.
- Корректное отображение длинных названий и больших списков.
- Адаптивность интерфейса.
- Доступность клавиатурной навигации и понятные состояния фокуса.

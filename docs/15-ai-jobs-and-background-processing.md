# 15. AI Jobs and Background Processing

**Статус:** PROPOSED по деталям реализации; **CONFIRMED (D-008):** Redis + BullMQ; **CONFIRMED (D-011):** статусы AIJob.

## 1. Цель

Документ определяет единый механизм выполнения фоновых задач в сервисе.

Он должен обеспечивать:

- выполнение долгих операций без блокировки HTTP-запросов;
- повторную обработку временных ошибок;
- защиту от повторного выполнения одной операции;
- отмену задач;
- восстановление после падения worker-процесса;
- ограничение параллельной нагрузки;
- контроль стоимости AI-запросов;
- проверку прав доступа на протяжении выполнения задачи;
- корректное поведение при удалении документов и отзыве доступа;
- наблюдаемость и диагностику ошибок.

Главный принцип:

**Постановка задачи в очередь, её выполнение и сохранение результата — три отдельных этапа, каждый из которых должен быть безопасен при повторении.**

## 2. Какие операции выполняются в фоне

| Операция | Причина |
|---|---|
| Генерация ответа AI | Непредсказуемая продолжительность запроса |
| Создание юридического документа | Длительная генерация и возможные повторные попытки |
| Анализ документа | Извлечение текста, разбиение на фрагменты, создание embeddings |
| OCR | Высокая вычислительная нагрузка |
| Подготовка исследования | Несколько последовательных AI- и поисковых операций |
| Повторная обработка документа | Необходимость восстановления после ошибки |
| Массовая обработка файлов | Нельзя выполнять без ограничений в API-процессе |

Не всякая операция обязана использовать одну очередь. Например, OCR и LLM-запросы имеют разные профили нагрузки, поэтому в дальнейшем их следует разделить на отдельные очереди или группы workers.

## 3. Термины

Важно не смешивать четыре сущности.

**Business job** — запись о задаче в приложении. Она содержит владельца, тип операции, статус, параметры, результат и информацию об ошибках.

**Queue message** — сообщение, которое сообщает worker, что задача доступна для выполнения. Сообщение не является источником истины о состоянии задачи.

**Worker** — процесс, который забирает задачу, проверяет её состояние, выполняет операцию и сохраняет результат.

**Provider request** — отдельный запрос к внешнему AI-провайдеру или локальной модели. Одна задача может включать несколько таких запросов.

Например, задача «подготовить проект договора» может состоять из нескольких этапов и нескольких запросов к модели. Повтор всей задачи не должен автоматически означать повтор уже успешно завершённых этапов.

## 4. Предлагаемая архитектура

```text
Next.js frontend
      |
      v
NestJS API
      |
      | 1. Проверка пользователя и прав
      | 2. Создание AIJob
      | 3. Запись события в Outbox
      v
PostgreSQL
      |
      | Outbox publisher
      v
Queue / Redis
      |
      v
Worker
      |
      | Проверка статуса и прав
      | Получение контекста
      | Вызов AI Gateway
      | Проверка результата
      v
PostgreSQL + private object storage
      |
      v
Frontend получает статус и результат
```

### 4.1. Технологический вариант

- NestJS — API и общие сервисы бизнес-логики (**D-008**).
- PostgreSQL — источник истины для состояния задач и результатов (**D-008**).
- BullMQ + Redis — очередь фоновых задач (**CONFIRMED, D-008**).
- Отдельные worker-процессы — выполнение фоновых задач.
- AI Gateway — единая точка доступа к моделям и провайдерам.
- Private object storage — хранение больших результатов и файлов.

Redis и BullMQ — **подтверждённый** выбор очереди MVP (**D-008**). Требования к надёжности, идемпотентности и обработке повторов обязательны независимо от деталей конфигурации workers.

### 4.2. Источник истины

PostgreSQL хранит актуальный статус задачи.

Очередь отвечает только за доставку сообщений исполнителям. Если сообщение потерялось, появилось дважды или было доставлено после отмены задачи, система должна корректно обработать ситуацию по состоянию в БД.

## 5. Модель данных

Ниже перечислены предлагаемые сущности и расширения. Это не окончательная схема Prisma.

### 5.1. AIJob

Основная запись задачи.

Предлагаемые поля:

- `id` — UUID;
- `organizationId` — организация;
- `createdByUserId` — создатель;
- `workspaceId` — рабочее пространство, если применимо;
- `conversationId` — диалог, если применимо;
- `type` — тип задачи;
- `status` — текущее состояние;
- `priority` — приоритет;
- `input` — минимальные параметры задачи или ссылка на защищённый контекст;
- `inputHash` — отпечаток нормализованного запроса;
- `idempotencyKey` — ключ идемпотентности;
- `attemptCount` — количество попыток;
- `maxAttempts` — максимально разрешённое число попыток;
- `createdAt`;
- `startedAt`;
- `completedAt`;
- `cancelRequestedAt`;
- `nextRetryAt`;
- `lastErrorCode`;
- `resultId` — ссылка на результат;
- `estimatedCost`;
- `actualCost`;
- `requestId` — идентификатор для трассировки.

Не следует без необходимости копировать полный текст юридических документов в поле `input`. Лучше хранить идентификаторы документов, версий и необходимые параметры. Если снимок входных данных необходим для воспроизводимости, он должен иметь отдельную политику доступа, хранения и удаления.

### 5.2. AIJobAttempt

История отдельных попыток выполнения.

Предлагаемые поля:

- `id`;
- `jobId`;
- `attemptNumber`;
- `workerId`;
- `startedAt`;
- `finishedAt`;
- `status`;
- `providerId`, если применимо;
- `modelId`, если применимо;
- `providerRequestId`, если он предоставлен;
- `errorCode`;
- `errorCategory`;
- `inputTokens`;
- `outputTokens`;
- `estimatedCost`;
- `actualCost`;
- `durationMs`.

Не сохранять секреты, API-ключи и полный конфиденциальный промпт в технических логах.

### 5.3. OutboxEvent

Событие, которое необходимо надёжно передать в очередь.

Предлагаемые поля:

- `id`;
- `eventType`;
- `aggregateId` — например, `jobId`;
- `payload`;
- `createdAt`;
- `publishedAt`;
- `attemptCount`;
- `lastError`;
- `nextAttemptAt`.

Outbox нужен для защиты от ситуации, когда запись задачи в PostgreSQL прошла успешно, а публикация сообщения в очередь — нет.

### 5.4. Job lease / heartbeat

Для контроля зависших задач worker должен периодически подтверждать, что он продолжает выполнять работу.

Вариант реализации — отдельные поля в `AIJob`:

- `leaseOwner`;
- `leaseExpiresAt`;
- `heartbeatAt`.

Либо отдельная сущность, если это удобнее выбранной очереди.

Lease не заменяет блокировки и проверку статуса в БД. Он помогает обнаруживать задачи, которые могли остаться без исполнителя после аварийного завершения процесса.

### 5.5. AIUsageRecord

Учёт использования модели.

Предлагается фиксировать отдельно каждый фактический вызов провайдера, включая случаи с неопределённым исходом, когда запрос мог быть обработан провайдером, но ответ не дошёл до приложения.

Запись должна содержать ссылку на задачу и попытку, модель, доступные данные об использовании токенов, стоимость и статус расчёта.

Это расширение согласуется с учётом использования в `docs/14-ai-provider-and-model-gateway.md`.

## 6. Статусы задачи

**CONFIRMED (D-011).** Допустимые статусы AIJob — только:

| Статус | Значение |
|---|---|
| `queued` | Задача создана и ожидает выполнения |
| `running` | Задача выполняется |
| `succeeded` | Задача успешно завершена |
| `failed` | Задача завершилась окончательной ошибкой |
| `cancelled` | Задача отменена |
| `timed_out` | Превышено допустимое время выполнения |

Статусы `retry_wait` и `completed` **не используются**. Ожидание повтора выражается полями (`attemptCount`, `nextRetryAt`, `maxAttempts` и т.п.) при статусе `queued` или `running`, а не отдельным статусом job. Успех — только `succeeded`.

Терминальный статус — `succeeded`, `failed`, `cancelled` или `timed_out`. После перехода в терминальный статус задача не должна самопроизвольно возвращаться к выполнению.

### 6.1. Допустимые переходы

```text
queued
  ├──> running
  └──> cancelled

running
  ├──> succeeded
  ├──> queued          # повтор: через поля nextRetryAt / attemptCount, не через статус retry_wait
  ├──> failed
  ├──> timed_out
  └──> cancelled
```

Переходы должны контролироваться серверной логикой. Нельзя позволять клиенту произвольно передавать новый статус через API.

Если отмена запрошена во время выполнения, задача может некоторое время оставаться в `running`, пока worker не подтвердит отмену. Для UI при необходимости можно отдельно возвращать признак `cancellationRequested`.

## 7. Создание задачи и надёжная публикация

При создании задачи API должен:

1. Аутентифицировать пользователя.
2. Проверить членство в организации.
3. Проверить права на целевое рабочее пространство, документы и диалог.
4. Проверить формат и допустимость входных данных.
5. Проверить лимиты, квоты и доступность операции.
6. Зарезервировать бюджет, если для этого типа задачи используется предварительное резервирование.
7. Создать `AIJob`.
8. Создать `OutboxEvent`.
9. Зафиксировать изменения в одной транзакции PostgreSQL.
10. Вернуть `202 Accepted` и идентификатор задачи.

Публикация события в очередь выполняется отдельно после фиксации транзакции.

### 7.1. Почему нельзя просто записать задачу и отправить сообщение

Предположим, приложение сначала записало задачу в БД, а затем попыталось отправить её в Redis. Если Redis недоступен, задача останется в БД, но worker о ней не узнает.

Обратный порядок тоже небезопасен: сообщение может попасть в очередь, а транзакция БД завершиться ошибкой.

Transactional Outbox устраняет эту проблему: задача и событие создаются в одной транзакции, а отдельный процесс повторяет публикацию до успеха.

### 7.2. Обработка Outbox

Publisher должен:

- выбирать неопубликованные события;
- публиковать их в очередь;
- помечать событие как опубликованное после подтверждения;
- повторять попытки при временных ошибках;
- отслеживать возраст самого старого неопубликованного события;
- поддерживать безопасную повторную публикацию.

Возможна ситуация, когда сообщение отправлено, но процесс упал до записи `publishedAt`. Поэтому повторная публикация допустима, а worker обязан быть идемпотентным.

## 8. Идемпотентность

Идемпотентность означает, что повтор одного и того же запроса не создаёт несколько независимых задач и не приводит к повторному выполнению уже завершённой операции без необходимости.

### 8.1. HTTP API

Для операций создания задачи поддержать `Idempotency-Key`.

Сервер связывает ключ с организацией, пользователем, типом операции и нормализованным содержимым запроса.

Правила:

- повтор того же ключа и того же запроса возвращает существующую задачу;
- повтор ключа с другим содержимым возвращает конфликт;
- ключ не должен быть глобальным между организациями;
- срок хранения ключей должен быть определён;
- проверка и создание выполняются атомарно.

### 8.2. Worker

Перед выполнением worker проверяет:

- существует ли задача;
- допускает ли текущий статус выполнение;
- не отменена ли задача;
- не завершена ли она другим worker;
- не выполняется ли уже эта задача с действующей арендой.

Повторная доставка сообщения не должна приводить к повторной публикации результата или созданию дублирующих сообщений в диалоге.

### 8.3. Внешние AI-запросы

Идемпотентность самого приложения не гарантирует идемпотентность внешнего провайдера.

Если запрос отправлен, но соединение оборвалось до получения ответа, приложение может не знать, выполнил ли провайдер запрос и начислил ли стоимость.

Поэтому:

- использовать idempotency-механизм провайдера, если он документирован и подходит для этой операции;
- сохранять идентификаторы вызовов и доступные данные об использовании;
- не считать неизвестный результат гарантированно бесплатным;
- не повторять автоматически потенциально дорогостоящую операцию без классификации ошибки и проверки политики повторов.

## 9. Выполнение задачи worker-процессом

Рекомендуемый алгоритм:

1. Получить сообщение из очереди.
2. Прочитать задачу из PostgreSQL.
3. Проверить статус и возможность выполнения.
4. Атомарно получить право на выполнение задачи.
5. Установить lease и начать heartbeat.
6. Повторно проверить доступ пользователя к необходимому контексту.
7. Проверить лимиты и доступный бюджет.
8. Получить актуальные версии документов и необходимые данные.
9. Выполнить операцию через сервисный слой и AI Gateway.
10. Проверить результат.
11. Перед сохранением результата повторно проверить состояние задачи и применимые ограничения доступа.
12. Сохранить результат и обновить статус в транзакции.
13. Зафиксировать фактическое использование и расчёт стоимости.
14. Освободить lease и завершить обработку.

Каждый этап должен иметь понятную стратегию восстановления после сбоя.

Не следует полагаться только на проверку статуса в начале выполнения: задача может быть отменена, документ удалён или доступ отозван уже во время вызова модели.

## 10. Lease, heartbeat и восстановление

Worker периодически обновляет heartbeat и продлевает lease.

Если lease истёк, задача считается потенциально зависшей. Восстановитель проверяет её состояние и определяет дальнейшее действие.

Восстановитель не должен безусловно повторно запускать любую задачу с истёкшим lease: предыдущий worker мог отправить запрос провайдеру, но не успеть записать ответ.

Правила восстановления:

- `queued` без сообщения в очереди — повторная публикация;
- `running` с истёкшим lease — проверка состояния и восстановление;
- задача с известным безопасным этапом — продолжение с последнего подтверждённого этапа;
- задача с неопределённым результатом внешнего вызова — применение политики неопределённого исхода;
- терминальная задача — повторно не запускать.

При завершении worker должен корректно прекращать приём новых задач и давать активным операциям ограниченное время на завершение или безопасную передачу управления.

## 11. Повторные попытки и обработка ошибок

Повторы должны быть ограничены и зависеть от типа ошибки.

### 11.1. Ошибки, которые обычно можно повторять

- временная недоступность провайдера;
- HTTP 429 с соблюдением `Retry-After`;
- временные сетевые ошибки;
- временная недоступность очереди или БД;
- некоторые ошибки 5xx.

### 11.2. Ошибки, которые обычно не следует повторять автоматически

- невалидный входной запрос;
- отсутствие прав;
- удалённый документ;
- неподдерживаемый формат;
- некорректная конфигурация;
- отсутствие необходимой модели или провайдера;
- превышение лимита, если ожидание не меняет ситуацию;
- отказ по политике обработки данных.

Ошибки должны классифицироваться централизованно. Не следует определять повтор только по тексту сообщения.

### 11.3. Backoff

Предлагается экспоненциальная задержка с jitter — случайным разбросом, чтобы множество задач не повторялись одновременно.

Примерная схема задержек:

- первая повторная попытка — около 2 секунд;
- вторая — около 5 секунд;
- третья — около 15 секунд;
- дальнейшие попытки — с увеличением задержки и верхним ограничением.

Это пример, а не утверждённые значения. Для 429 приоритет имеет документированный `Retry-After`.

Максимальное количество попыток и общий дедлайн зависят от типа задачи. Генерация текста и OCR могут иметь разные лимиты.

### 11.4. Исчерпание попыток

Когда лимит попыток исчерпан:

- задача переводится в `failed` или `timed_out`;
- сохраняется безопасный код ошибки;
- освобождается резерв бюджета или выполняется его окончательный расчёт;
- ошибка становится доступна клиенту в нормализованном виде;
- событие фиксируется в наблюдаемости;
- при необходимости задача попадает в очередь ручного разбора.

Dead-letter queue или аналогичный механизм допустим для диагностики. Ручной повтор должен быть отдельным контролируемым действием, а не автоматическим бесконечным циклом.

## 12. Отмена задачи

API должен предоставлять возможность отменить задачу, если её состояние допускает отмену.

Отмена включает:

1. Проверку прав пользователя на задачу.
2. Фиксацию запроса на отмену в БД.
3. Попытку отменить сообщение или выполнение средствами очереди.
4. Уведомление worker, если задача уже выполняется.
5. Прекращение дальнейших этапов задачи.
6. Запрет публикации результата после подтверждённой отмены.
7. Корректировку учёта расходов.

### 12.1. Отмена внешнего запроса

Если провайдер поддерживает отмену, AI Gateway может использовать её. Однако отмена на стороне приложения не гарантирует, что провайдер немедленно остановил генерацию или перестал учитывать стоимость.

Поэтому система должна различать:

- отмену задачи в приложении;
- подтверждённую отмену запроса провайдером, если такой механизм есть;
- фактическое использование и стоимость, которые могли возникнуть до отмены.

### 12.2. Гонка между отменой и завершением

Возможна ситуация, когда worker получил ответ модели одновременно с запросом отмены.

Переход в терминальный статус и сохранение результата должны быть защищены транзакцией и проверкой актуального состояния. Если задача уже отменена, worker не должен публиковать результат как успешный.

Отмена не означает, что уже отправленные внешнему провайдеру данные можно отозвать. Это отдельный вопрос политики обработки данных.

## 13. Права доступа во время выполнения

Проверка доступа при создании задачи недостаточна.

Права необходимо проверять:

- при создании задачи;
- перед началом выполнения;
- перед получением документов и других защищённых данных;
- перед каждым последующим этапом, если он обращается к защищённому контексту;
- перед сохранением результата;
- при чтении статуса и результата через API.

### 13.1. Если доступ отозван

Если пользователь потерял доступ к рабочему пространству, документу или организации, система не должна раскрывать результат только потому, что задача была создана ранее.

Минимальное обязательное поведение:

- запрещать чтение результата пользователю, потерявшему доступ;
- не использовать документ, который больше недоступен для соответствующего сценария;
- проверять актуальные права перед формированием защищённого результата;
- не публиковать результат в недоступный диалог;
- учитывать правила удаления данных из `docs/08-data-lifecycle-and-deletion.md`.

Нужно отдельно определить, отменять ли автоматически все ещё не начавшиеся задачи при отзыве доступа. Это зависит от того, какие данные задача уже зафиксировала и какая политика принята для организации.

**Важно:** результат AI — тоже защищённые данные. Нельзя считать его безопасным только потому, что он уже создан.

## 14. Удаление документов и данных

Если документ удаляется во время выполнения задачи, worker обязан учитывать жизненный цикл документа.

До начала обработки нужно проверить, что документ существует, находится в допустимом состоянии и доступен для данного сценария.

При удалении документа система должна:

- пометить документ в соответствии с правилами жизненного цикла;
- запретить создание новых задач на его основе;
- остановить или безопасно завершить связанные задачи;
- не позволять сохранять результаты, нарушающие политику удаления;
- удалить или поставить на удаление производные данные в соответствии с `docs/08-data-lifecycle-and-deletion.md`;
- корректно обработать временные файлы и промежуточные результаты.

Если операция уже отправлена внешнему провайдеру, приложение не может гарантировать удаление данных на стороне провайдера без соответствующего подтверждённого механизма. Это ограничение должно учитываться при выборе провайдера и политике обработки данных.

## 15. Ограничение нагрузки

Очередь сама по себе не защищает от перегрузки. Нужны явные лимиты.

### 15.1. Уровни ограничения

Предлагается ограничивать:

- общее количество одновременно выполняемых задач;
- количество активных задач на организацию;
- количество активных задач на пользователя;
- число запросов к конкретному провайдеру;
- число запросов к конкретной модели;
- параллельную обработку документов;
- максимальный размер входных данных;
- допустимую стоимость одной задачи;
- суммарный бюджет организации за установленный период.

Лимиты должны конфигурироваться и не быть разбросаны по контроллерам и worker-классам.

### 15.2. Разделение типов задач

Минимально разумно разделить нагрузку на:

- `ai-interactive` — диалог и короткие генерации;
- `ai-long-running` — исследования и большие генерации;
- `document-processing` — извлечение текста и подготовка документов;
- `ocr` — OCR и тяжёлые операции обработки изображений.

Это логическое разделение. Физически очереди можно объединить на старте, если нагрузка небольшая, но архитектура должна позволять выделить отдельные workers без переписывания бизнес-логики.

### 15.3. Приоритеты

Приоритеты могут использоваться для интерактивных задач, однако они не должны позволять одной организации постоянно вытеснять задачи остальных.

Нужно определить правила справедливого распределения ресурсов, ограничения на высокие приоритеты и защиту от злоупотреблений.

## 16. Учёт стоимости и бюджетов

Задача может содержать несколько вызовов модели, поэтому стоимость нельзя рассчитывать только по числу задач.

### 16.1. Резервирование бюджета

Перед выполнением дорогостоящей операции система может зарезервировать предполагаемую стоимость.

Резервирование должно быть атомарным относительно доступного бюджета организации. Иначе параллельные задачи смогут одновременно потратить один и тот же остаток.

После завершения:

- фактическая стоимость фиксируется;
- резерв корректируется;
- неиспользованный остаток освобождается;
- превышение ожидаемой стоимости обрабатывается по принятой политике.

### 16.2. Неопределённая стоимость

Если сетевое соединение оборвалось после отправки запроса, но до получения ответа, фактическое использование может быть неизвестно.

В таком случае нельзя автоматически считать запрос бесплатным. Запись использования должна иметь соответствующий статус, например `unknown` или `pending_reconciliation`, если это поддерживается моделью учёта.

### 16.3. Защита от дорогих циклов

Для каждой задачи нужно определить:

- максимальное количество вызовов модели;
- максимальный бюджет;
- максимальное время выполнения;
- максимальный объём входных и выходных данных;
- допустимые стратегии повторов;
- условия перехода к другому провайдеру или модели.

Fallback на другую модель не должен обходить ограничения конфиденциальности, бюджета или политики организации.

## 17. Передача результата клиенту

Основной способ взаимодействия — асинхронный API:

1. Клиент создаёт задачу.
2. Получает `jobId`.
3. Запрашивает статус.
4. При завершении получает результат.

Предлагаемые endpoints описаны в `docs/11-api-conventions.md`:

- `POST /api/v1/ai-jobs`;
- `GET /api/v1/ai-jobs/{jobId}`;
- `GET /api/v1/ai-jobs/{jobId}/result`;
- `POST /api/v1/ai-jobs/{jobId}/cancel`.

Результат может быть небольшим JSON-объектом либо ссылкой на защищённый объект в хранилище.

Перед выдачей результата API проверяет актуальные права доступа. Нельзя полагаться на то, что пользователь когда-то имел право создать задачу.

### 17.1. SSE и потоковая генерация

Server-Sent Events (SSE) могут использоваться для отображения прогресса или потокового ответа.

Но SSE не заменяет сохранение состояния задачи в БД.

Если клиент отключился:

- задача может продолжить работу, если это соответствует выбранному режиму;
- при повторном подключении клиент получает актуальный статус;
- повторная подписка не запускает новую задачу;
- доступ к потоку проверяется на сервере;
- сообщения потока не должны содержать данные, которые пользователь больше не вправе видеть.

Для первого MVP допустимо начать с опроса статуса, а SSE добавить после стабилизации механизма фоновых задач. Для интерактивного чата решение о потоковой генерации следует согласовать отдельно.

## 18. Безопасность

Обязательные требования:

- каждый endpoint проверяет аутентификацию и авторизацию;
- `jobId` не является доказательством права доступа;
- нельзя получать чужие задачи через подбор UUID;
- входные параметры проходят runtime-валидацию;
- ошибки провайдера не возвращаются клиенту в сыром виде;
- секреты и API-ключи не попадают в очередь, пользовательские ошибки и логи;
- защищённые входные данные не передаются в общедоступные очереди или внешние сервисы без одобренной политики;
- worker использует минимально необходимые права;
- временные файлы защищены и удаляются;
- внутренние административные действия аудируются;
- результаты и ссылки на файлы защищены теми же правилами доступа, что и исходные данные.

Очередь должна передавать минимальный набор данных: обычно `jobId`, тип события и технические метаданные. Полные юридические документы не следует вкладывать в сообщение очереди без необходимости.

## 19. Наблюдаемость

### 19.1. Метрики

Предлагается отслеживать:

- число задач по типам и статусам;
- время ожидания в очереди;
- длительность выполнения;
- долю успешных задач;
- количество повторных попыток;
- количество задач с исчерпанными попытками;
- возраст самой старой задачи в очереди;
- количество зависших задач;
- задержку публикации Outbox;
- число отмен;
- количество ошибок по провайдерам;
- стоимость по организации, модели и типу задачи;
- число вызовов с неопределённым результатом;
- использование concurrency-лимитов.

### 19.2. Логи

Каждая запись по задаче должна содержать, где применимо:

- `requestId`;
- `jobId`;
- `attemptId`;
- `organizationId`;
- `workerId`;
- тип задачи;
- этап выполнения;
- нормализованный код ошибки.

Полные тексты юридических документов, промпты с конфиденциальными данными и ответы моделей не должны попадать в обычные технические логи.

### 19.3. Оповещения

Нужно предусмотреть оповещения о:

- длительной задержке очереди;
- росте количества окончательных ошибок;
- зависших задачах;
- недоступности Redis или выбранной очереди;
- накоплении неопубликованных Outbox-событий;
- росте стоимости или превышении бюджета;
- массовых ошибках AI Gateway.

Пороговые значения следует определить после получения реальных данных нагрузки.

## 20. Тестирование

Обязательные сценарии:

### Создание и идемпотентность
- повтор одного `Idempotency-Key` не создаёт новую задачу;
- тот же ключ с другим запросом возвращает конфликт;
- сбой после фиксации транзакции не теряет задачу;
- повторная публикация Outbox безопасна.

### Выполнение
- задача успешно проходит весь жизненный цикл;
- повторное сообщение не создаёт дубликат результата;
- два worker не выполняют одну задачу одновременно без разрешённой стратегии;
- падение worker восстанавливается;
- задача с терминальным статусом не запускается повторно.

### Повторы
- временная ошибка приводит к повтору;
- постоянная ошибка не вызывает бесконечные повторы;
- учитывается `Retry-After`;
- исчерпание попыток переводит задачу в конечный статус;
- неопределённый исход внешнего вызова обрабатывается по отдельной политике.

### Отмена
- отмена до запуска исключает выполнение;
- отмена во время выполнения предотвращает публикацию результата;
- гонка отмены и завершения не приводит к противоречивому статусу;
- расходы за уже выполненные вызовы не исчезают из учёта.

### Доступ и удаление
- пользователь не читает чужую задачу;
- отзыв доступа блокирует получение результата;
- удалённый документ не используется для нового этапа;
- результат не сохраняется вопреки правилам удаления;
- задача не публикует результат в недоступный диалог.

### Нагрузка и бюджеты
- лимиты организации и пользователя соблюдаются при параллельных запросах;
- резерв бюджета не расходуется дважды;
- превышение бюджета блокирует новые дорогостоящие вызовы;
- тяжёлая обработка документов не блокирует интерактивные задачи.

## 21. Критерии готовности

Механизм фоновых задач считается готовым для MVP, когда:

- [ ] API создаёт задачу и возвращает её идентификатор;
- [ ] состояние задачи хранится в PostgreSQL;
- [ ] публикация сообщений надёжна благодаря Outbox или эквивалентному механизму;
- [ ] повторная доставка сообщения не приводит к дублированию результата;
- [ ] worker умеет восстанавливаться после сбоя;
- [ ] настроены таймауты и ограниченные повторные попытки;
- [ ] реализована отмена;
- [ ] проверяются права доступа при получении результата;
- [ ] удаление документа корректно обрабатывается активными задачами;
- [ ] учитываются фактические расходы и неопределённые результаты запросов;
- [ ] настроены лимиты нагрузки;
- [ ] реализованы логи, метрики и базовые оповещения;
- [ ] автоматические тесты покрывают критические гонки и сбои;
- [ ] документация API соответствует фактической реализации.

## 23. Инструкции для реализации через Cursor

При реализации Cursor должен:

1. Сначала изучить существующие модули и соглашения проекта; сверить `docs/decisions-log.md` (**D-008**, **D-011**).
2. Сверить модель задачи с `docs/06-data-model.md` и API из `docs/11-api-conventions.md`.
3. Не создавать вторую несовместимую модель `AIJob`, если она уже существует.
4. Использовать Redis + BullMQ как подтверждённую очередь MVP (**D-008**); не подменять стек без нового решения в журнале.
5. Статусы AIJob только по **D-011**: `queued`, `running`, `succeeded`, `failed`, `cancelled`, `timed_out` (не `retry_wait`, не `completed` как статус job; ретраи — поля).
6. Реализовать создание задачи, публикацию события и обработку сообщения как отдельные этапы.
7. Не использовать только память процесса для хранения статусов и прогресса.
8. Добавить тесты на повторную доставку, падение worker, отмену и отзыв доступа.
9. Не считать проверку прав при создании задачи достаточной для защиты результата.
10. Не логировать конфиденциальные юридические данные.
11. Не реализовывать неоговорённые политики хранения, расходы или автоматический доступ к данным.
12. Обновить документацию после фактической реализации.
13. Отдельно сообщить о компромиссах, незакрытых решениях и сценариях, которые не покрыты тестами.

---

**Итог:** фоновые задачи должны быть устойчивыми к повторной доставке, падению worker, отмене, отзыву доступа и неопределённому результату AI-вызова. Очередь — это механизм доставки работы, а не источник истины о задаче. Источником истины остаётся БД, а права доступа должны действовать на протяжении всего жизненного цикла операции.

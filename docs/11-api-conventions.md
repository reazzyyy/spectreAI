# 11. API Conventions — Соглашения и стандарты Backend API

**Статус:** PROPOSED для деталей контрактов; **CONFIRMED:** стек/префикс `/api/v1` (**D-008**), статусы AIJob (**D-011**), сущности Client/Matter в MVP (**D-009**).  
**Версия:** 0.2  
**Тип документа:** техническая спецификация  
**Приоритет:** высокий

## 1. Цель

Документ определяет единые соглашения для HTTP API приложения.

Цели:

1. Обеспечить предсказуемое взаимодействие frontend и backend.
2. Исключить различия в обработке одинаковых ситуаций между модулями.
3. Сделать API удобным для типизации и автоматического тестирования.
4. Обеспечить единый формат ошибок.
5. Стандартизировать валидацию входных данных.
6. Не допустить обхода авторизации через отдельные endpoint'ы.
7. Предусмотреть безопасную работу с долгими AI-задачами.
8. Упростить изменение API без хаотичных несовместимостей.

Документ является нормативным для новых endpoint'ов после утверждения. Он не означает, что API уже реализован.

## 3. Общие правила REST API

### 3.1. Базовый адрес

Все прикладные endpoint'ы располагаются под префиксом:

`/api/v1`

Примеры:

```text
GET    /api/v1/workspaces
POST   /api/v1/workspaces
GET    /api/v1/workspaces/{workspaceId}
PATCH  /api/v1/workspaces/{workspaceId}
DELETE /api/v1/workspaces/{workspaceId}

GET    /api/v1/clients
POST   /api/v1/clients
GET    /api/v1/clients/{clientId}

GET    /api/v1/matters
POST   /api/v1/matters
GET    /api/v1/matters/{matterId}
```

Ресурсы `clients` и `matters` входят в MVP (**D-009**). Связь с workspace в теле/фильтрах может быть необязательной.

Версия в URL позволяет менять контракт контролируемо. Изменение версии не должно использоваться как замена обычной обратной совместимости.

### 3.2. Именование ресурсов

- Использовать существительные во множественном числе.
- Использовать `kebab-case` для составных сегментов URL.
- Использовать HTTP-метод для выражения действия.
- Не кодировать бизнес-действия в названиях endpoint'ов без необходимости.

Предпочтительно:

```text
POST /api/v1/documents
GET  /api/v1/documents/{documentId}
PATCH /api/v1/documents/{documentId}
```

Для специальных операций допустимы отдельные подресурсы:

```text
POST /api/v1/documents/{documentId}/archive
POST /api/v1/ai-jobs/{jobId}/cancel
POST /api/v1/admin-access-requests/{requestId}/approve
```

Такие endpoint'ы должны соответствовать отдельным правилам авторизации и бизнес-валидации.

### 3.3. HTTP-методы

| Метод | Назначение |
|---|---|
| GET | Получение данных без изменения состояния |
| POST | Создание ресурса или запуск операции |
| PATCH | Частичное изменение ресурса |
| PUT | Полная замена ресурса, если действительно необходима |
| DELETE | Удаление или запрос на удаление согласно контракту |

GET не должен запускать генерацию, удалять данные или изменять состояние бизнес-сущности.

### 3.4. HTTP-статусы

| Код | Когда использовать |
|---|---|
| `200 OK` | Успешное чтение или изменение с ответом |
| `201 Created` | Ресурс создан |
| `202 Accepted` | Долгая задача принята в обработку |
| `204 No Content` | Успешная операция без тела ответа |
| `400 Bad Request` | Некорректный запрос общего уровня |
| `401 Unauthorized` | Нет действительной аутентификации |
| `403 Forbidden` | Доступ запрещён согласно выбранной политике |
| `404 Not Found` | Ресурс не найден либо скрыт от пользователя |
| `409 Conflict` | Конфликт состояния или ограничений целостности |
| `413 Content Too Large` | Превышен допустимый размер запроса или файла |
| `415 Unsupported Media Type` | Неподдерживаемый тип содержимого |
| `422 Unprocessable Content` | Входные данные не проходят семантическую валидацию |
| `429 Too Many Requests` | Превышен лимит запросов или квота |
| `500 Internal Server Error` | Неожиданная внутренняя ошибка |
| `502 Bad Gateway` | Ошибка взаимодействия с upstream-сервисом |
| `503 Service Unavailable` | Сервис временно недоступен |
| `504 Gateway Timeout` | Истёк допустимый срок ожидания upstream-сервиса |

Необходимо выбрать единый подход к разделению ошибок `400` и `422`. В рамках предлагаемого стандарта `400` используется для структурно некорректного запроса, а `422` — для данных, которые синтаксически допустимы, но не соответствуют правилам валидации.

Коды не должны использоваться механически: ответ обязан соответствовать фактической ситуации.

## 4. Формат JSON

### 4.1. Общие правила

- Поля JSON используют `camelCase`.
- Идентификаторы в API передаются строками.
- Даты и время передаются в ISO 8601.
- Время передаётся с явным часовым поясом; для системных временных отметок рекомендуется UTC.
- Денежные значения не должны терять точность из-за представления в JavaScript `number`.
- Неизвестные поля во входных DTO не должны молча изменять поведение endpoint'а.
- В ответ не включаются внутренние поля ORM или сущности базы данных напрямую.

Пример даты:

```json
{
  "createdAt": "2026-10-26T12:30:00.000Z"
}
```

### 4.2. Отсутствующее поле и `null`

Эти состояния имеют разные значения.

В PATCH-запросе:

- поле отсутствует — значение не изменяется;
- поле передано с `null` — очистка значения, если она разрешена контрактом;
- поле передано со значением — значение изменяется после валидации.

Если поле нельзя очищать, `null` должен отклоняться.

### 4.3. Внутренние сущности и API DTO

API не должен возвращать модели Prisma напрямую.

Вместо этого используются явные DTO ответов, например:

```ts
export interface DocumentResponse {
  id: string;
  workspaceId: string;
  title: string;
  status:
    | "uploaded"
    | "processing"
    | "ready"
    | "processing_failed"
    | "archived"
    | "deletion_pending"
    | "deleted";
  createdAt: string;
  updatedAt: string;
}
```

Пример приведён для иллюстрации структуры. Фактические статусы должны совпадать с утверждённой моделью данных.

## 5. Единый формат ошибок

### 5.1. Контракт

Предлагаемый формат:

```ts
export interface ApiErrorResponse {
  error: {
    code: string;
    message: string;
    requestId: string;
    details?: Array<{
      field?: string;
      code: string;
      message: string;
    }>;
  };
}
```

Пример ответа:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed",
    "requestId": "2b43e2f4-3e7c-4c8a-aab2-9f8cbe6a5a11",
    "details": [
      {
        "field": "title",
        "code": "REQUIRED",
        "message": "This field is required"
      }
    ]
  }
}
```

Тексты сообщений предназначены для диагностики. Пользовательский интерфейс может отображать локализованный текст на русском языке на основании стабильного `code`.

### 5.2. Правила

1. `code` является стабильным машинно-читаемым идентификатором.
2. `message` не содержит stack trace, SQL, секреты или конфиденциальные данные.
3. `requestId` связывает ответ с техническим событием.
4. `details` не должен возвращать содержимое защищённых ресурсов.
5. Клиент не должен определять логику только по тексту `message`.
6. Неожиданные ошибки преобразуются в безопасный `500`.
7. Детали внутренней ошибки сохраняются в защищённой системе мониторинга с учётом политики логирования.

### 5.3. Предлагаемые коды

| Код | Значение |
|---|---|
| `VALIDATION_ERROR` | Ошибка валидации |
| `UNAUTHENTICATED` | Требуется вход |
| `FORBIDDEN` | Операция запрещена |
| `NOT_FOUND` | Ресурс не найден или недоступен |
| `CONFLICT` | Конфликт состояния |
| `RATE_LIMITED` | Превышен лимит |
| `QUOTA_EXCEEDED` | Превышена квота |
| `PAYLOAD_TOO_LARGE` | Слишком большой запрос |
| `UNSUPPORTED_MEDIA_TYPE` | Неподдерживаемый формат |
| `AI_PROVIDER_UNAVAILABLE` | Провайдер недоступен |
| `AI_PROVIDER_TIMEOUT` | Истёк таймаут провайдера |
| `AI_OUTPUT_INVALID` | Результат AI не прошёл валидацию |
| `AI_TASK_NOT_CANCELLABLE` | Задачу нельзя отменить в текущем состоянии |
| `RESOURCE_STATE_INVALID` | Операция недопустима в текущем состоянии |
| `INTERNAL_ERROR` | Неожиданная ошибка |

Необходимо документировать коды, которые используются каждым endpoint'ом. Не все коды применимы ко всем операциям.

## 6. Валидация запросов

### 6.1. Общий принцип

Валидация выполняется на backend до передачи данных в бизнес-логику.

Frontend может проверять поля для удобства пользователя, но frontend-валидация не заменяет backend-валидацию.

### 6.2. DTO в NestJS

Рекомендуется применять DTO и единый механизм валидации на уровне NestJS.

Пример:

```ts
export class CreateWorkspaceDto {
  @IsString()
  @MinLength(1)
  @MaxLength(120)
  name!: string;

  @IsOptional()
  @IsString()
  @MaxLength(2000)
  description?: string;
}
```

Конкретный набор библиотек и правила валидации необходимо зафиксировать в backend-стандартах.

### 6.3. Глобальная политика

Предлагается:
- отклонять неизвестные поля;
- проверять типы;
- ограничивать длину строк;
- ограничивать размеры массивов;
- проверять UUID;
- валидировать даты и числовые диапазоны;
- нормализовать ошибки в единый формат;
- не выполнять преобразования типов, способные скрыть некорректный ввод.

Для NestJS это можно реализовать через глобальный `ValidationPipe` с настройками `whitelist`, `forbidNonWhitelisted` и `transform`, дополнительно проверив поведение преобразования типов.

### 6.4. Валидация по контексту

Одной проверки типа недостаточно.

Например, корректный UUID может обозначать:
- ресурс другого пользователя;
- документ другой организации;
- удалённый документ;
- ресурс, который нельзя изменять в текущем состоянии.

После структурной валидации выполняются проверки прав и бизнес-правил.

### 6.5. Валидация AI-ответов

AI-ответы считаются внешним недоверенным вводом.

Они проходят:
1. проверку наличия результата;
2. проверку допустимого формата;
3. структурную runtime-валидацию;
4. проверку ссылок на источники;
5. проверку бизнес-ограничений.

Нельзя использовать невалидированный ответ модели для изменения прав, удаления ресурсов или других критичных операций.

## 7. Аутентификация и авторизация

### 7.1. Аутентификация

Каждый защищённый endpoint должен иметь определённое требование к аутентификации.

Публичные endpoint'ы должны быть явно обозначены и иметь ограничения по частоте запросов.

Не следует полагаться на то, что пользователь пришёл из защищённой страницы frontend.

### 7.2. Авторизация

Перед операцией с ресурсом backend проверяет:

1. Кто инициирует запрос.
2. Действительна ли сессия.
3. Состоит ли пользователь в организации.
4. Доступно ли ему рабочее пространство.
5. Имеет ли он право на конкретное действие.
6. Не отозван ли доступ.
7. Допустима ли операция в текущем состоянии ресурса.

Проверка должна быть централизованной или реализованной через единый механизм политик.

### 7.3. Организация

Если endpoint работает в контексте организации, организация должна определяться из проверенного контекста членства.

Нельзя принимать `organizationId` из запроса как достаточное доказательство права доступа.

Если клиент передаёт идентификатор организации для переключения текущего контекста, backend всё равно проверяет активное членство и необходимые полномочия.

### 7.4. Ошибки доступа

Для закрытых ресурсов допускается отвечать `404`, чтобы не подтверждать их существование постороннему пользователю.

Выбранная политика должна быть единообразной и не раскрывать через сообщения об ошибках существование чужих документов, чатов или рабочих пространств.

### 7.5. Административный доступ

Endpoint'ы административного управления организацией не должны автоматически разрешать чтение содержимого документов или чатов.

Правила временного доступа должны соответствовать `docs/07-access-control-matrix.md` и `docs/09-threat-model.md`.

## 8. Пагинация и фильтрация

### 8.1. Пагинация

Для небольших списков можно использовать offset pagination.

Пример:

```text
GET /api/v1/documents?limit=20&offset=0
```

Предлагаемые ограничения:
- `limit` по умолчанию — 20;
- максимальный `limit` — 100;
- `offset` не может быть отрицательным.

Числа являются предварительными и должны быть проверены нагрузочными тестами.

Для больших изменяющихся списков предпочтительна cursor pagination.

### 8.2. Ответ списка

Предлагаемый формат:

```ts
export interface PaginatedResponse<T> {
  items: T[];
  page: {
    limit: number;
    nextCursor?: string;
    hasMore: boolean;
  };
}
```

Этот формат предполагает cursor pagination. Если для endpoint используется offset pagination, его контракт должен явно отражать соответствующие поля. Не нужно смешивать обе модели в одном endpoint без необходимости.

### 8.3. Фильтрация

Пример:

```text
GET /api/v1/documents?status=ready&workspaceId={workspaceId}
```

Все фильтры должны:
- проходить валидацию;
- иметь документированные допустимые значения;
- учитываться в проверках доступа;
- не позволять расширить область видимости данных.

Переданный `workspaceId` не предоставляет право читать рабочее пространство.

### 8.4. Сортировка

Пользователь может выбирать сортировку только по явно разрешённым полям.

Нельзя напрямую подставлять произвольное значение query-параметра в SQL или ORM-сортировку без проверки допустимого списка.

Для стабильной пагинации порядок сортировки должен иметь однозначное разрешение совпадающих значений, например дополнительную сортировку по ID.

## 9. Создание и изменение ресурсов

### 9.1. Создание

При создании backend сам определяет:
- владельца;
- организацию;
- системные статусы;
- даты создания;
- технические идентификаторы.

Клиент не должен самостоятельно задавать защищённые системные поля.

### 9.2. Обновление

PATCH изменяет только разрешённые поля.

Backend обязан проверять:
- право изменять ресурс;
- допустимость изменения каждого поля;
- текущий статус;
- конфликты параллельного изменения, если для ресурса предусмотрена защита от гонок.

### 9.3. Удаление

Удаление может быть логическим или физическим в зависимости от модели жизненного цикла.

API должен явно описывать:
- какой статус получает ресурс;
- когда исчезает пользовательский доступ;
- что происходит с производными данными;
- выполняется ли удаление асинхронно;
- как получить статус операции.

Удаление не должно считаться завершённым только потому, что запись скрыта в интерфейсе.

### 9.4. Конкурентное изменение

Для критичных операций рекомендуется использовать версию ресурса, `updatedAt` или иной механизм optimistic concurrency.

Если ресурс изменился после того, как клиент его прочитал, backend может вернуть `409 Conflict`.

Конкретный механизм выбирается отдельно для документов, настроек и административных разрешений.

## 10. Идемпотентность

### 10.1. Где нужна

Идемпотентность особенно важна для:
- создания AI-задач;
- оплаты или списания квот, если появится платный функционал;
- загрузки файлов;
- запуска исследования;
- запуска пакетной обработки;
- административных операций, которые не должны выполняться дважды.

### 10.2. Ключ идемпотентности

Для поддерживаемых операций можно использовать заголовок:

```text
Idempotency-Key: <unique-client-generated-value>
```

Backend должен определить:
- срок хранения ключа;
- область уникальности;
- поведение при повторе с тем же телом;
- поведение при повторе с другим телом;
- связь с исходным результатом.

Повтор с тем же ключом и теми же параметрами должен возвращать согласованный результат либо статус исходной операции.

Повтор с тем же ключом, но другим содержимым должен приводить к конфликту.

Идемпотентность создания внутренней задачи не гарантирует, что внешний AI-провайдер выполнит запрос только один раз. Это зависит от возможностей его API.

## 11. Долгие операции и AI-задачи

### 11.1. Когда использовать асинхронный режим

Асинхронный API следует использовать для операций, которые:
- могут выполняться долго;
- требуют нескольких вызовов модели;
- обрабатывают много документов;
- включают исследование с большим количеством источников;
- должны продолжаться после закрытия страницы;
- требуют повторных попыток и мониторинга.

### 11.2. Создание задачи

Пример:

```http
POST /api/v1/ai-jobs
Content-Type: application/json
```

```json
{
  "type": "document_analysis",
  "workspaceId": "d2c7b09b-c770-4e36-8d4c-bf3d78dd97a5",
  "input": {
    "documentIds": [
      "90e5dbe8-a84a-4418-a77a-1095a69a22bd"
    ],
    "instruction": "Выдели основные риски договора"
  }
}
```

Идентификаторы приведены как примеры формата. В production клиент не может заставить backend использовать документ без проверки прав.

При успешном принятии задачи backend возвращает `202 Accepted` с идентификатором задачи.

### 11.3. Получение статуса

```text
GET /api/v1/ai-jobs/{jobId}
```

Пример:

```json
{
  "id": "f7b94b2e-9b2e-4a7e-91be-5a0f3b2a7f10",
  "status": "running",
  "progress": {
    "completed": 1,
    "total": 3
  },
  "createdAt": "2026-10-26T12:30:00.000Z"
}
```

Поле `progress` необязательно. Его смысл зависит от типа задачи; нельзя выдавать приблизительный прогресс за точное измерение, если этапы нельзя надёжно посчитать.

### 11.4. Получение результата

```text
GET /api/v1/ai-jobs/{jobId}/result
```

Backend обязан повторно проверить актуальные права пользователя. Сам факт создания задачи этим пользователем не гарантирует вечного доступа к её результату.

### 11.5. Отмена задачи

```text
POST /api/v1/ai-jobs/{jobId}/cancel
```

Отмена должна учитывать текущее состояние задачи.

Если запрос уже отправлен внешней модели, backend может не иметь возможности остановить обработку у провайдера. В таком случае система должна отдельно определить, прекращает ли она внутреннюю обработку и выдачу результата.

### 11.6. Статусы задачи

**CONFIRMED (D-011).** Статусы AIJob в API — только:

- `queued`;
- `running`;
- `succeeded`;
- `failed`;
- `cancelled`;
- `timed_out`.

Не использовать `completed` или `retry_wait` как значение `status`. Поле `progress.completed` (счётчик этапов), если есть, — не статус job. Успех — `succeeded`. Ретраи — поля задачи / попыток, не отдельный статус.

Необходимо определить допустимые переходы и исключить произвольное изменение статуса клиентом.

## 12. Streaming API

Если для чата выбран SSE, предлагается endpoint:

```text
POST /api/v1/ai/chat/stream
```

Перед началом потока backend:
1. проверяет сессию;
2. проверяет доступ к чату и документам;
3. валидирует запрос;
4. применяет лимиты;
5. создаёт или определяет задачу;
6. начинает поток.

События должны иметь документированный формат. Например:

```text
event: text_delta
data: {"text":"Основной риск договора..."}

event: message_complete
data: {"taskId":"f7b94b2e-9b2e-4a7e-91be-5a0f3b2a7f10"}
```

Формат является предварительным.

Требования:
- поток не передаёт секреты;
- закрытие соединения обрабатывается предсказуемо;
- ошибки имеют безопасный код;
- повторное подключение не запускает незаметно новую генерацию;
- правила восстановления потока определены явно;
- прокси и сервер имеют подходящие таймауты;
- авторизация проверяется до выдачи защищённого результата.

Если клиент должен возобновлять поток, необходимо определить, сохраняются ли события и как используется `Last-Event-ID`. Не следует обещать восстановление потока, если сервер не хранит историю событий.

## 13. Загрузка файлов

### 13.1. Endpoint

Предлагаемый вариант:

```text
POST /api/v1/documents
Content-Type: multipart/form-data
```

### 13.2. Требования

Backend проверяет:
- аутентификацию;
- доступ к рабочему пространству;
- размер;
- допустимые форматы;
- фактический тип содержимого;
- лимиты пользователя и организации;
- состояние обработки.

Файл нельзя делать доступным по публичной постоянной ссылке без отдельного решения.

### 13.3. Асинхронная обработка

После загрузки документ может перейти в состояние `processing`.

API должен позволять получить актуальный статус. Ошибка OCR или парсера не должна превращаться в успешный статус документа.

### 13.4. Скачивание

Скачивание выполняется через защищённый endpoint или временную ссылку с ограниченным сроком действия.

Если используется подписанная ссылка, необходимо определить:
- срок жизни;
- возможность повторного использования;
- привязку к конкретному объекту;
- поведение после отзыва доступа;
- способ защиты от утечки ссылки.

## 14. Ограничение частоты и квоты

Rate limiting и квоты — разные механизмы.

**Rate limiting** ограничивает частоту запросов за период времени.

**Квота** ограничивает общий объём использования ресурса, например AI-расходы за месяц.

Нужно определить отдельные лимиты для:
- аутентификации и восстановления;
- загрузки файлов;
- поиска;
- создания AI-задач;
- генерации;
- экспорта;
- административных операций.

При превышении лимита возвращается `429 Too Many Requests` с безопасным кодом и, когда это возможно, информацией о времени повторной попытки.

Нельзя использовать только IP-адрес как единственный способ ограничения. Для аутентифицированных операций учитываются пользователь, организация и характер операции.

## 15. Безопасность API

### 15.1. Обязательные требования

- Все защищённые ресурсы проверяются на backend.
- Входные данные валидируются.
- Неизвестные поля отклоняются согласно выбранной политике.
- Защищённые ответы не кэшируются публично.
- Секреты не передаются в URL.
- Изменяющие состояние операции защищаются от CSRF, если используется cookie-аутентификация.
- Чувствительные операции ограничиваются по частоте.
- Ошибки не раскрывают внутренние детали.
- Файловые endpoint'ы имеют отдельные ограничения.
- Ссылки на скачивание не заменяют проверку доступа, если политика требует повторной авторизации.
- CORS настраивается по разрешённым origin, а не разрешает произвольные источники без обоснования.

### 15.2. Защита от IDOR

Для каждого endpoint'а с ID ресурса нужно проверить, может ли пользователь заменить ID и получить чужие данные.

Это относится не только к `GET`, но и к:
- `PATCH`;
- `DELETE`;
- запуску задач;
- получению результатов;
- скачиванию;
- отмене задач;
- административным операциям.

### 15.3. Request ID

Каждый запрос должен иметь идентификатор для диагностики.

Если клиент передаёт собственный request ID, backend должен проверить формат и не допустить его использования для внедрения управляющих символов или подделки журналов. Альтернативно backend генерирует собственный ID и сохраняет входной ID отдельно, если он нужен.

## 16. Версионирование и обратная совместимость

### 16.1. Правила

- Несовместимые изменения публичного контракта требуют новой версии API или согласованной миграции.
- Добавление необязательного поля обычно совместимо, но клиенты должны корректно обрабатывать неизвестные поля ответа.
- Удаление поля, изменение его типа или изменение смысла существующего статуса требует отдельного плана миграции.
- Ошибки и коды состояний являются частью API-контракта.

### 16.2. Депрекация

Если endpoint устаревает:
1. документируется замена;
2. фиксируется срок поддержки;
3. при необходимости добавляется предупреждение;
4. миграция проверяется на frontend;
5. удаление выполняется после согласованного периода.

Для раннего MVP не требуется сложная система поддержки нескольких версий одновременно, но обратную совместимость необходимо учитывать.

## 17. OpenAPI и документация

Рекомендуется поддерживать OpenAPI-спецификацию, генерируемую или проверяемую на основании backend-контрактов.

Для каждого endpoint'а описываются:
- метод и путь;
- аутентификация;
- необходимые разрешения;
- параметры пути;
- query-параметры;
- тело запроса;
- схема успешного ответа;
- возможные ошибки;
- ограничения размера и частоты;
- особенности асинхронной работы;
- правила доступа к результату.

Документация не должна расходиться с реальным поведением API.

В CI рекомендуется проверять, что изменения контрактов не создают незапланированных несовместимостей.

## 18. Тестирование

### 18.1. Unit-тесты

Проверяют:
- валидацию DTO;
- преобразование ошибок;
- бизнес-правила;
- формирование ответов;
- допустимые переходы статусов.

### 18.2. Интеграционные тесты

Проверяют:
- работу API с базой данных;
- ограничения целостности;
- создание и изменение ресурсов;
- транзакции;
- обработку конфликтов;
- работу очередей и задач.

### 18.3. Тесты авторизации

Для каждого защищённого endpoint'а необходимо проверить:
- неаутентифицированного пользователя;
- пользователя без членства в организации;
- участника без права на действие;
- пользователя другой организации;
- пользователя с отозванным доступом;
- удалённый или недоступный ресурс;
- повторный запрос после изменения прав.

### 18.4. Контрактные тесты

Проверяют:
- формат успешного ответа;
- формат ошибки;
- корректность статусов;
- схему DTO;
- отсутствие неожиданных полей;
- соответствие OpenAPI.

### 18.5. Критерий приёмки

Ни один endpoint не считается готовым только потому, что успешный сценарий работает из браузера. Должны быть проверены ошибочные запросы, права доступа и обработка некорректного состояния.

## 19. Стандарт разработки нового endpoint'а

Для каждого нового endpoint'а разработчик должен:

1. Определить ресурс и бизнес-операцию.
2. Указать HTTP-метод и путь.
3. Определить DTO запроса и ответа.
4. Описать ошибки и HTTP-статусы.
5. Определить требования к аутентификации.
6. Определить права доступа к каждому ресурсу.
7. Добавить валидацию.
8. Реализовать бизнес-логику вне контроллера.
9. Добавить защиту от дублирования, если операция может повторяться.
10. Добавить unit- и интеграционные тесты.
11. Проверить сценарии доступа к чужим ресурсам.
12. Обновить OpenAPI.
13. Проверить отсутствие конфиденциальных данных в логах.
14. Описать особенности пагинации, загрузки или фонового выполнения, если они применимы.

## 20. Критерии приёмки документа

- [ ] Все новые endpoint'ы находятся под согласованным API-префиксом.
- [ ] Форматы JSON и ошибок единообразны.
- [ ] Все входные данные валидируются на backend.
- [ ] Все защищённые операции проверяют актуальные права.
- [ ] Пагинация и сортировка ограничены и документированы.
- [ ] Для повторяемых операций определена идемпотентность.
- [ ] Долгие AI-задачи имеют явные статусы.
- [ ] Результаты AI-задач повторно проверяются на доступ.
- [ ] Загрузка и скачивание файлов имеют отдельные политики.
- [ ] Rate limiting и квоты определены для чувствительных операций.
- [ ] OpenAPI соответствует реальному контракту.
- [ ] Есть автоматические тесты авторизации и обработки ошибок.

## 22. Итог

Все модули платформы должны использовать единые правила API:

1. REST с согласованным префиксом.
2. Явные DTO запросов и ответов.
3. Runtime-валидация на backend.
4. Единый формат ошибок.
5. Проверка прав на каждый ресурс и действие.
6. Предсказуемая пагинация.
7. Контролируемая идемпотентность.
8. Отдельный контракт долгих AI-задач.
9. Защищённая работа с файлами и streaming.
10. OpenAPI и автоматические тесты как часть разработки.

Основной принцип: **endpoint должен быть безопасным и предсказуемым независимо от того, вызывает его frontend, другой внутренний модуль или пользователь вручную через HTTP-клиент.**

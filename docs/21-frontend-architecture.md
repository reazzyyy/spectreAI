# Frontend Architecture

**Файл:** `docs/21-frontend-architecture.md`  
**Статус:** **FSD CONFIRMED (D-023)**; Next.js **CONFIRMED (D-008)**; прочие детали UI/библиотек — Proposed / OPEN (FE-002+)  
**Проект:** AI-платформа для юридических команд  
**Основной стек:** Next.js App Router, React, TypeScript (**D-008**); организация кода — Feature-Sliced Design (**D-023**, ADR-0002)

---

## 1. Цель документа

Определить архитектуру frontend-приложения, правила организации кода и взаимодействия с backend.

Frontend должен поддерживать:

- AI-чат с потоковой генерацией ответов.
- Загрузку, просмотр и анализ юридических документов.
- Подготовку и редактирование юридических текстов.
- Юридические исследования и работу с источниками.
- Рабочие пространства организаций и команд.
- Разграничение доступа к документам, чатам и результатам AI.
- Обработку длительных фоновых задач.
- Корректное отображение ошибок, загрузки и промежуточных состояний.

Основная цель архитектуры — сделать проект понятным для разработчиков и AI-агентов, чтобы изменения в одной функции не приводили к непредсказуемым изменениям во всём приложении.

## 2. Архитектурные принципы

### 2.1. Разделение ответственности (FSD, **D-023**)

Код `apps/web` организуется по **Feature-Sliced Design**. Нормативные слои:

- **`app`** — маршруты Next.js App Router, layouts, композиция страниц, провайдеры.
- **`widgets`** — крупные самостоятельные блоки UI (shell, чат-панель, сайдбар).
- **`features`** — пользовательские действия и сценарии (login, upload, send message).
- **`entities`** — представление бизнес-сущностей и связанный UI/модель отображения.
- **`shared`** — UI-примитивы, API-клиент, утилиты без знания фич продукта.

Не следует помещать всю логику в React-компоненты страниц или создавать параллельную структуру вне FSD (`components/` как свалка, «utils на всё»).

### 2.2. Backend — источник истины

Frontend не определяет самостоятельно:

- Имеет ли пользователь право читать документ.
- Может ли пользователь открыть конкретный чат.
- Разрешено ли администратору организации читать содержимое.
- Может ли AI использовать документ в контексте.
- Завершена ли фоновая задача.
- Допустима ли операция с точки зрения бизнес-правил.

Frontend может скрывать недоступные действия для удобства, но backend обязан повторно проверять все права.

### 2.3. Минимально необходимая сложность

Не добавлять библиотеки и архитектурные абстракции без конкретной необходимости.

Например, не нужно одновременно внедрять несколько глобальных state-менеджеров, несколько API-клиентов или собственный универсальный фреймворк форм.

### 2.4. Постепенное развитие

Сначала реализуется минимальный рабочий сценарий от интерфейса до backend. Затем архитектура расширяется на основе реальных потребностей.

Не следует заранее строить сложную систему плагинов, микрофронтендов или универсальных конструкторов AI-сценариев.

## 3. Стек frontend

| Задача | Решение |
|---|---|
| Framework | Next.js App Router (**CONFIRMED, D-008**) |
| UI | React |
| Язык | TypeScript |
| Валидация данных | Zod для подходящих клиентских сценариев |
| Серверные данные | TanStack Query — если выбран и нужен |
| Локальное состояние | React state и Context по необходимости |
| Формы | React Hook Form + Zod — кандидат для стандартных форм |
| API | Типизированный клиент поверх `fetch` |
| Потоковая генерация | Fetch Streams или SSE в зависимости от backend-контракта |
| Тестирование | Vitest + React Testing Library |
| E2E | Playwright |
| UI-иконки | Lucide React — если выбран дизайн-системой |
| Мониторинг ошибок | Sentry — если выбран для проекта |

Next.js — **подтверждённый** frontend MVP (**D-008**). Остальные строки таблицы — кандидаты; не требование установить все зависимости сразу.

Перед установкой библиотек необходимо проверить существующие зависимости проекта и согласовать их с backend API и текущей версией Next.js.

В режимах synthetic/test (до разрешения передачи реальных данных, **D-012** / **O-002**) UI должен явно показывать, что используется синтетический провайдер / тестовые данные, а не production OpenAI.

## 4. Структура проекта (FSD, **CONFIRMED D-023**)

Нормативная раскладка слоёв в `apps/web/src`. Конкретные слайсы появляются по мере фич; пустые заготовки «на будущее» не обязательны.

### 4.1. Правила импортов (**CONFIRMED**, **D-023**)

Направление зависимостей:

`app → widgets → features → entities → shared`

Не требуется искусственно прогонять каждый импорт через все слои; запрещены импорты «вверх» и циклы.

Правила:

1. `shared` не импортирует код из `entities`, `features`, `widgets` или `app`.
2. `entities` не импортирует `features` и `widgets`.
3. `features` не импортирует `widgets`.
4. `widgets` не импортирует страницы из `app`.
5. Между модулями одного слоя не должно быть скрытых циклических зависимостей.
6. Публичные API модулей экспортируются через `index.ts`, если это помогает контролировать импорты.
7. Не создавать `index.ts` в каждой папке механически, если он не выполняет полезной функции.

Контроль границ в репозитории: **Steiger** (`pnpm --filter @spectre/web lint:fsd`) и ESLint (`lint`) с запретом deep-import слайсов / плоского `@/components`. Правила слоёв — CONFIRMED (**ADR-0002** / **D-023**).

### 4.2. Что должно находиться в слоях

**`shared`**

Общие кнопки, поля ввода, модальные окна, API-клиент, обработчики ошибок, общие типы, форматирование дат и другие независимые утилиты.

**`entities`**

Представление сущностей: документ, сообщение, пользователь, организация, AI-задача. Например, компонент статуса документа или типизированная модель сообщения.

**`features`**

Действия пользователя: отправить сообщение, загрузить документ, создать черновик, отменить задачу, пригласить участника.

**`widgets`**

Крупные самостоятельные блоки интерфейса: боковая панель, чат, просмотрщик документов, панель результатов исследования.

**`app`**

Маршрутизация, layouts, композиция страниц, обработка ошибок маршрута и интеграция с возможностями Next.js.

## 5. Маршрутизация и организация страниц

Предлагаемые основные разделы:

- `/login` — вход.
- `/invite/[token]` — принятие приглашения.
- `/workspace/[workspaceId]` — рабочее пространство.
- `/chat/[conversationId]` — конкретный диалог.
- `/documents` — список документов.
- `/documents/[documentId]` — документ.
- `/research/[researchId]` — исследование.
- `/drafts/[draftId]` — юридический черновик.
- `/settings` — пользовательские настройки.
- `/settings/members` — управление участниками, если разрешено правами.

Окончательная схема URL должна учитывать API и модель данных из backend-документации.

### Правила маршрутов

- Маршруты не должны содержать бизнес-логику, которую можно вынести в feature или отдельный модуль.
- `page.tsx` отвечает преимущественно за композицию страницы и получение необходимых данных.
- `layout.tsx` используется для общего интерфейса раздела.
- Доступ к защищённым данным проверяется на сервере, а backend проверяет его независимо.
- Нельзя считать скрытие ссылки в Sidebar механизмом авторизации.
- При отсутствии доступа показывается согласованное состояние: например, 403 или 404 — в зависимости от принятой политики раскрытия существования ресурса.

## 6. Server Components и Client Components

В Next.js App Router компоненты по умолчанию остаются Server Components, пока не требуется клиентская интерактивность.

### Server Components подходят для

- Получения данных при открытии страницы.
- Начального отображения списков документов.
- Формирования каркаса страницы.
- Отображения данных, которые не требуют интерактивного состояния браузера.

### Client Components нужны для

- Форм ввода и интерактивных контролов.
- AI-чата и потокового вывода.
- Редактирования текста.
- Drag-and-drop и загрузки файлов.
- Управления состоянием интерфейса.
- Клиентских подписок и polling.
- Интерактивного просмотра документов.

### Правила

1. Не добавлять `'use client'` в корневой layout только ради одного интерактивного компонента.
2. Держать клиентские границы как можно уже.
3. Не передавать в клиентские компоненты секреты и серверные конфигурации.
4. Не считать данные, полученные в Server Component, автоматически актуальными после пользовательских мутаций.
5. После изменения данных явно обновлять нужный кэш или повторно запрашивать данные.
6. Не использовать Server Actions как обходной путь для авторизации backend API.
7. Не обращаться к базе данных напрямую из клиентских компонентов.

Если frontend и NestJS работают под одним доменом, рекомендуемый вариант — единая точка входа с маршрутизацией `/api/v1` на backend. Конкретный способ серверного проксирования необходимо согласовать с инфраструктурой.

## 7. API-клиент

Все HTTP-запросы должны проходить через согласованный API-слой, а не реализовываться независимо в каждом компоненте.

Пример структуры:

```text
shared/api/
├── client.ts
├── errors.ts
├── types.ts
└── endpoints/
```

### 7.1. Ответственность API-клиента

- Формировать URL и параметры запросов.
- Передавать необходимые заголовки.
- Поддерживать авторизационные cookie в соответствии с выбранной схемой.
- Обрабатывать сетевые ошибки.
- Нормализовать ошибки backend.
- Проверять HTTP-статусы.
- Поддерживать `AbortSignal` для отмены запросов.
- Не выводить содержимое конфиденциальных документов в технические логи.

API-клиент не должен автоматически повторять любой запрос после ошибки. Повторы допустимы только для подходящих операций с учётом их идемпотентности.

### 7.2. Типизация

- Не использовать `any` для обхода типизации.
- Не считать `response.json()` безопасно типизированным автоматически.
- Проверять данные на границах системы, если от этого зависит корректность работы.
- Использовать DTO и OpenAPI-контракт backend как источник API-типов.
- Не дублировать вручную одни и те же API-типы в нескольких местах.
- Не импортировать Prisma-типы backend непосредственно во frontend.

Пример базовой функции:

```ts
export async function apiRequest<T>(
  path: string,
  init: RequestInit = {},
): Promise<T> {
  const response = await fetch(`/api/v1${path}`, {
    ...init,
    credentials: "same-origin",
    headers: {
      ...init.headers,
    },
  });

  if (!response.ok) {
    throw await parseApiError(response);
  }

  return response.json() as Promise<T>;
}
```

Это только иллюстрация. В production-реализации нужно отдельно учесть `204 No Content`, ошибки без JSON, CSRF-защиту, заголовки корреляции и проверку ответа. Не следует копировать пример как готовый универсальный клиент.

## 8. Работа с серверными данными

Нужно различать три вида состояния:

1. **Серверные данные** — документы, чаты, участники, AI-задачи.
2. **Локальное состояние интерфейса** — открытая панель, выбранная вкладка, видимость модального окна.
3. **Временное состояние ввода** — текст, который пользователь ещё не отправил.

Серверные данные могут управляться обычным `fetch` и механизмами Next.js. Если приложению требуются кэширование, повторные запросы, синхронизация и polling, можно использовать TanStack Query.

Не нужно дублировать один и тот же серверный список в нескольких независимых хранилищах.

### Правила кэширования

- Кэшировать только те данные, для которых определены правила актуальности.
- Не использовать общий кэш для содержимого разных организаций без надёжного разделения ключей и контекста.
- Учитывать смену пользователя, организации и рабочего пространства.
- После изменения или удаления документа инвалидировать связанные данные.
- Не сохранять конфиденциальные документы в `localStorage` или `sessionStorage` по умолчанию.
- Не использовать общий CDN-кэш для приватных API-ответов.
- Не показывать устаревшие данные после отзыва доступа без предусмотренной политики обновления.

Пример ключа кэша:

```ts
[
  "documents",
  organizationId,
  workspaceId,
  filters,
]
```

Ключи должны включать все параметры, влияющие на результат. Но само наличие `organizationId` в ключе не заменяет проверку доступа на backend.

## 9. AI-чат и потоковая генерация

AI-чат — одна из наиболее сложных frontend-функций. Его необходимо проектировать отдельно от обычной формы отправки сообщения.

### 9.1. Состояния интерфейса

Состояния **UI-локальные**; статусы AIJob на API — только **D-011** (`queued`, `running`, `succeeded`, `failed`, `cancelled`, `timed_out`):

- `idle` — ожидание ввода.
- `submitting` — сообщение отправляется.
- `queued` — задача принята и ожидает выполнения (AIJob `queued`).
- `streaming` — ответ поступает частями (при потоке; AIJob обычно `running`).
- `completed` — UI: генерация завершена; маппинг с AIJob **`succeeded`** (не путать с устаревшим статусом job `completed`).
- `failed` — произошла ошибка (AIJob `failed` / `timed_out` по контракту).
- `cancelling` — выполняется отмена.
- `cancelled` — задача отменена (AIJob `cancelled`).

Не вводить UI-статус `retry_wait` как статус AIJob; задержку повтора показывать по полям ретрая. В synthetic-режиме отображать метку синтетического провайдера (**D-012**).

### 9.2. Поток работы

1. Пользователь вводит сообщение.
2. Frontend проверяет допустимость ввода.
3. Создаётся пользовательское сообщение или AI-задача согласно API-контракту.
4. Backend подтверждает принятие задачи.
5. Frontend получает промежуточные события или опрашивает состояние задачи.
6. Текст и ссылки на источники отображаются по мере поступления.
7. После завершения frontend обновляет состояние диалога.
8. При ошибке пользователь видит понятное сообщение и допустимый вариант повторения.

### 9.3. Потоковый транспорт

Вариант транспорта зависит от backend:

- **Fetch Streams** — когда нужен потоковый POST-запрос и удобная передача тела запроса.
- **SSE** — когда используется отдельный канал серверных событий.
- **Polling** — более простой запасной вариант для длительных задач.

Нельзя заранее считать, что SSE обязательно нужен для всех задач. Контракт должен определить формат событий, завершение потока, обработку переподключений и отмену.

### 9.4. Обработка потока

- Не предполагать, что один сетевой пакет соответствует одному полному сообщению.
- Корректно собирать частично поступающие данные.
- Обрабатывать завершение соединения и некорректный формат событий.
- Не создавать дубликаты сообщений при переподключении.
- Не считать закрытие браузерного соединения подтверждением отмены AI-задачи.
- Для отмены использовать отдельную backend-операцию, если она предусмотрена контрактом.
- Поддерживать состояние незавершённой задачи после перехода на другую страницу, если это соответствует UX.
- Не запускать повторную генерацию автоматически без проверки, не была ли исходная задача уже выполнена.

### 9.5. Отображение источников

Ссылки на нормативные акты и другие источники должны отображаться как структурированные данные, а не извлекаться регулярными выражениями из произвольного текста ответа.

Для каждой ссылки, если данные доступны, отображать название источника, реквизиты, дату или редакцию и ссылку на подтверждающий материал.

Frontend не должен самостоятельно придумывать отсутствующие реквизиты или считать ссылку достоверной только потому, что модель включила её в текст.

## 10. Работа с документами

Frontend должен поддерживать:

- Выбор файла.
- Проверку формата и размера до отправки.
- Отображение прогресса загрузки, если его позволяет транспорт.
- Отображение состояния обработки.
- Просмотр доступного результата извлечения текста.
- Запуск анализа документа.
- Просмотр связанных источников и результатов.
- Обновление и удаление документа в рамках разрешений.

### Важные ограничения

Клиентская проверка формата и размера нужна для удобства, но backend обязан повторить все критические проверки.

Не загружать большие файлы в память целиком без необходимости. При загрузке и обработке учитывать ограничения браузера, сети и сервера.

Документ, который ещё обрабатывается, не должен выглядеть как полностью готовый к анализу. Ошибки OCR и извлечения текста нужно показывать отдельно от ошибок AI-генерации.

При замене версии документа frontend должен обновлять связанные данные, не оставляя пользователю результаты, относящиеся к предыдущей версии, без явного обозначения.

## 11. Формы и пользовательский ввод

Для каждой формы необходимо определить:

- Начальные значения.
- Правила валидации.
- Состояние отправки.
- Поведение при повторном нажатии.
- Отображение серверных ошибок.
- Сохранение введённых данных при допустимых временных ошибках.
- Поведение после успешного сохранения.

Предлагается использовать React Hook Form и Zod для сложных или повторяющихся форм. Для небольших форм достаточно стандартного React state, если это не приводит к дублированию логики.

Правила:

1. Валидация frontend улучшает UX, но не заменяет backend-валидацию.
2. Не очищать форму при временной сетевой ошибке без необходимости.
3. Блокировать повторную отправку, когда она может создать дубликат.
4. Для важных изменений показывать явный результат операции.
5. Не помещать секреты или чувствительные данные в URL.
6. Не считать скрытое поле подтверждением полномочий пользователя.

## 12. Ошибки и состояния загрузки

Каждый экран, работающий с серверными данными, должен иметь понятные состояния:

- Начальная загрузка.
- Пустой результат.
- Успешно загруженные данные.
- Ошибка загрузки.
- Отсутствие доступа.
- Ресурс не найден.
- Повторная загрузка или обновление.
- Устаревшие данные, если это существенно для сценария.

Не следует показывать бесконечный спиннер, если backend вернул ошибку или задача перешла в конечное состояние.

### Категории ошибок

| Категория | Поведение интерфейса |
|---|---|
| Сетевая ошибка | Сообщение о проблеме соединения и возможность повторить запрос |
| Ошибка валидации | Показать ошибки рядом с соответствующими полями |
| 401 | Запустить предусмотренный сценарий восстановления сессии или входа |
| 403 | Сообщить об отсутствии доступа |
| 404 | Показать состояние отсутствующего ресурса |
| 409 | Объяснить конфликт состояния и предложить обновить данные |
| 429 | Сообщить об ограничении частоты запросов и учесть `Retry-After`, если он передан |
| 5xx | Показать нейтральную ошибку сервера и доступный вариант восстановления |
| Ошибка AI-задачи | Показать состояние задачи, если оно известно, и безопасный вариант повторного запуска |

Не показывать пользователю необработанный stack trace, внутренние сообщения инфраструктуры или секреты.

## 13. Доступ и конфиденциальность

Юридические документы и переписка могут содержать коммерческую тайну, персональные данные и сведения о делах клиентов.

Обязательные правила frontend:

- Не использовать клиентское состояние как доказательство наличия прав.
- Не помещать содержимое документов и сообщений в URL.
- Не отправлять конфиденциальный текст в сторонние аналитические сервисы.
- Не включать содержимое документов в сообщения об ошибках и диагностические логи.
- Не хранить содержимое документов в браузерном постоянном хранилище без отдельного обоснования и утверждённой политики.
- Не отображать содержимое документа только потому, что его идентификатор известен.
- При отзыве доступа обновлять интерфейс и прекращать дальнейшие запросы к закрытому ресурсу.
- Учитывать, что уже полученные данные невозможно гарантированно стереть из памяти браузера пользователя.

Политика доступа администратора организации остаётся неизменной: административные полномочия сами по себе не дают права читать содержимое чатов и документов. Если предусмотрен процесс временного доступа по запросу и одобрению, frontend должен отображать его состояние и границы доступа, но решение принимает backend.

## 14. UI-компоненты и дизайн-система

Предлагается единый набор базовых компонентов:

```text
shared/ui/
├── button/
├── input/
├── textarea/
├── select/
├── dialog/
├── dropdown/
├── tooltip/
├── badge/
├── skeleton/
├── alert/
├── spinner/
└── empty-state/
```

Не нужно создавать собственные варианты компонента для каждого экрана. Если два компонента имеют одинаковую семантику и поведение, следует рассмотреть их объединение.

При этом не стоит превращать один универсальный компонент в систему десятков флагов и условных веток. Специализированный компонент оправдан, если у него отдельная ответственность.

### Требования к интерфейсу

- Единые отступы, типографика, цвета и радиусы.
- Понятная визуальная иерархия.
- Поддержка клавиатурной навигации.
- Видимые состояния фокуса.
- Достаточный контраст.
- Корректная работа с длинными юридическими текстами.
- Удобное копирование текста и реквизитов.
- Адаптивность для поддерживаемых размеров экрана.
- Отсутствие горизонтального переполнения при отображении длинных документов и таблиц.

Дизайн-система должна помогать работать с большим объёмом текста и сложными юридическими сценариями, а не мешать им декоративными элементами.

## 15. Тестирование

### Unit-тесты

Проверять:

- API-клиент и преобразование ошибок.
- Форматирование и обработку данных.
- Логику отображения состояний AI-задачи.
- Обработку потоковых событий.
- Клиентскую валидацию.
- Поведение отдельных feature-компонентов.

### Integration-тесты

Проверять:

- Отправку сообщения и получение результата.
- Загрузку документа и обновление статуса.
- Обработку серверных ошибок.
- Отмену AI-задачи.
- Обновление данных после мутаций.
- Поведение при смене рабочего пространства.

### E2E-тесты

Минимальный набор сценариев:

1. Пользователь входит в систему.
2. Открывает разрешённое рабочее пространство.
3. Создаёт чат и отправляет сообщение.
4. Видит результат AI-генерации.
5. Загружает документ и дожидается завершения обработки.
6. Запускает анализ документа.
7. Получает ошибку при попытке открыть ресурс без прав.
8. Не получает доступ к содержимому после отзыва полномочий.
9. Видит корректное состояние при ошибке фоновой задачи.
10. Выходит из системы, после чего защищённые экраны становятся недоступны.

Frontend-тесты не заменяют проверки авторизации и безопасности backend.

## 16. Производительность

Необходимо:

- Использовать Server Components там, где это уменьшает ненужный клиентский JavaScript.
- Избегать глобальных клиентских провайдеров без необходимости.
- Не загружать тяжёлые редакторы и просмотрщики до того, как они нужны.
- Использовать виртуализацию для действительно больших списков сообщений или документов, если измерения показывают необходимость.
- Не перерисовывать весь чат при поступлении каждого фрагмента потока, если это становится узким местом.
- Ограничивать количество одновременно активных запросов и подписок.
- Проверять производительность на реалистичных объёмах документов и сообщений.

Конкретные бюджеты производительности должны быть определены после появления прототипа и измерений. Не следует заранее объявлять неподтверждённые показатели обязательными.

## 17. Логирование и мониторинг

Frontend может фиксировать:

- Ошибки интерфейса.
- Неудачные сетевые запросы без чувствительного тела запроса.
- Время загрузки ключевых экранов.
- Продолжительность ожидания AI-задачи.
- Ошибки потокового соединения.
- События, необходимые для диагностики UX.

Не отправлять в логи:

- Полные тексты юридических документов.
- Содержимое переписки.
- Тексты запросов к AI без отдельного обоснования и утверждённой политики.
- Токены сессии, приглашений и восстановления.
- Секреты и приватные ключи.

Для корреляции ошибок frontend и backend следует использовать идентификатор запроса, если он поддерживается API.

## 18. Правила работы Cursor и других AI-агентов

Перед изменением кода агент обязан:

1. Прочитать этот документ и связанные требования.
2. Проверить фактическую структуру репозитория.
3. Изучить существующие зависимости и соглашения.
4. Найти уже реализованные компоненты и API-функции.
5. Определить минимальный набор изменяемых файлов.
6. Проверить согласованность с API-контрактом.
7. Не создавать альтернативную архитектуру без необходимости.

Во время реализации агент обязан:

- Не переносить бизнес-логику в UI без причины.
- Не создавать новые библиотеки-обёртки, если достаточно существующих.
- Не добавлять зависимости без объяснения пользы.
- Не обходить TypeScript-ошибки через `any` или отключение проверок.
- Не дублировать API-типы и бизнес-сущности.
- Не изменять backend-контракт самовольно, если он зафиксирован.
- Не добавлять фиктивные ответы AI в production-путь.
- Не считать скрытие кнопок реализацией контроля доступа.

После реализации агент должен сообщить:

- Какие файлы изменены.
- Какую функциональность реализовано.
- Какие тесты выполнены.
- Какие проверки не удалось выполнить.
- Какие предположения или открытые вопросы остались.
- Какие изменения API или backend потребовались.

## 19. Критерии приёмки

Frontend-архитектура считается принятой для MVP, если:

- Маршруты организованы через App Router.
- Код следует FSD (**D-023**): слои и правила импортов §4.1 соблюдены.
- API-запросы используют единый согласованный механизм.
- Серверные данные не дублируются бесконтрольно в нескольких хранилищах.
- Ошибки API обрабатываются единообразно.
- Потоковая генерация не создаёт дубликаты сообщений при повторном подключении.
- Загрузка документов отражает фактическое состояние обработки.
- Смена пользователя и рабочего пространства не раскрывает ранее загруженные данные через кэш.
- Для защищённых операций backend остаётся источником решения об авторизации.
- Критические пользовательские сценарии покрыты автоматическими тестами.
- В логах нет конфиденциального содержимого документов и переписки.

## 21. Рекомендуемый порядок реализации

1. Настроить базовую структуру Next.js, TypeScript и линтинг.
2. Реализовать API-клиент и единый формат обработки ошибок.
3. Реализовать авторизацию и защищённый layout.
4. Создать базовую дизайн-систему.
5. Реализовать рабочее пространство и навигацию.
6. Реализовать список документов и загрузку файлов.
7. Реализовать чат с асинхронными AI-задачами.
8. Добавить потоковый вывод, если он поддерживается backend.
9. Реализовать просмотр результатов анализа и источников.
10. Добавить тесты, мониторинг и проверки доступа.
11. Проверить поведение кэша при смене пользователя, организации и прав.

**Основное правило:** сначала реализовать один полноценный вертикальный сценарий от UI до backend, проверить его и только после этого расширять архитектуру на остальные функции.

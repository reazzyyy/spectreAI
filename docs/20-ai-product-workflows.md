# AI Product Workflows

**Статус:** PROPOSED по UX-деталям; стек и AIJob — по `docs/decisions-log.md` (**D-008**, **D-011**, **D-012**).  
**Версия:** 0.1

## 1. Назначение

Документ описывает основные сквозные пользовательские сценарии MVP AI-платформы для юридических команд.

До разрешения передачи реальных клиентских данных (**O-002**) продуктовые сценарии с моделями выполняются только через `SyntheticAIProvider` (**D-012**); целевой внешний провайдер — OpenAI API (**D-015**).

Документ связывает:

- интерфейс Next.js (**D-008**);
- API на NestJS (**D-008**);
- аутентификацию и права доступа;
- рабочие пространства и переписки;
- обработку документов;
- RAG;
- внешний правовой поиск;
- AI Gateway;
- фоновые задачи;
- хранение результатов;
- аудит и обработку ошибок.

Цель — определить не только отдельные компоненты системы, но и ожидаемое поведение продукта при выполнении реальных юридических задач.

Связанные документы:

- `docs/06-data-model.md`;
- `docs/07-access-control-matrix.md`;
- `docs/08-data-lifecycle-and-deletion.md`;
- `docs/11-api-conventions.md`;
- `docs/12-authentication-and-sessions.md`;
- `docs/13-file-storage-and-document-processing.md`;
- `docs/14-ai-provider-and-model-gateway.md`;
- `docs/15-ai-jobs-and-background-processing.md`;
- `docs/16-prompt-management-and-ai-safety.md`;
- `docs/17-rag-and-knowledge-retrieval.md`;
- `docs/18-legal-research-and-external-sources.md`;
- `docs/19-conversation-and-workspace-context.md`.

Все сценарии и API в документе являются проектными предложениями, пока они не согласованы и не реализованы.

## 2. Область MVP

Для первой версии предлагаются пять основных пользовательских сценариев.

| Сценарий | Пользовательская ценность | Приоритет |
|---|---|---|
| AI-чат | Получение ответов и помощь в повседневных юридических задачах | P0 |
| Анализ документов | Извлечение условий, рисков, обязательств и проблем | P0 |
| Подготовка документов | Создание и редактирование проектов юридических текстов | P0 |
| Юридическое исследование | Поиск правовых норм и судебной практики | P1 |
| Работа с Workspace | Организация переписок, документов и результатов по делу | P0 |

P0 — необходимое ядро продукта. P1 — важная функция, объём которой зависит от готовности и качества подключённых источников.

Для MVP не требуется реализовывать полноценную автоматизированную юридическую фирму, автономное принятие юридических решений или сложные многоэтапные AI-агенты с неограниченным доступом к инструментам.

## 3. Общая архитектура пользовательского запроса

Основной поток:

```text
User Interface
      |
      v
Next.js Application
      |
      v
NestJS API
      |
      v
Authentication and Authorization
      |
      v
Conversation and Workflow Service
      |
      +--> Context Builder
      |
      +--> Document Retrieval
      |
      +--> Legal Research
      |
      +--> AI Gateway
      |
      v
AI Job / Worker when needed
      |
      v
Result Validation
      |
      v
Database and Object Storage
      |
      v
Frontend Result View
```

Не каждый запрос требует всех компонентов. Обычный вопрос может обрабатываться без RAG, а юридическое исследование потребует поиска источников и проверки ссылок.

### 3.1. Общие правила

Для каждого сценария:

1. Сервер проверяет пользователя и права доступа.
2. Определяется тип задачи.
3. Формируется контекст из разрешённых источников.
4. При необходимости создаётся фоновая задача.
5. AI Gateway выполняет запрос к подходящей модели.
6. Результат проходит предусмотренные проверки.
7. Система сохраняет результат и необходимую метаинформацию.
8. Frontend отображает результат и состояние операции.

Модель не должна самостоятельно определять права доступа, выбирать произвольные документы или обходить ограничения продукта.

## 4. Пользовательские сущности

### 4.1. Workspace

Workspace объединяет материалы по задаче, делу или проекту.

Предлагаемые разделы интерфейса:

- Overview;
- Conversations;
- Documents;
- Research;
- Settings — при наличии разрешения.

Необязательно реализовывать все разделы как отдельные страницы. В MVP можно использовать единый экран Workspace с вкладками.

### 4.2. Conversation

Conversation — отдельная переписка.

Она может быть:

- создана из Workspace;
- создана из общего раздела чата;
- привязана к выбранным документам;
- использована для анализа или подготовки текста.

Переписки должны иметь понятные названия. Автоматически созданное название можно предложить после первого сообщения и позволить пользователю изменить его.

### 4.3. Document

Документ представляет загруженный материал с собственным статусом обработки и версионированием.

Пользователь должен различать:

- загрузку файла;
- обработку файла;
- доступность содержимого для поиска;
- ошибку обработки;
- архивирование;
- удаление.

Успешная загрузка не означает, что файл уже обработан и готов для анализа.

### 4.4. AI Job

AI Job — длительная операция, например:

- анализ большого договора;
- обработка файла;
- юридическое исследование;
- подготовка сложного документа.

Пользователь должен видеть состояние операции, а не получать бесконечный индикатор загрузки без объяснения.

## 5. Сценарий A: AI-чат

### 5.1. Цель

Позволить юристу задать вопрос, получить ответ и продолжить обсуждение в одной переписке.

Примеры:

- «Объясни разницу между этими условиями договора».
- «Предложи более точную формулировку».
- «Какие риски есть у этого условия?».
- «Сравни два подхода к решению вопроса».

### 5.2. Пользовательский путь

1. Пользователь открывает Chat.
2. Создаёт новую переписку или открывает существующую.
3. Вводит сообщение.
4. При необходимости выбирает документы.
5. Отправляет запрос.
6. Видит состояние выполнения.
7. Получает ответ.
8. Может продолжить обсуждение, скопировать результат или запросить изменение текста.

### 5.3. Frontend

Frontend отвечает за:

- отображение истории сообщений;
- ввод и отправку сообщения;
- состояние отправки;
- отображение ответа;
- отображение ошибок;
- отмену запроса, если операция поддерживает отмену;
- восстановление состояния при обновлении страницы;
- отображение подключённых документов;
- отображение доступных действий над результатом.

Отправка сообщения должна блокировать случайную повторную отправку, но не мешать продолжить работу после корректного завершения.

### 5.4. Backend

Backend:

1. Проверяет права доступа к Conversation.
2. Валидирует сообщение.
3. Сохраняет сообщение пользователя.
4. Определяет режим контекста.
5. Получает необходимую историю.
6. Формирует запрос к AI Gateway.
7. Сохраняет результат.
8. Возвращает ответ или идентификатор фоновой задачи.

Для короткого запроса допустима синхронная обработка. Если операция длительная или требует нескольких этапов, используется AI Job.

### 5.5. Состояния интерфейса

Состояния **локальные для UI** (не статусы AIJob):

- `idle`;
- `submitting`;
- `streaming`;
- `processing`;
- `completed` — UI: генерация/операция завершена успешно; на backend AIJob это **`succeeded` (D-011)**;
- `failed`;
- `cancelled`.

Не все состояния обязательны для каждой реализации. Например, при отсутствии потоковой выдачи `streaming` не используется. Не путать UI-`completed` со статусом AIJob.

### 5.6. Ошибки

Если запрос не выполнен:

- сообщение пользователя остаётся в истории, если оно уже сохранено;
- система показывает понятную ошибку;
- пользователь может повторить запрос;
- повтор не должен случайно создавать несколько одинаковых фоновых задач;
- внутренние трассировки и секреты провайдера не показываются пользователю.

### 5.7. Критерии приёмки

- [ ] Пользователь может создать и открыть переписку.
- [ ] Сообщения сохраняются в корректном порядке.
- [ ] При повторном открытии история восстанавливается.
- [ ] Права доступа проверяются на сервере.
- [ ] Ответ относится к текущей переписке.
- [ ] Ошибки отображаются без потери доступной истории.
- [ ] Повторная отправка контролируется.
- [ ] Доступны предусмотренные действия над ответом.

## 6. Сценарий B: анализ юридического документа

### 6.1. Цель

Позволить пользователю загрузить договор или другой юридический документ и получить структурированный анализ.

Примеры:

- анализ рисков договора;
- выявление односторонних условий;
- поиск сроков и обязательств;
- анализ ответственности сторон;
- проверка наличия обязательных разделов;
- подготовка краткого резюме.

### 6.2. Пользовательский путь

1. Пользователь открывает Workspace или создаёт его.
2. Загружает файл.
3. Видит состояние обработки.
4. После успешной обработки открывает документ.
5. Выбирает «Анализировать документ».
6. Выбирает тип анализа либо вводит свой вопрос.
7. Запускает анализ.
8. Получает результат со ссылками на конкретные фрагменты документа.
9. Переходит к соответствующим фрагментам.
10. Может продолжить обсуждение в Conversation.

### 6.3. Обработка файла

Фоновая обработка описана в `docs/13-file-storage-and-document-processing.md`.

До анализа система должна проверить:

- что файл успешно загружен;
- что формат поддерживается;
- что извлечение текста завершилось успешно;
- что документ доступен пользователю;
- что версия документа определена;
- что извлечённый текст пригоден для анализа.

Если извлечение завершилось ошибкой, анализ не должен запускаться так, будто текст доступен полностью.

### 6.4. Подготовка контекста

Контекст формируется из:

- вопроса пользователя;
- выбранной версии документа;
- релевантных фрагментов;
- дополнительных документов, если они выбраны;
- разрешённых инструкций Workspace.

Не следует автоматически подключать все документы организации.

### 6.5. Структура результата

Для типового анализа можно использовать следующие разделы:

1. Краткое резюме.
2. Основные условия.
3. Обязательства сторон.
4. Сроки и порядок исполнения.
5. Ответственность.
6. Потенциальные риски.
7. Неоднозначные или отсутствующие условия.
8. Рекомендуемые вопросы для проверки.
9. Ссылки на исходные фрагменты.

Конкретная структура зависит от типа документа и поставленной задачи.

### 6.6. Ссылки на фрагменты

Каждый существенный вывод должен по возможности ссылаться на конкретный фрагмент документа.

Система должна сохранять идентификатор версии и координаты фрагмента, если они доступны.

Для PDF координаты могут включать страницу и положение фрагмента. Для DOCX — структурный элемент, абзац или иной устойчивый указатель, если он реализован.

Нельзя показывать фиктивный номер страницы или абзаца.

### 6.7. Ограничения анализа

Система должна сообщать, если:

- часть текста не извлечена;
- документ содержит сканы без распознавания;
- таблицы или приложения обработаны не полностью;
- существенные страницы отсутствуют;
- вывод зависит от фактов, не содержащихся в документе.

### 6.8. Критерии приёмки

- [ ] Анализ запускается только после успешной обработки документа.
- [ ] Анализ использует правильную версию файла.
- [ ] Результат имеет структурированный формат.
- [ ] Ссылки ведут к существующим фрагментам.
- [ ] Неполнота извлечения отображается пользователю.
- [ ] Доступ к документу проверяется до обработки.
- [ ] Удалённый или недоступный документ не включается в новый контекст.
- [ ] Ошибки обработки и AI-запроса различаются.

## 7. Сценарий C: подготовка юридического документа

### 7.1. Цель

Позволить пользователю подготовить проект документа на основании заданных требований, выбранных материалов и, если нужно, проверенных правовых источников.

Примеры:

- проект договора;
- ответ на претензию;
- дополнительное соглашение;
- юридическое заключение;
- проект письма контрагенту;
- правовая позиция.

### 7.2. Пользовательский путь

1. Пользователь выбирает Workspace.
2. Открывает функцию создания документа.
3. Выбирает тип документа или описывает задачу.
4. Указывает стороны, обстоятельства и требования.
5. Выбирает исходные документы, если они нужны.
6. Указывает, требуется ли правовое исследование.
7. Запускает подготовку.
8. Получает черновик.
9. Проверяет результат.
10. Редактирует, копирует или сохраняет его в поддерживаемом формате.

### 7.3. Сбор требований

Перед генерацией система должна определить, достаточно ли информации для полезного результата.

Если отсутствуют критические сведения, например тип договора, сторона пользователя или дата, от которой зависит применимое право, система должна задать уточняющий вопрос либо явно перечислить допущения.

Необязательно блокировать генерацию из-за любого отсутствующего поля. Решение зависит от риска и назначения документа.

### 7.4. Контекст

Допустимые источники:

- требования пользователя;
- выбранные документы;
- подтверждённые факты из Workspace;
- утверждённые шаблоны;
- разрешённые правовые источники;
- применимые инструкции организации.

Факты, которые модель вывела предположительно, не должны автоматически становиться подтверждёнными обстоятельствами.

### 7.5. Черновик и юридическая проверка

Сгенерированный текст должен обозначаться как проект, требующий проверки юристом.

Если документ содержит ссылки на нормы или судебную практику, система должна проверить их существование и, когда это возможно, применимость на заданную дату.

Если источники недоступны, система должна сообщить об этом и не подменять проверку правдоподобной ссылкой.

### 7.6. Редактирование

Для MVP допустим простой workflow:

- сгенерировать черновик;
- скопировать текст;
- запросить изменение;
- получить новую редакцию;
- сохранить результат в переписке.

Полноценный редактор с отслеживанием изменений, комментариями, согласованием и управлением версиями можно реализовать позже.

### 7.7. Критерии приёмки

- [ ] Пользователь может задать тип документа и требования.
- [ ] Система уточняет критически важные неизвестные сведения.
- [ ] Источники контекста проверяются по ACL.
- [ ] Результат сохраняется как черновик.
- [ ] Правовые ссылки проверяются, если используются.
- [ ] Неизвестные факты не выдаются за подтверждённые.
- [ ] Пользователь может запросить новую редакцию.
- [ ] Ошибка генерации не приводит к потере исходных требований.

## 8. Сценарий D: юридическое исследование

### 8.1. Цель

Помочь юристу найти нормативные акты и судебные решения, относящиеся к правовому вопросу.

Сценарий зависит от фактически подключённых источников и не должен обещать полное покрытие законодательства или судебной практики.

### 8.2. Пользовательский путь

1. Пользователь формулирует правовой вопрос.
2. Указывает юрисдикцию и дату анализа, если они неочевидны.
3. Выбирает доступные категории источников.
4. Запускает исследование.
5. Видит ход выполнения.
6. Получает предварительный вывод.
7. Просматривает нормы и судебные решения.
8. Открывает первоисточники.
9. Уточняет вопрос или продолжает исследование.

### 8.3. Backend workflow

1. Создать `LegalResearchRun`.
2. Определить область и дату поиска.
3. Разложить сложный вопрос на подзапросы.
4. Выполнить поиск по доступным источникам.
5. Проверить метаданные и версии.
6. Отобрать подтверждающие фрагменты.
7. Сформировать контекст.
8. Получить аналитический ответ через AI Gateway.
9. Проверить цитаты.
10. Сохранить результат и метаданные исследования.

### 8.4. Частичный результат

Если часть источников недоступна, система может показать частичный результат, если:

- неполнота явно обозначена;
- недоступные источники перечислены;
- вывод не выдаётся за исчерпывающее исследование;
- непроверенные ссылки исключены или явно помечены.

### 8.5. Критерии приёмки

- [ ] Исследование связано с заданной юрисдикцией и датой.
- [ ] Источники доступны через разрешённые интеграции.
- [ ] Для результатов сохраняются реквизиты и версии.
- [ ] Цитаты проходят предусмотренную проверку.
- [ ] Недоступность источника отражается в результате.
- [ ] Пользователь может открыть первоисточник.
- [ ] Частичный результат не выдаётся за полный.
- [ ] Все действия проходят через серверную авторизацию.

## 9. Сценарий E: работа в Workspace

### 9.1. Цель

Объединить документы, переписки и исследования в рамках одной юридической задачи.

Workspace должен помогать организовывать работу, но не превращаться в неограниченный общий контекст, передаваемый модели целиком.

### 9.2. Создание Workspace

Пользователь:

1. Создаёт рабочее пространство.
2. Указывает название.
3. При необходимости добавляет описание.
4. Выбирает доступных участников, если эта функция предусмотрена его правами.
5. Загружает документы.
6. Создаёт переписки и исследования.

Backend проверяет полномочия на создание Workspace и назначение участников.

### 9.3. Добавление участников

При добавлении пользователя необходимо:

- проверить членство в организации;
- определить разрешённые роли;
- установить доступ к Workspace;
- учесть существующие ограничения;
- не предоставлять права на все объекты организации автоматически.

Изменение членства или отзыв доступа должны применяться к последующим запросам без ожидания завершения обычного кеширования прав.

### 9.4. Список материалов

Интерфейс должен показывать:

- документы и их статусы;
- переписки;
- исследования;
- время последнего обновления;
- доступные действия;
- ошибки обработки.

Если пользователь не имеет права открыть конкретный материал, интерфейс не должен раскрывать его содержимое.

### 9.5. Критерии приёмки

- [ ] Workspace объединяет связанные материалы.
- [ ] Пользователь видит только доступные ему объекты.
- [ ] У каждого документа отображается состояние обработки.
- [ ] Переписки не смешивают контекст автоматически.
- [ ] Изменения доступа учитываются сервером.
- [ ] Удаление связи с документом не удаляет сам документ без отдельного действия.
- [ ] Административные полномочия не обходят правила доступа к содержимому.

## 10. Сквозной сценарий: договор → исследование → заключение

Этот сценарий объединяет несколько функций и подходит для демонстрации ценности продукта.

### 10.1. Пользовательский сценарий

1. Юрист создаёт Workspace для сделки.
2. Загружает проект договора.
3. Дожидается обработки файла.
4. Запускает анализ рисков.
5. Просматривает выводы со ссылками на пункты договора.
6. Выбирает один из рисков.
7. Запускает правовое исследование по этому вопросу.
8. Система находит доступные нормы и судебные материалы.
9. Юрист проверяет первоисточники.
10. Создаёт проект заключения с учётом анализа и исследования.
11. Проверяет результат и сохраняет его в рамках Workspace.

### 10.2. Технический поток

```text
Workspace
   |
   v
Upload Contract
   |
   v
Document Processing Job
   |
   v
Document Ready
   |
   v
Contract Analysis Job
   |
   v
Risk Findings + Document Evidence
   |
   v
Legal Research Job
   |
   v
Legal Evidence + Citations
   |
   v
Drafting Job
   |
   v
Draft Legal Opinion
   |
   v
Human Review
```

### 10.3. Правила сквозного контекста

- Анализ договора использует определённую версию документа.
- Исследование получает конкретный юридический вопрос, а не автоматически весь договор.
- Во внешний поисковый запрос передаётся минимально необходимая информация.
- Правовые источники хранятся отдельно от документов клиента.
- Заключение использует подтверждённые результаты предыдущих этапов.
- Каждая операция повторно проверяет права доступа.
- При изменении договора система должна обозначить, что предыдущий анализ относится к другой версии.

### 10.4. Критерии приёмки

- [ ] Все операции связаны с правильным Workspace.
- [ ] Между этапами передаются идентификаторы и версии, а не только произвольный текст.
- [ ] Можно определить, какой документ использовался для анализа.
- [ ] Правовые источники доступны для отдельной проверки.
- [ ] Результат не теряет происхождение ключевых выводов.
- [ ] Изменение исходного документа не меняет исторический результат незаметно.
- [ ] Отмена или ошибка одного этапа корректно отражается в интерфейсе.

## 11. Состояния фоновых операций

Для длительных сценариев используется общий механизм AI Jobs.

**CONFIRMED (D-011).** Статусы AIJob:

- `queued`;
- `running`;
- `succeeded`;
- `failed`;
- `cancelled`;
- `timed_out`.

Не использовать `retry_wait` или `completed` как статусы job. Ожидание повтора — через поля задачи (например `nextRetryAt`); UI при необходимости показывает локальный индикатор задержки, не отдельный статус AIJob.

### 11.1. UX состояния

| Статус AIJob / UI | Поведение интерфейса |
|---|---|
| `queued` | Показывать, что операция ожидает выполнения |
| `running` | Показывать выполнение |
| UI: задержка повтора (не статус AIJob) | При значимой задержке — по данным полей ретрая (`nextRetryAt` и т.п.) |
| `succeeded` (UI может маппить в локальный `completed`) | Отобразить результат |
| `failed` | Показать понятную ошибку и допустимые действия |
| `cancelled` | Отобразить отмену |
| `timed_out` | Сообщить о превышении времени и предложить допустимый повтор |

### 11.2. Повторная отправка

Повторная отправка не должна создавать дублирующие операции по одному действию пользователя.

Для этого применяются идемпотентные ключи, идентификаторы операции и правила из `docs/11-api-conventions.md` и `docs/15-ai-jobs-and-background-processing.md`.

### 11.3. Частичные результаты

Если задача состоит из нескольких этапов, нужно определить, можно ли сохранить промежуточные результаты.

Частичный результат должен иметь явный статус и не должен отображаться как завершённое исследование или окончательный документ.

## 12. Общие правила обработки ошибок

### 12.1. Категории ошибок

Предлагается различать:

- ошибки авторизации;
- ошибки валидации;
- недоступность документа;
- ошибки извлечения текста;
- ошибки поиска;
- ошибки AI-провайдера;
- превышение лимита;
- отмену операции;
- ошибки проверки цитат;
- внутренние технические ошибки.

### 12.2. Поведение продукта

Для каждой ошибки следует определить:

1. Что сохраняется.
2. Что видит пользователь.
3. Можно ли безопасно повторить операцию.
4. Нужно ли повторно проверять права.
5. Какие сведения попадают в аудит.
6. Как система предотвращает дублирование.

Не следует показывать пользователю необработанные stack traces, секреты или внутренние URL.

### 12.3. Неопределённость результата

Отдельно от технических ошибок необходимо отображать ограничения содержательной достоверности:

- недостаточно данных;
- документ обработан не полностью;
- источники не удалось проверить;
- историческая редакция не подтверждена;
- судебная практика неполна;
- вывод зависит от дополнительных обстоятельств.

Это не обязательно ошибка выполнения. Это может быть корректным результатом работы системы.

## 13. API и frontend orchestration

Конкретные эндпоинты должны соответствовать `docs/11-api-conventions.md`. Ниже перечислены логические операции.

| Операция | API-ресурс | Тип выполнения |
|---|---|---|
| Создать переписку | Conversations | Обычно синхронно |
| Отправить сообщение | Messages / AI Jobs | Синхронно или асинхронно |
| Загрузить документ | Documents | Загрузка + фоновая обработка |
| Проверить обработку | Documents / Jobs | Получение статуса |
| Запустить анализ | AI Jobs | Асинхронно |
| Создать правовое исследование | Legal Research | Асинхронно при длительной операции |
| Получить результат | Job Result / Research Result | По готовности |
| Подключить документ | Conversation Documents | Синхронно |
| Отменить задачу | AI Jobs | Синхронно принять запрос на отмену |

Это не окончательный контракт. До реализации необходимо сопоставить операции с уже существующими DTO и контроллерами.

### 13.1. Frontend orchestration

Frontend должен:

- отображать серверные состояния;
- не считать локальное состояние доказательством успешного выполнения;
- восстанавливать статус операции после перезагрузки;
- обрабатывать сетевые ошибки;
- предотвращать случайные дубликаты;
- сохранять введённый пользователем текст при ошибке;
- не обходить авторизацию ради удобства интерфейса.

Для обновления состояния допустимы polling или SSE. Выбор зависит от требований к задержке, нагрузки и инфраструктуры.

## 14. Наблюдаемость и аудит

Для каждой операции рекомендуется фиксировать:

- идентификатор запроса;
- пользователя и организацию;
- идентификатор Workspace и Conversation;
- тип сценария;
- идентификатор AI Job;
- использованные версии документов;
- использованные правовые источники;
- модель и маршрут AI Gateway;
- статус выполнения;
- длительность;
- потребление и стоимость, если доступны;
- ошибки и результат валидации.

Полные тексты документов и сообщений не следует без необходимости копировать в технические логи.

Для сквозных сценариев полезно иметь возможность связать загрузку файла, обработку, анализ, исследование и подготовку документа через корреляционные идентификаторы.

## 15. Тестирование

### 15.1. Функциональные тесты

- создание и открытие переписки;
- отправка и сохранение сообщения;
- загрузка и обработка файла;
- анализ документа;
- подготовка черновика;
- запуск исследования;
- просмотр результата;
- работа с несколькими материалами Workspace.

### 15.2. Тесты доступа

- пользователь не может открыть чужой Workspace;
- пользователь не может анализировать недоступный документ;
- нельзя подключить документ из другой организации;
- отзыв доступа блокирует последующие запросы;
- кеш не раскрывает результаты;
- идентификаторы в запросах не позволяют обойти ACL.

### 15.3. Тесты устойчивости

- временный сбой AI-провайдера;
- ошибка извлечения текста;
- недоступность правового источника;
- повторная отправка запроса;
- отмена фоновой задачи;
- превышение лимита контекста;
- повторное открытие страницы с активной задачей.

### 15.4. Тесты юридического качества

- корректность ссылок на документ;
- корректность ссылок на правовые источники;
- сохранение версии документа;
- отсутствие выдуманных реквизитов;
- обозначение неполноты исследования;
- отсутствие утверждений об актуальности без подтверждения.

## 16. Этапы реализации

### Этап 1. Рабочий AI-чат

- Conversation;
- Message;
- AI Gateway;
- сохранение истории;
- базовые состояния интерфейса;
- обработка ошибок.

### Этап 2. Документы

- загрузка;
- обработка;
- статусы;
- анализ выбранного документа;
- ссылки на фрагменты.

### Этап 3. Workspace

- объединение документов и переписок;
- управление контекстом;
- доступ участников;
- тесты изоляции.

### Этап 4. Подготовка документов

- шаблоны задач;
- сбор требований;
- генерация черновика;
- редактирование и повторная генерация.

### Этап 5. Правовое исследование

- поиск по разрешённым источникам;
- проверка версий;
- цитирование;
- интеграция результатов в переписку и Workspace.

### Этап 6. Сквозные процессы

- анализ документа;
- исследование по выявленному вопросу;
- подготовка заключения;
- связывание результатов;
- аудит и контроль качества.

### Этап 7. Оптимизация

- производительность;
- стоимость;
- UX длительных задач;
- качество AI-результатов;
- наблюдаемость;
- безопасность.

## 17. Критерии готовности MVP

- [ ] Работает основной AI-чат.
- [ ] История переписки сохраняется и восстанавливается.
- [ ] Пользователь может загружать и обрабатывать поддерживаемые документы.
- [ ] Реализован хотя бы один полезный сценарий анализа документа.
- [ ] Можно подготовить черновик юридического текста.
- [ ] Workspace объединяет связанные материалы.
- [ ] Контекст формируется с учётом прав доступа.
- [ ] Длительные операции имеют наблюдаемые состояния.
- [ ] Повторные запросы контролируются.
- [ ] Пользователь получает понятные ошибки.
- [ ] Источники и версии доступны для проверки там, где это применимо.
- [ ] Внутренние документы не передаются внешним источникам без разрешённого основания.
- [ ] Реализованы тесты изоляции данных.
- [ ] Критические сценарии покрыты интеграционными тестами.
- [ ] Неопределённость и ограничения результатов отображаются явно.

## 19. Инструкции для Cursor

Перед реализацией:

1. Изучи текущую структуру репозитория.
2. Найди реализованные модули Conversation, Workspace, Documents, AI Jobs и AI Gateway.
3. Сопоставь текущие API с этим документом.
4. Составь список существующих возможностей, пробелов и конфликтов.
5. Не создавай дубликаты сущностей и сервисов.
6. Предложи минимальный вертикальный сценарий для реализации.
7. Сначала реализуй один полный сценарий от интерфейса до хранения результата.
8. Добавь тесты доступа, обработки ошибок и повторных запросов.
9. Обнови документацию по фактически реализованному поведению.
10. Только после проверки переходи к следующему сценарию.

### Рекомендуемый первый вертикальный сценарий

**Пользователь создаёт Conversation → отправляет сообщение → получает AI-ответ → история сохраняется → пользователь обновляет страницу → история восстанавливается.**

После завершения этого сценария можно добавить подключение одного документа, затем его анализ, Workspace и правовое исследование.

Не следует начинать с реализации всех сценариев и всех модулей одновременно: это затруднит проверку интеграций, прав доступа и корректности данных.

## 20. Итог

Этот документ описывает продуктовые процессы, которые объединяют ранее спроектированные технические модули.

Ключевой принцип реализации — развивать продукт сквозными сценариями. Каждый сценарий должен работать полностью: от действия пользователя до корректно сохранённого результата, с проверкой доступа, обработкой ошибок и понятным отображением состояния.

Для MVP важнее надёжно реализовать несколько полезных юридических задач, чем создать большое количество функций, которые не связаны между собой или не обеспечивают проверяемость результата.

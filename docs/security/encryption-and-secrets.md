# Шифрование и управление секретами

**Статус: PROPOSED**

Сверять с `docs/03-data-security.md` и `docs/23-deployment-and-infrastructure.md`. Фактический механизм at rest и владельцы ключей — OPEN (`DECISIONS-TO-REVIEW.md`).

## Требования
- Использовать TLS для передачи данных между браузером и сервисом, а также между компонентами там, где это поддерживается архитектурой.
- Для PostgreSQL, файлов, резервных копий и журналов проверить шифрование at rest и задокументировать фактический механизм.
- Не хранить секреты в репозитории, Docker-образах, frontend bundle или логах.
- Для локальной разработки предоставить `.env.example` только с пустыми/безопасными placeholder-значениями.
- Ограничить доступ к секретам по принципу least privilege; разделять dev/test/staging/production.
- Ротация должна иметь документированный процесс и тестируемый сценарий отзыва скомпрометированного секрета.
- Не использовать один общий секрет для независимых сред.

## Не считать подтверждённым без проверки
- наличие шифрования дисков или управляемого шифрования у провайдера;
- ротацию ключей;
- централизованное хранилище секретов;
- регулярную ротацию и ограничение доступа;
- шифрование резервных копий.

## Свидетельства
Сохранять ссылку на конфигурацию, результат проверки, владельца контроля и дату последней верификации. Не помещать сами секреты в evidence.

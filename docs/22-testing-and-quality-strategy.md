# Testing and Quality Strategy

**Файл:** `docs/22-testing-and-quality-strategy.md`  
**Статус:** Proposed для tooling/CI; обязательные проверки по **D-008–D-022** (изоляция org, AIJob D-011, Synthetic/O-002, admin grant D-013/D-016, файлы D-010/D-017, pgvector D-018, удаление D-019).  
**Проект:** AI-платформа для юридических команд  
**Область:** Frontend, backend, API, база данных, AI, безопасность, CI/CD

---

## 1. Цель документа

Определить единые правила контроля качества при разработке и эксплуатации платформы.

Система работает с юридическими документами, перепиской и результатами AI-анализа. Поэтому недостаточно проверить, что интерфейс отображается, а API возвращает HTTP 200.

Необходимо проверять:

- Корректность бизнес-логики.
- Работу API и целостность данных.
- Разграничение доступа между организациями и пользователями.
- Безопасность хранения, обработки и удаления документов.
- Корректность фоновых задач и AI-генерации.
- Достоверность отображаемых юридических источников.
- Устойчивость к сетевым ошибкам и повторным запросам.
- Работу приложения после изменений в коде.

Этот документ определяет стратегию тестирования, но не заменяет конкретные тесты отдельных модулей.

## 2. Основные принципы

### 2.1. Проверяем поведение, а не только код

Тест должен подтверждать результат, который важен пользователю или системе.

Например, недостаточно проверить, что функция `checkAccess()` возвращает `false` для определённого входа. Необходимо также проверить, что пользователь не может получить документ через API, даже если знает его идентификатор.

### 2.2. Безопасность — часть функциональности

Для каждого сценария доступа необходимо проверять не только разрешённые действия, но и запрещённые.

Если пользователь может читать собственный документ, нужно проверить, что он не может прочитать документ другой организации, изменить чужой ресурс или получить его содержимое через поиск.

### 2.3. AI требует отдельной стратегии оценки

Обычные тесты не могут гарантировать, что языковая модель всегда выдаёт юридически правильный ответ.

Поэтому необходимо разделять:

- Технические проверки AI-интеграции.
- Проверки соблюдения инструкций и формата.
- Проверки использования источников.
- Оценку качества ответов на подготовленных примерах.
- Экспертную оценку юридической корректности.

### 2.4. Тесты должны быть воспроизводимыми

По возможности тесты не должны зависеть от случайных результатов генерации, реального внешнего провайдера, нестабильного интернета или текущего состояния production-данных.

Внешние сервисы подменяются тестовыми адаптерами там, где проверяется логика нашего приложения, а не сам сервис.

### 2.5. Не обходить проверки ради успешного CI

Нельзя считать исправлением ошибки:

- Отключение TypeScript-проверки.
- Исключение теста из запуска без объяснения.
- Ослабление утверждений до бессмысленных проверок.
- Добавление `skip`, `only` или аналогичных механизмов для сокрытия проблем.
- Игнорирование ошибок линтера.
- Подмену реального результата фиктивным успешным ответом.

Изменение тестов допустимо, если изменилось требуемое поведение и это обосновано.

## 3. Уровни тестирования

Предлагается использовать следующую стратегию.

| Уровень | Что проверяет | Когда запускать |
|---|---|---|
| Unit | Изолированная логика функций и модулей | При каждом изменении |
| Integration | Взаимодействие модулей, БД, очередей и API | При каждом изменении соответствующих модулей |
| API / Contract | Форматы запросов, ответов, ошибок и совместимость | При изменении API |
| E2E | Полные пользовательские сценарии | Перед слиянием и релизом |
| Security | Контроль доступа, изоляция и защита данных | При изменениях, затрагивающих безопасность |
| AI Evaluation | Качество и соответствие AI-ответов | При изменении промптов, моделей, RAG или обработки документов |
| Load | Производительность и поведение под нагрузкой | Перед значимым релизом и при изменениях инфраструктуры |
| Manual QA | UX, сложные визуальные и юридические сценарии | Перед релизом по необходимости |

Не все тесты должны запускаться на каждом коммите. Быстрые проверки выполняются постоянно, а тяжёлые наборы — по расписанию или перед релизом.

## 4. Unit-тесты

Unit-тесты проверяют небольшие части логики без необходимости запускать всю систему.

### 4.1. Backend

Проверять:

- Бизнес-правила.
- Проверки и преобразование DTO.
- Расчёт лимитов и стоимости AI-запросов.
- Проверку допустимости переходов состояния AI-задачи (**D-011**: только `queued|running|succeeded|failed|cancelled|timed_out`; без `retry_wait`/`completed` как статус job).
- Логику определения прав доступа.
- Формирование фильтров для поиска документов.
- Правила удаления данных.
- Обработку ошибок провайдера.
- Валидацию ссылок и метаданных юридических источников.

### 4.2. Frontend

Проверять:

- Обработку API-ошибок.
- Отображение статусов фоновых задач.
- Клиентскую валидацию форм.
- Форматирование дат, реквизитов и денежных значений.
- Разбор потоковых событий.
- Поведение отдельных компонентов при загрузке, ошибке и пустом результате.

### 4.3. Правила

- Не тестировать каждую внутреннюю строку кода только ради покрытия.
- Не привязывать тесты к деталям реализации, которые не важны для поведения.
- Проверять граничные случаи и ошибки.
- Для критической бизнес-логики использовать отдельные тесты на разрешённые и запрещённые сценарии.

## 5. Integration-тесты

Integration-тесты подтверждают, что несколько частей системы правильно работают вместе.

### 5.1. База данных

Проверять:

- Создание и обновление записей.
- Внешние ключи и уникальные ограничения.
- Транзакции при связанных операциях.
- Конкурентное изменение одного ресурса.
- Отсутствие частично сохранённых данных при ошибке.
- Корректность миграций на тестовой базе.
- Поведение при повторном выполнении идемпотентных операций.

Тесты базы данных желательно запускать на том же типе СУБД, который используется в production. Для проекта предполагается PostgreSQL.

### 5.2. API

Проверять:

- Валидацию входных данных.
- Формат успешного ответа.
- Формат ошибок.
- Авторизацию и проверку прав.
- Пагинацию и фильтрацию.
- Конфликты состояния.
- Обработку отсутствующих ресурсов.
- Ограничение частоты запросов там, где оно предусмотрено.
- Корректность транзакций при выполнении операций.

### 5.3. Фоновые задачи

Проверять:

- Постановку задачи в очередь.
- Получение задачи worker-процессом.
- Успешное завершение.
- Повторную попытку после временной ошибки.
- Отказ после исчерпания попыток.
- Отмену задачи.
- Обработку зависшей задачи.
- Отсутствие дублирования результата при повторной доставке сообщения.
- Поведение при удалении документа во время обработки.

Очередь может доставить задачу повторно. Поэтому система должна быть спроектирована с учётом повторного выполнения операций, а не рассчитывать на однократный запуск.

## 6. API-контрактные тесты

API-контракт определяет, как frontend и backend обмениваются данными.

Необходимо проверять:

- Совпадение схем запросов с документацией.
- Совпадение схем ответов.
- Типы идентификаторов и дат.
- Формат ошибок.
- Обязательные и необязательные поля.
- Поведение при неизвестных полях.
- Совместимость frontend с изменениями backend.
- Корректность обработки `401`, `403`, `404`, `409`, `429` и `5xx`.

Если используется OpenAPI, рекомендуется генерировать типы frontend из согласованного контракта и проверять изменения схем в CI.

Изменение контракта должно быть осознанным. Нельзя незаметно переименовывать поля или менять смысл ответа, если frontend ещё зависит от прежнего формата.

## 7. Тестирование авторизации и изоляции организаций

Это один из наиболее важных разделов проекта.

### 7.1. Базовые сценарии (изоляция организаций)

Подготовить как минимум две организации:

- Организация A.
- Организация B.

В каждой организации создать разных пользователей, рабочие пространства, документы, чаты, а также `Client`/`Matter` при необходимости (**D-009**).

Проверить:

1. Пользователь A читает разрешённый документ своей организации.
2. Пользователь A не читает документ организации B.
3. Пользователь A не получает содержимое чужого документа через изменение ID в URL.
4. Пользователь не получает чужие сообщения через API чатов.
5. Поиск (в т.ч. FTS и `pgvector`, **D-018**) не возвращает документы, к которым нет доступа.
6. RAG не использует недоступные документы в контексте AI.
7. Фоновые задачи не выдают результат пользователю, у которого нет соответствующих прав; статусы AIJob соответствуют **D-011**.
8. Приватные ссылки на файлы не позволяют обойти проверку доступа.
9. Кэш не возвращает данные другой организации.
10. Отзыв членства или разрешения прекращает доступ к соответствующим операциям.
11. Client/Matter одной организации недоступны другой организации.

### 7.2. Проверка администратора и `admin_grant:approve`

Для администратора организации отдельно проверить:

- Он может выполнять разрешённые административные действия.
- Сам по себе административный статус не даёт доступ к содержимому чатов и документов.
- Он может создать запрос на временный доступ, если это разрешено.
- Он не может одобрить собственный запрос.
- Одобрять может только участник с `admin_grant:approve`, назначенный владельцем; заявитель ≠ согласующий (**D-016**).
- Без подходящего независимого согласующего доступ не выдаётся.
- Запрос без одобрения не открывает содержимое.
- Доступ ограничен согласованными ресурсами; TTL ≤ 60 минут, проверка срока на сервере (**D-013**).
- По истечении срока доступ прекращается.
- Все значимые действия фиксируются в аудите.
- После отзыва временного доступа повторный запрос к содержимому блокируется.

### 7.3. Проверка IDOR

IDOR — ситуация, когда пользователь меняет идентификатор ресурса и получает чужие данные.

Нужно проверять не только прямой `GET`, но и все операции, принимающие идентификаторы:

- Получение документа.
- Получение версии документа.
- Скачивание файла.
- Чтение чата.
- Получение результата AI-задачи.
- Просмотр исследования.
- Изменение и удаление ресурса.
- Доступ к источникам и вложениям.

Нельзя ограничиваться тестом одного endpoint: проверка должна покрывать все маршруты, через которые может быть доступно содержимое.

## 8. Тестирование жизненного цикла данных

Необходимо проверять полный путь данных, включая производные результаты.

### 8.1. Документы

Проверить:

- Загрузка разрешённого файла.
- Отклонение недопустимого формата.
- Отклонение файла, превышающего лимит.
- Ошибку извлечения текста.
- Повторную обработку.
- Замену версии.
- Архивирование.
- Удаление исходного файла.
- Удаление извлечённого текста, чанков, эмбеддингов и связанных результатов в соответствии с политикой хранения.

### 8.2. Удаление данных (**D-019**, **D-020**)

После подтверждённого удаления:

- Данные становятся недоступны сразу после фиксации операции (**D-019**).
- Удаление из основной системы, извлечённого текста, индексов (в т.ч. `pgvector`) и производных — в пределах 24 часов (**D-019**).

После удаления документа проверить, что недоступны:

- Оригинальный файл.
- Производные файлы и извлечённый текст.
- Чанки и эмбеддинги.
- Записи в поисковых индексах.
- Результаты, которые должны быть удалены по утверждённой политике.
- Ссылки на ресурс, которые больше не должны открываться.

Отдельно проверять поведение кэшей, очередей и уже запущенных AI-задач.

Резервные копии хранятся до 35 дней (**D-020**); тесты не должны обещать мгновенное исчезновение из всех бэкапов. При restore — повторное применение журнала удалений, чтобы удалённые данные не вернулись в рабочую систему.

### 8.3. Восстановление

Проверить резервное восстановление в изолированной среде и убедиться, что после восстановления применяются актуальные правила доступа и удаления (включая journal of deletions, **D-020**).

## 9. Тестирование AI-интеграции

AI-сценарии необходимо тестировать отдельно от внутренней логики бизнес-приложения.

### 9.1. Тестовый / Synthetic AI-провайдер

До разрешения передачи реальных клиентских документов (**O-002**) в автоматических и интеграционных тестах использовать `SyntheticAIProvider` / mock-адаптер (**D-012**): реальные документы в OpenAI API не отправлять. Адаптер должен уметь возвращать:

- Успешный ответ.
- Пустой ответ.
- Некорректный формат.
- Задержку.
- Ошибку авторизации провайдера.
- Ограничение частоты запросов.
- Временную сетевую ошибку.
- Превышение времени ожидания.
- Прерванный поток.
- Ошибку после получения части ответа.

Это позволяет воспроизводить редкие ошибки и проверять восстановление без расходов на реальные API-вызовы.

### 9.2. Проверка AI Gateway

Проверять:

- Выбор провайдера с подходящими возможностями.
- Соблюдение политики обработки данных.
- Корректную передачу параметров.
- Учет токенов и стоимости, если они доступны.
- Таймауты и ограниченные повторы.
- Корректную обработку ошибок.
- Отмену задач.
- Запрет небезопасного fallback на провайдера с неподходящей политикой данных.
- Отсутствие секретов в логах.

### 9.3. Проверка потоковой генерации

Проверять:

- Поступление нескольких частей ответа.
- Разбиение события между сетевыми пакетами.
- Корректное завершение потока.
- Обрыв соединения.
- Повторное подключение.
- Отмену генерации.
- Отсутствие дубликатов.
- Корректное сохранение конечного результата.
- Обработку источников, поступающих отдельно от текста.

### 9.4. Ограничения внешних провайдеров (**D-012**, **D-015**, **O-002**)

Целевой внешний провайдер — OpenAI API (**D-015**); модель OPEN. До завершения проверки договора и политики передачи (**O-002**) — только Synthetic / синтетические данные (**D-012**).

Тестовые сценарии с реальным OpenAI API не должны по умолчанию отправлять реальные клиентские документы.

Для проверки реального API (после разрешения политики) использовать специально подготовленные синтетические данные и отдельные тестовые ключи с ограниченными полномочиями и бюджетом.

### 9.5. Статусы AIJob и поиск

Отдельно проверять:

- Допустимые переходы и сериализацию статусов AIJob только по **D-011** (`succeeded`, не `completed`; нет `retry_wait` как статуса).
- Поведение PostgreSQL FTS + `pgvector` с повторной проверкой ACL (**D-018**).

## 10. Оценка качества AI-ответов

Unit-тесты не доказывают юридическую корректность ответа модели. Для этого нужен отдельный evaluation-набор.

### 10.1. Подготовка набора

Создать набор репрезентативных юридических задач, включающий:

- Краткое резюме договора.
- Поиск потенциально рискованных условий.
- Сравнение двух редакций документа.
- Подготовку проекта юридического текста.
- Поиск применимых нормативных актов.
- Ответ с обязательными ссылками на источники.
- Случаи недостатка данных.
- Противоречивые документы.
- Устаревшую редакцию правового акта.
- Попытку получить вывод, который не подтверждается источниками.
- Документ с вредоносными инструкциями внутри текста.
- Запрос на использование документа, к которому у пользователя нет доступа.

В наборе должны быть эталонные критерии оценки, подготовленные или проверенные компетентным специалистом.

### 10.2. Критерии оценки

Предлагаемые критерии:

| Критерий | Что оценивается |
|---|---|
| Соответствие задаче | Ответ действительно решает поставленную задачу |
| Фактическая корректность | Утверждения не противоречат проверенным данным |
| Подтверждение источниками | Источники действительно подтверждают соответствующие утверждения |
| Полнота | Не пропущены существенные элементы задачи |
| Соблюдение ограничений | Модель не выходит за допустимые рамки |
| Обработка неопределённости | Недостаток данных обозначен явно |
| Структура результата | Формат пригоден для предусмотренного сценария |
| Конфиденциальность | В ответе не раскрываются недоступные данные |

Для критических сценариев результат оценивается по заранее определённым правилам, а не только по субъективной оценке «ответ выглядит хорошо».

### 10.3. Регрессионная оценка

После изменения модели, системного промпта, RAG, разбиения документов или правил формирования контекста необходимо повторно запускать evaluation-набор.

Сравнивать:

- Изменение качества ответов.
- Корректность ссылок.
- Частоту неподтверждённых утверждений.
- Соблюдение ограничений.
- Стоимость и время ответа.

Необходимо сохранять версии конфигураций и результаты оценок, чтобы понимать, какое изменение повлияло на качество.

### 10.4. Ограничение

Даже успешное прохождение evaluation-набора не гарантирует правильность любого юридического ответа. AI-результат должен оставаться проверяемым пользователем, а критические сценарии требуют экспертной проверки.

## 11. Тестирование юридических источников

Отдельно проверять:

- Существование источника.
- Корректность реквизитов.
- Соответствие ссылки указанному документу.
- Актуальность редакции на нужную дату.
- Соответствие цитаты содержимому источника.
- Различие между действующей и утратившей силу нормой.
- Отображение даты проверки или редакции, если эти данные доступны.
- Корректную обработку отсутствующего источника.

В тестах использовать подготовленный набор источников с проверенными метаданными.

Если источник временно недоступен, система не должна незаметно подменять его выдуманной ссылкой или представлять непроверенные реквизиты как подтверждённые.

## 12. E2E-тестирование

E2E-тесты проходят через реальный интерфейс и API в тестовой среде.

### Минимальный набор сценариев MVP

**Авторизация**
- Вход.
- Выход.
- Приглашение пользователя.
- Отзыв доступа.
- Истечение сессии.

**Рабочие пространства**
- Открытие доступного пространства.
- Отказ в доступе к чужому пространству.
- Управление участниками в рамках разрешений.

**Документы**
- Загрузка.
- Отображение состояния обработки.
- Просмотр результата.
- Запуск анализа.
- Удаление.
- Проверка недоступности удалённого ресурса.

**AI-чат**
- Создание чата.
- Отправка сообщения.
- Получение ответа.
- Отображение источников.
- Ошибка провайдера.
- Отмена задачи.
- Повторное открытие завершённого диалога.

**Юридическое исследование**
- Запуск исследования.
- Получение результатов.
- Переход к источнику.
- Обработка ситуации, когда источник не подтверждён или недоступен.

**Безопасность**
- Запрет межорганизационного доступа.
- Запрет доступа администратора к содержимому без одобрения.
- Запрет повторного использования просроченного временного доступа.

E2E-тесты должны использовать изолированные тестовые данные и не зависеть от содержимого production.

## 13. Нагрузочное тестирование

Нагрузочные тесты нужны для проверки поведения системы при ожидаемой и повышенной нагрузке.

Проверять:

- Одновременные пользовательские запросы.
- Создание множества AI-задач.
- Очередь фоновых задач.
- Массовую загрузку документов.
- Поиск по большому количеству чанков.
- Ограничение параллельных обращений к провайдерам.
- Исчерпание лимитов провайдера.
- Увеличение задержек базы данных.
- Отказ отдельного worker-процесса.

### Метрики

- Время ответа API: p50, p95, p99.
- Доля ошибок.
- Количество задач в очереди.
- Время ожидания до начала выполнения.
- Полное время выполнения AI-задачи.
- Использование CPU, RAM и соединений с БД.
- Стоимость и количество токенов, если доступны.
- Доля задач, завершившихся таймаутом.

Численные SLO и целевые показатели нагрузки должны быть утверждены отдельно после определения инфраструктуры, ожидаемого числа активных пользователей и выбранных AI-провайдеров.

## 14. Проверки безопасности

Предлагаемый набор:

- Попытки обхода авторизации.
- Межорганизационный доступ.
- IDOR.
- CSRF для защищённых изменяющих операций, если используется cookie-based authentication.
- XSS и небезопасный рендеринг содержимого документов.
- SQL injection и небезопасная обработка параметров.
- Небезопасная загрузка файлов.
- Утечка секретов.
- Утечка содержимого через логи.
- Использование недоступных документов в RAG.
- Prompt injection в документах и внешних источниках.
- Утечка данных через кэш.
- Небезопасные публичные ссылки на файлы.
- Недостаточная защита фоновых задач.
- Ошибки отзыва доступа.

Автоматизированные тесты должны дополняться независимым security review перед использованием реальных клиентских данных.

## 15. Тестовые данные

### 15.1. Принципы

- Использовать синтетические юридические документы.
- Не копировать реальные конфиденциальные дела в тестовую среду.
- Не использовать production-базу для автоматических тестов.
- Создавать данные с известными правами доступа.
- Изолировать тестовые организации друг от друга.
- Удалять тестовые данные после завершения тестов.
- Не использовать реальные секреты и API-ключи в репозитории.

### 15.2. Фабрики тестовых данных

Рекомендуется создать общие фабрики для:

- Пользователей.
- Организаций.
- Членств и ролей.
- Рабочих пространств.
- Документов и версий.
- Чатов и сообщений.
- AI-задач.
- Источников и цитат.
- Запросов и одобрений временного доступа.

Фабрики должны создавать валидные данные по умолчанию и позволять переопределять необходимые поля.

## 16. CI и обязательные проверки

Предлагаемый порядок CI:

1. Установка зависимостей по lock-файлу.
2. Проверка форматирования, если она настроена.
3. ESLint.
4. TypeScript typecheck.
5. Unit-тесты.
6. Integration-тесты.
7. Сборка production.
8. API-контрактные тесты.
9. Проверка миграций.
10. E2E и security-наборы на предусмотренных этапах.

Для каждого шага необходимо сохранять понятный результат и диагностические сообщения.

### Правила CI

- Ошибка обязательной проверки блокирует слияние.
- Нельзя скрывать ошибку сборки ради успешного pipeline.
- Нельзя использовать незафиксированные зависимости для воспроизводимого CI.
- Секреты хранятся в защищённых настройках CI, а не в репозитории.
- Изменения миграций проверяются на тестовой базе.
- Нельзя запускать destructive-тесты против production.

Полный E2E-набор может запускаться отдельным pipeline, если он слишком медленный для каждого коммита. Но критические проверки доступа должны выполняться до релиза.

## 17. Definition of Done

Задача считается завершённой, когда выполнены применимые условия:

- Реализовано требуемое поведение.
- Учтены ошибки и граничные случаи.
- Проверены права доступа.
- Добавлены или обновлены соответствующие тесты.
- ESLint и TypeScript-проверки пройдены.
- Не нарушен API-контракт.
- Не появились новые утечки конфиденциальных данных.
- Документация обновлена при изменении контракта или архитектуры.
- Сборка проходит либо чётко указана известная блокирующая проблема.
- Проверки, которые не удалось выполнить, явно перечислены.

Не все пункты применимы к каждой задаче. Например, изменение текста кнопки не требует нагрузочного тестирования. Но изменение авторизации требует соответствующих тестов безопасности.

## 18. Правила для Cursor

Перед началом задачи:

1. Изучить требования и связанные документы.
2. Найти существующие тесты и соглашения.
3. Определить риски изменения.
4. Составить минимальный план реализации и проверок.
5. Для изменения прав доступа определить положительные и отрицательные сценарии.

Во время работы:

- Сначала исправлять первопричину, а не маскировать ошибку.
- Не отключать проверки ради успешного запуска.
- Не добавлять `skip` и `only` без обоснованной необходимости.
- Не подменять интеграционные тесты unit-тестами, если проверяется взаимодействие модулей.
- Не утверждать, что тест пройден, если он не запускался.
- Не использовать реальные клиентские данные.
- Не менять ожидаемое поведение теста только ради соответствия новому коду без подтверждения требований.

После реализации агент должен сообщить:

- Что изменено.
- Какие тесты добавлены или обновлены.
- Какие команды запускались.
- Какие проверки завершились успешно.
- Какие проверки завершились ошибкой.
- Какие проверки не запускались и почему.
- Какие риски остались.

## 19. Приоритеты тестирования для MVP

Предлагаемый порядок по риску:

**P0 — до допуска реальных клиентских данных**
- Изоляция организаций.
- Авторизация и отзыв доступа.
- Политика административного доступа к содержимому.
- Безопасная загрузка и выдача файлов.
- Контроль доступа при поиске и RAG.
- Защита секретов и конфиденциальных данных.
- Удаление документов и связанных данных.
- Базовая обработка ошибок AI-провайдера.

**P1 — до полноценного запуска MVP**
- Полные сценарии чата.
- Обработка фоновых задач.
- Потоковая генерация, если используется.
- Проверка юридических источников.
- Восстановление после временных ошибок.
- Критические E2E-сценарии.
- Проверка миграций и восстановления резервной копии.

**P2 — по мере развития продукта**
- Расширенный нагрузочный профиль.
- Большой evaluation-набор AI.
- Расширенная кроссбраузерная проверка.
- Дополнительные сценарии конкурентного редактирования.
- Автоматизированная оценка качества UX.

Приоритеты не означают, что проверки P2 можно игнорировать навсегда: они должны быть включены в план развития.

## 21. Итог

Стратегия качества строится на трёх уровнях:

1. **Корректность системы:** код, API, база данных, очереди и интеграции.
2. **Безопасность:** доступ к документам, организациям, поиску, AI-контексту и результатам.
3. **Качество юридического продукта:** источники, точность, полнота и проверяемость AI-ответов.

Успешная сборка — необходимое, но недостаточное условие готовности релиза. Для юридической AI-платформы критически важно подтвердить не только то, что система работает, но и то, что она корректно ограничивает доступ и не представляет непроверенные результаты как достоверные юридические факты.

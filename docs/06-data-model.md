# 06. Модель данных (Data Model)

**Проект:** AI-сервис для юридических команд  
**Версия:** 0.2.2  
**Статус:** PROPOSED для деталей схемы; острова **CONFIRMED** по журналу: PostgreSQL + Prisma (**D-008**), Client/Matter (**D-009**), статусы AIJob (**D-011**), лимиты файлов (**D-010/D-017**), `pgvector` (**D-018**), TTL/`admin_grant:approve` (**D-013/D-016**), удаление/бэкапы (**D-019/D-020**), цель хранения аудита 1 год (**D-021**). Сверять с `docs/decisions-log.md`.  
**Назначение:** определить основные сущности системы, связи между ними, правила хранения данных и ограничения целостности.

## 1. Цель документа

Документ описывает логическую модель данных MVP AI-сервиса для юристов.

Модель должна поддерживать:
- организации и пользователей;
- рабочие пространства;
- документы и их версии;
- чаты и сообщения;
- AI-задачи и результаты обработки;
- источники и цитаты;
- разграничение доступа;
- запросы на временный административный доступ к содержимому;
- аудит действий;
- жизненный цикл данных и удаление.

Логическая модель для MVP. **CONFIRMED (D-008):** PostgreSQL + Prisma. Конкретные типы колонок и физическая структура таблиц уточняются в миграциях Prisma; не менять стек без нового решения в `docs/decisions-log.md`.

## 2. Основные принципы

### 2.1. Изоляция организаций

Каждая сущность, содержащая данные организации, должна быть связана с `organization_id`.

Backend обязан проверять принадлежность объекта организации при каждом обращении. Нельзя полагаться только на идентификатор, полученный от клиента.

Запрос с подменённым идентификатором организации или объекта не должен раскрывать чужие данные.

### 2.2. Проверка доступа к содержимому

Наличие роли администратора организации не даёт автоматического права читать документы, чаты и дела.

Отдельный доступ администратора к содержимому возможен только по запросу с обязательным одобрением уполномоченного сотрудника.

Разрешение должно ограничиваться областью и сроком действия. Оно не должно автоматически предоставлять права на изменение, удаление, экспорт или передачу данных внешнему AI-провайдеру.

### 2.3. Минимизация данных

Система должна хранить только данные, необходимые для работы продукта, обеспечения безопасности и выполнения согласованных требований к аудиту.

Не допускается сохранять секреты авторизации, ключи доступа и полное содержимое документов в технических логах.

### 2.4. Явные связи

Связи между пользователями, организациями, рабочими пространствами, документами и чатами должны задаваться явно.

Нельзя определять права доступа только по названию объекта, его URL, принадлежности к папке на клиенте или факту наличия идентификатора в запросе.

## 3. Организации и пользователи

### 3.1. Organization

Представляет юридическую фирму или юридическую команду.

Предлагаемые поля:
- `id` — уникальный идентификатор;
- `name` — название организации;
- `status` — состояние организации;
- `created_at` — дата создания;
- `updated_at` — дата изменения.

Возможные состояния:
- `active`;
- `suspended`;
- `deleted` — только если будет утверждена соответствующая модель удаления.

Правила:
- данные разных организаций должны быть логически изолированы;
- при блокировке организации новые операции должны прекращаться в соответствии с утверждённой политикой;
- удаление организации должно учитывать связанные документы, чаты, результаты AI и требования к аудиту.

### 3.2. User

Представляет пользователя системы.

Предлагаемые поля:
- `id`;
- `email` или другой утверждённый идентификатор входа;
- `display_name`;
- `status`;
- `created_at`;
- `updated_at`.

Возможные состояния:
- `active`;
- `invited`;
- `suspended`;
- `deactivated`.

Способ аутентификации, обязательность email, поддержка SSO и правила восстановления доступа должны быть утверждены отдельно.

### 3.3. OrganizationMembership

Связывает пользователя с организацией.

Поля:
- `id`;
- `organization_id`;
- `user_id`;
- `role`;
- `status`;
- `created_at`;
- `updated_at`.

Предлагаемые роли:
- `owner`;
- `admin`;
- `member`.

Это предварительная схема. Окончательная ролевая модель должна быть согласована отдельно.

Ограничения:
- пользователь не может получить доступ к организации без активного членства;
- членство должно проверяться на сервере;
- удаление или блокировка членства должны прекращать доступ в соответствии с политикой сессий;
- роль `admin` не должна автоматически предоставлять доступ к содержимому.

## 4. Рабочие пространства

### 4.1. Workspace

Рабочее пространство объединяет документы, чаты и другие материалы, относящиеся к определённой задаче, клиенту или делу.

Поля:
- `id`;
- `organization_id`;
- `name`;
- `description`;
- `status`;
- `created_by`;
- `created_at`;
- `updated_at`.

Возможные состояния:
- `active`;
- `archived`;
- `deleted`.

Связь Workspace с сущностями `Client` и `Matter` в MVP **может быть необязательной** (**D-009**): рабочее пространство не обязано всегда представлять одно дело или одного клиента.

### 4.2. Client

**CONFIRMED (D-009).** Клиент организации (юридическое или физическое лицо, по которому ведётся работа).

Поля:
- `id`;
- `organization_id`;
- `name`;
- `status`;
- `created_by`;
- `created_at`;
- `updated_at`.

Правила:
- принадлежит организации; изоляция по `organization_id` обязательна;
- доступ к карточке клиента и связанным материалам проверяется сервером по ACL, а не только по членству в организации;
- связь с `Workspace` необязательна: клиент может существовать без workspace и наоборот.

### 4.3. Matter

**CONFIRMED (D-009).** Дело / юридический проект в рамках организации.

Поля:
- `id`;
- `organization_id`;
- `client_id` — необязательная ссылка на `Client`;
- `workspace_id` — необязательная ссылка на `Workspace` (**D-009**);
- `name` / `title`;
- `status`;
- `created_by`;
- `created_at`;
- `updated_at`.

Правила:
- принадлежит организации;
- связь с `Workspace` и `Client` может отсутствовать;
- права на содержимое дела не выводятся только из факта наличия идентификатора Matter.

### 4.4. WorkspaceMembership

Связывает пользователя с рабочим пространством.

Поля:
- `id`;
- `workspace_id`;
- `user_id`;
- `role`;
- `created_at`;
- `updated_at`.

Возможные права:
- просмотр;
- создание и редактирование содержимого;
- управление участниками;
- архивирование.

Точная матрица прав должна быть согласована отдельно.

Участие в организации не означает автоматического доступа ко всем рабочим пространствам и их содержимому.

## 5. Документы

### 5.1. Document

Представляет документ, загруженный пользователем или созданный системой.

Поля:
- `id`;
- `organization_id`;
- `workspace_id`;
- `title`;
- `status`;
- `created_by`;
- `created_at`;
- `updated_at`;
- `deleted_at` — если применяется мягкое удаление.

Возможные состояния:
- `uploaded`;
- `processing`;
- `ready`;
- `processing_failed`;
- `archived`;
- `deletion_pending`;
- `deleted`.

Переходы между состояниями должны быть ограничены и проверяться backend.

### 5.2. DocumentVersion

Представляет конкретную версию документа.

Поля:
- `id`;
- `document_id`;
- `version_number`;
- `storage_key`;
- `mime_type`;
- `file_size`;
- `checksum`;
- `uploaded_by`;
- `created_at`;
- `processing_status`.

Файл следует хранить в отдельном объектном хранилище или другом утверждённом файловом хранилище. В базе данных хранится ссылка или ключ, а не обязательно само содержимое файла.

Требования:
- доступ к файлу выдаётся только после серверной проверки прав;
- нельзя использовать публичные ссылки для конфиденциальных документов;
- временные ссылки на скачивание должны иметь ограниченный срок действия;
- контрольная сумма может применяться для проверки целостности;
- новая версия не должна незаметно подменять историю предыдущих версий.

### 5.3. DocumentExtraction

Хранит результат извлечения текста из документа.

Поля:
- `id`;
- `document_version_id`;
- `extraction_status`;
- `extracted_text_reference` или `extracted_text`;
- `language`;
- `created_at`;
- `updated_at`.

Физическое хранение извлечённого текста — в основной базе данных, отдельном хранилище или другом защищённом слое — остаётся открытым архитектурным решением.

Извлечённый текст должен иметь уровень защиты не ниже исходного документа.

## 6. Фрагменты документов и поиск

### 6.1. DocumentChunk

Представляет фрагмент документа, используемый для поиска и передачи контекста AI-модели.

Поля:
- `id`;
- `document_version_id`;
- `chunk_index`;
- `text_reference` или `text`;
- `page_number` — если применимо;
- `start_offset`;
- `end_offset`;
- `created_at`.

Фрагменты должны сохранять связь с исходной версией документа, чтобы система могла корректно показывать источники и цитаты.

### 6.2. Embedding

Представляет векторное представление фрагмента документа.

Предлагаемые поля:
- `id`;
- `chunk_id`;
- `embedding_model`;
- `embedding_version`;
- `vector_reference` или `vector`;
- `created_at`.

**Хранилище векторов для MVP — CONFIRMED (D-018):** PostgreSQL с расширением `pgvector`, совместно с полнотекстовым поиском PostgreSQL. Не выбирать отдельный внешний vector DB без нового решения в журнале.

**Остаётся OPEN:** конкретная модель embeddings, размерность вектора и физические типы колонок (уточняются при реализации Prisma/миграций и после оценки качества на русском).

Векторы и поисковые индексы также могут раскрывать конфиденциальную информацию через результаты поиска и должны быть защищены соответствующими ACL.

## 7. Чаты и сообщения

### 7.1. Conversation

Представляет диалог пользователя с AI или другой тип диалога, поддерживаемый продуктом.

Поля:
- `id`;
- `organization_id`;
- `workspace_id`;
- `created_by`;
- `title`;
- `conversation_type`;
- `status`;
- `created_at`;
- `updated_at`;
- `deleted_at`.

Возможные типы:
- `assistant`;
- `document_analysis`;
- `research`;
- `drafting`.

Это предварительный перечень.

До реализации необходимо утвердить, являются ли чаты личными, общими для рабочего пространства или поддерживают оба режима.

### 7.2. ConversationMembership

Если поддерживаются общие чаты, отдельная сущность связывает пользователей с диалогом.

Поля:
- `id`;
- `conversation_id`;
- `user_id`;
- `role`;
- `created_at`.

Для личного чата не следует автоматически создавать доступ всем участникам рабочего пространства.

### 7.3. Message

Представляет сообщение пользователя или AI.

Поля:
- `id`;
- `conversation_id`;
- `author_type`;
- `author_user_id` — если сообщение создано пользователем;
- `content_reference` или `content`;
- `status`;
- `created_at`;
- `updated_at`.

Возможные типы автора:
- `user`;
- `assistant`;
- `system`.

Содержимое сообщений является конфиденциальными данными и должно наследовать ограничения доступа диалога.

### 7.4. MessageAttachment

Связывает сообщение с документом или другим вложением.

Поля:
- `id`;
- `message_id`;
- `document_id` или `document_version_id`;
- `created_at`.

При чтении вложения необходимо повторно проверить права на сам документ. Доступ к сообщению не должен автоматически обходить ограничения документа.

## 8. AI-задачи и результаты

### 8.1. AIJob

Представляет асинхронную или синхронную задачу обработки AI.

Поля:
- `id`;
- `organization_id`;
- `requested_by`;
- `workspace_id`;
- `conversation_id`;
- `job_type`;
- `status`;
- `provider`;
- `model`;
- `created_at`;
- `started_at`;
- `completed_at`;
- `error_code`.

Возможные состояния (**CONFIRMED, D-011** — только этот набор):
- `queued`;
- `running`;
- `succeeded`;
- `failed`;
- `cancelled`;
- `timed_out`.

Не использовать `completed` или `retry_wait` как статусы AIJob. Повторы отражаются полями (`attempt_count`, `next_retry_at` и т.п.), успех — только `succeeded`. Поле `completed_at` — метка времени завершения, не статус.

Необходимо ограничивать количество одновременных задач, время выполнения и потребление ресурсов.

### 8.2. AIJobInput

Описывает входные данные задачи.

Поля:
- `id`;
- `ai_job_id`;
- `source_type`;
- `source_id`;
- `source_version_id`;
- `created_at`.

Входные данные могут включать сообщения, документы, фрагменты и другие разрешённые источники.

Перед запуском задачи необходимо проверить доступ к каждому источнику. Проверка прав только при создании задачи недостаточна: перед фактическим чтением и передачей данных модели права следует проверить повторно.

### 8.3. AIJobResult

Хранит результат обработки.

Поля:
- `id`;
- `ai_job_id`;
- `result_reference` или `result_content`;
- `created_at`;
- `status`.

Результат AI может содержать конфиденциальную информацию, даже если она отсутствует в явном виде в названии задачи.

Доступ к результату должен проверяться сервером. Сохранение результата не должно обходить ACL исходных данных.

### 8.4. AIProviderConfiguration

Описывает конфигурацию провайдера моделей.

Поля:
- `id`;
- `provider`;
- `model`;
- `status`;
- `configuration_reference`;
- `created_at`;
- `updated_at`.

Секреты и API-ключи не должны храниться в открытом виде в обычных полях этой сущности. Для них необходимо использовать защищённое хранилище секретов или утверждённый механизм управления секретами.

Архитектура должна позволять в будущем подключать собственные модели без изменения бизнес-модели документов и чатов.

## 9. Источники и цитаты

### 9.1. SourceReference

Представляет источник, использованный при формировании ответа AI.

Поля:
- `id`;
- `ai_job_id`;
- `source_type`;
- `source_id`;
- `source_version_id`;
- `chunk_id`;
- `page_number`;
- `start_offset`;
- `end_offset`.

Источник должен однозначно связываться с документом или внешним материалом, если он был разрешён политикой research.

### 9.2. Citation

Представляет ссылку или цитату, включённую в ответ.

Поля:
- `id`;
- `message_id`;
- `source_reference_id`;
- `quote_reference` или `quote_text`;
- `created_at`.

Цитаты должны позволять проверить происхождение ответа. При отображении цитаты сервер повторно проверяет право пользователя на исходный материал.

Если право на источник отозвано, интерфейс не должен продолжать раскрывать защищённый фрагмент только потому, что он был ранее включён в AI-ответ.

## 10. Запросы на административный доступ

Этот раздел реализует подтверждённые решения D-006 и D-007.

### 10.1. AdminContentAccessRequest

Представляет запрос администратора организации на чтение содержимого.

Поля:
- `id`;
- `organization_id`;
- `requested_by`;
- `purpose`;
- `scope_type`;
- `scope_reference`;
- `requested_expires_at`;
- `status`;
- `created_at`;
- `updated_at`.

Возможные состояния:
- `pending`;
- `approved`;
- `rejected`;
- `cancelled`;
- `expired`.

Поле `purpose` должно содержать краткое объяснение цели доступа и не должно использоваться для копирования текста документов или чатов.

### 10.2. AdminContentAccessDecision

Представляет решение уполномоченного сотрудника.

Поля:
- `id`;
- `request_id`;
- `decided_by`;
- `decision`;
- `reason`;
- `created_at`.

Возможные решения:
- `approved`;
- `rejected`.

Одобрение должно быть явным. Отсутствие ответа, ошибка сервиса или истечение времени рассмотрения не считаются согласием.

Заявитель не может одобрить собственный запрос.

### 10.3. AdminContentAccessGrant

Представляет фактически выданное разрешение.

Поля:
- `id`;
- `request_id`;
- `organization_id`;
- `granted_to`;
- `approved_by`;
- `scope_type`;
- `scope_reference`;
- `permissions`;
- `starts_at`;
- `expires_at`;
- `revoked_at`;
- `revoked_by`;
- `status`;
- `created_at`.

Разрешение создаётся только после одобрения.

По умолчанию `permissions` предоставляет только чтение в пределах согласованной области.

Срок действия должен быть ограничен. Продление и повторная выдача требуют утверждённой процедуры; бессрочное автоматическое продление запрещено.

### 10.4. Проверка разрешения

При каждом обращении к содержимому backend должен проверить:
1. Активность пользователя и членства в организации.
2. Полномочия пользователя на соответствующее действие.
3. Наличие одобрения.
4. Активность разрешения.
5. Отсутствие отзыва.
6. Неистёкший срок действия.
7. Соответствие запрашиваемого объекта области разрешения.
8. Соответствие действия предоставленным правам.

При невозможности подтвердить любой из пунктов доступ запрещается.

Запрос разрешения сам по себе не должен влиять на результат авторизации.

## 11. Аудит

### 11.1. AuditEvent

Представляет запись о событии безопасности или значимом действии.

Поля:
- `id`;
- `event_type`;
- `actor_user_id`;
- `organization_id`;
- `target_type`;
- `target_id`;
- `request_id`;
- `correlation_id`;
- `result`;
- `reason_code`;
- `metadata`;
- `created_at`.

Для административного доступа необходимо фиксировать:
- запрос;
- одобрение;
- отказ;
- выдачу разрешения;
- использование разрешения;
- отказ в доступе;
- истечение срока;
- отзыв разрешения.

Аудит должен позволять восстановить цепочку событий и определить, кто, когда, по какой причине и к какой области получил доступ.

### 11.2. Ограничения аудита

Запрещено помещать в журнал:
- полный текст документов;
- текст сообщений;
- prompts и ответы AI;
- извлечённые фрагменты;
- API-ключи и токены;
- секреты аутентификации.

Журнал должен быть защищён от изменения и удаления обычным администратором организации. Просмотр журнала не должен автоматически предоставлять доступ к содержимому документов.

Если обязательное событие аудита не удалось надёжно сохранить, выдача разрешения и чувствительная операция должны завершиться отказом.

**Срок хранения аудита — техническая цель CONFIRMED (D-021): 1 год**, с обязательной проверкой соответствия юридическим и договорным требованиям до production. Аудит не должен содержать текст документов, полные промпты/ответы или секреты.

**Остаётся OPEN:** механизм неизменяемого хранения (WORM/append-only и т.п.), полномочия на просмотр и экспорт журнала аудита, окончательная юридическая валидация срока 1 год.

## 12. Жизненный цикл данных

Для каждой категории данных необходимо определить:
- место хранения;
- уровень конфиденциальности;
- срок хранения;
- правила архивирования;
- правила удаления;
- влияние удаления на связанные сущности;
- порядок очистки резервных копий;
- обработку данных во внешних AI-провайдерах.

Удаление исходного документа должно запускать обработку связанных данных:
- версий документа;
- извлечённого текста;
- фрагментов;
- embeddings;
- индексов поиска;
- кэшированных результатов;
- ссылок на источники;
- результатов AI, содержащих данные документа.

Удаление не должно автоматически уничтожать записи аудита, если их хранение требуется утверждённой политикой или применимыми обязательствами. При этом аудит не должен содержать копию удаляемого содержимого.

Конкретная политика хранения и удаления должна быть согласована отдельно.

## 13. Ограничения целостности

На уровне базы данных или сервисного слоя необходимо обеспечить:
- уникальность идентификаторов;
- целостность внешних ключей;
- невозможность создания членства без существующих пользователя и организации;
- невозможность создания версии без исходного документа;
- невозможность создания фрагмента без версии документа;
- невозможность создания сообщения без существующего диалога;
- невозможность создания решения без соответствующего запроса;
- невозможность выдачи разрешения без одобренного запроса;
- невозможность использования отозванного или истёкшего разрешения;
- согласованность организации между связанными объектами.

Где возможно, ограничения следует реализовывать средствами базы данных. Проверки бизнес-правил должны дополнительно выполняться backend.

## 14. Индексы и производительность

Предварительно необходимы индексы по:
- `organization_id`;
- `workspace_id`;
- `user_id`;
- `document_id`;
- `conversation_id`;
- `created_at`;
- `status`;
- `request_id`;
- `granted_to`;
- `expires_at`.

Для журналов аудита следует предусмотреть эффективный поиск по организации, типу события, пользователю, целевому объекту и временному диапазону.

Окончательный набор индексов должен зависеть от объёма данных и результатов нагрузочного тестирования на PostgreSQL (**D-008**); для векторного поиска — `pgvector` (**D-018**).

## 15. Обязательные тесты

1. Пользователь одной организации не может получить содержимое другой организации.
2. Администратор без отдельного разрешения не может читать документы и чаты.
3. Запрос со статусом `pending` не предоставляет доступ.
4. Нельзя одобрить собственный запрос.
5. Пользователь без полномочий согласующего не может одобрить запрос.
6. Разрешение не распространяется за пределы согласованной области.
7. Истёкшее или отозванное разрешение не позволяет читать данные.
8. Проверка прав действует для API, скачивания, поиска, цитат, экспорта и фоновых AI-задач.
9. Отсутствие разрешения на исходный документ не позволяет получить его содержимое через AI-ответ или цитату.
10. Ошибка записи обязательного события аудита блокирует выдачу разрешения.
11. В журнал аудита не попадает конфиденциальное содержимое.
12. Повторная обработка запроса не создаёт дублирующее активное разрешение.
13. Удаление документа обрабатывает связанные извлечённые тексты, фрагменты, embeddings и индексы поиска.

## 16. Открытые решения

Подтверждено журналом (**D-008–D-022**), в т.ч.: PostgreSQL + Prisma; `Client`/`Matter` (связь с Workspace необязательна); статусы AIJob по D-011; лимиты файлов D-010/D-017; хранилище векторов `pgvector` (D-018); TTL admin grant ≤ 60 мин и `admin_grant:approve` (D-013/D-016); удаление ≤ 24 ч / бэкапы 35 дней (D-019/D-020); техническая цель хранения аудита 1 год (D-021).

Дополнительно согласовать (не CONFIRMED):
- детальную структуру ролей и ACL (многие ячейки в `07` OPEN);
- личные и общие чаты;
- физическое хранение файлов и извлечённого текста (продукт object storage);
- модель embeddings (не путать с уже подтверждённым `pgvector`);
- необходимость уведомления владельца содержимого (O-010);
- права на просмотр/экспорт аудита; юридическую валидацию срока 1 год;
- политику аварийного доступа (не в MVP, D-016);
- обработку и удаление данных у внешних AI-провайдеров (O-002);
- сущность Draft/DraftVersion и optional FK Document/Conversation → Client/Matter — без нового CONFIRMED не считать утверждёнными.

## 17. Критерии готовности

Модель данных считается готовой к реализации, когда:
- основные сущности и связи согласованы;
- роли и правила доступа определены;
- политика административного доступа реализуема без обходных путей;
- физическое хранение конфиденциальных данных выбрано;
- жизненный цикл и удаление данных определены;
- требования к аудиту согласованы;
- подготовлены миграции и тесты целостности;
- архитектурные решения зафиксированы в журнале решений.

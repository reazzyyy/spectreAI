# MVP — сквозные сценарии Retrieval Engine

**Статус:** PROPOSED  
**Версия:** 0.1

## 1. Цель

Проверить минимальную архитектуру на пяти юридических сценариях. Сценарии упорядочены по возрастанию сложности; успешная реализация одного не означает готовность следующих.

## 2. Сценарий A — точный поиск нормы

**Запрос:** «Найди статью 450 ГК РФ в редакции на указанную дату».

Поток:
1. Распознать реквизиты акта и положения.
2. Нормализовать название акта и номер статьи.
3. Найти соответствующее положение.
4. Определить редакцию, действовавшую на дату запроса.
5. Проверить источник и полноту текста.
6. Вернуть текст и реквизиты источника.

**Не требуется:** embeddings, vector search, RRF, reranker.

Критерии:
- корректно различаются акты с похожими сокращениями;
- возвращается правильное положение;
- редакция соответствует дате;
- результат содержит происхождение и locator;
- неоднозначность или отсутствие данных не маскируются выдуманным ответом.

## 3. Сценарий B — поиск нормы по описанию ситуации

**Запрос:** «Какие нормы регулируют увольнение за неоднократное неисполнение трудовых обязанностей?»

Поток:
1. Определить предмет и тип поисковой задачи.
2. Извлечь поисковые концепты, не подменяя ими юридические факты.
3. Выполнить lexical и vector retrieval.
4. Объединить результаты (RRF — кандидат).
5. Применить серверные ограничения доступа и временные фильтры.
6. Сформировать контекст из источников с provenance.
7. Сгенерировать ответ с привязкой утверждений к источникам.
8. Проверить наличие и соответствие ссылок.

Критерии:
- находятся нормы при перефразировании запроса;
- существенные источники не теряются;
- устаревшие редакции не выдаются как действующие;
- модель отделяет норму, вывод и неизвестные факты;
- при нехватке обстоятельств задаёт уточняющий вопрос.

## 4. Сценарий C — судебная практика по похожим обстоятельствам

**Запрос:** «Найди судебную практику по расторжению договора поставки из-за систематического нарушения сроков».

Дополнительно нужны метаданные судебного акта, суд, дата, категория спора, результат и локаторы фрагментов. Поиск должен сравнивать обстоятельства, а не только совпадение слов.

Не входит в первый нормативный вертикальный срез; используется как проверка расширяемости модели.

## 5. Сценарий D — проверка договора

Пользователь загружает договор и просит выявить юридические риски.

Необходимо связать конкретный пункт договора с применимыми нормами и объяснить тип замечания: возможное противоречие, риск, диспозитивное регулирование или недостаточность данных. Отличие от диспозитивной нормы само по себе не доказывает нарушение.

## 6. Сценарий E — комплексный анализ на разные даты

Нужно отдельно оценить:
- положение на дату заключения договора;
- положение на текущую дату;
- применимые переходные положения;
- судебную практику с учётом дат и обстоятельств.

Система не должна смешивать временные срезы и представлять предположение как установленный факт.

## 7. Приоритет реализации

1. Сценарий A — точный поиск нормы.
2. Сценарий B — гибридный поиск нормы.
3. Проверка ingestion и temporal model на реальном нормативном материале, использование которого допустимо.
4. Только после этого — расширение на судебную практику и пользовательские документы.

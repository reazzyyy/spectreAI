# Temporal Legal Retrieval — временная применимость

**Статус:** PROPOSED / TO_VALIDATE  
**Версия:** 0.2

## 1. Проблема

Для юридического ответа недостаточно найти текст нормы. Необходимо определить, какой текст действовал в юридически значимый момент и какие переходные правила применяются.

## 2. Разные временные измерения

Не смешивать:

- дату принятия акта;
- дату официального опубликования;
- дату вступления акта в силу;
- дату вступления в силу конкретного положения или изменения;
- дату прекращения действия положения;
- дату, когда источник был получен системой;
- дату, когда система записала или переобработала данные.

## 3. Почему период на уровне всего акта недостаточен

Поправочный закон может менять разные положения с разными датами вступления в силу. Переходные положения могут устанавливать специальные правила. Поэтому один `validFrom/validTo` на весь нормативный акт не гарантирует корректность исторического поиска.

Предварительное направление — хранить временные сведения на уровне изменяемого положения/версии текста и сохранять связь с актом, который внёс изменение. Но окончательная модель должна быть проверена на реальных примерах.

## 4. Вопросы, требующие юридической проработки

- частичное вступление поправок в силу;
- переходные положения;
- обратная сила;
- приостановление и возобновление действия;
- признание нормы утратившей силу;
- перенумерация и структурная перестройка;
- различие официального текста и консолидированной редакции;
- применение нормы к длящимся отношениям и событиям, начавшимся ранее.

## 5. Требования к поиску

Запрос должен иметь явный temporal context:
- дата, указанная пользователем;
- либо текущая дата, если это явно соответствует смыслу запроса;
- либо уточнение, если юридически значимая дата неизвестна.

Система должна сохранять, какую дату она использовала, и не подменять её датой загрузки документа.

## 6. Приоритет

Временная корректность — обязательное условие юридического retrieval, а не необязательная оптимизация. Однако точная схема и правила вычисления применимости остаются открытыми до юридической валидации.


## 7. Проверенная на примерах логическая модель

Три компонента разделяются по ответственности:

1. `LegalProvisionTextVersion` — история текста и период юридического действия конкретной версии.
2. `AmendmentOperation` — связь изменяющего акта с конкретным структурным фрагментом и типом изменения.
3. `ApplicabilityRule` — правила распространения нормы на правоотношения/события, включая переходные положения.

Это логические компоненты, а не утверждённый набор Prisma-моделей. Для MVP не требуется создавать отдельную таблицу для каждого компонента, если текущая схема может надёжно выразить связи и обеспечить аудит.

## 8. Контракт ApplicabilityRule для MVP

Минимальная логическая структура:

```ts
type ApplicabilityRule = {
  id: string;
  targetProvisionId: string;
  targetVersionId?: string;

  sourceActId: string;
  sourceLocator: string;

  // Когда соответствующее положение/изменение вступило в силу.
  effectiveFrom?: Date;
  effectiveTo?: Date;

  // Интервал правоотношений или событий, охватываемых правилом.
  relationPeriod?: {
    from?: Date;
    to?: Date;
    fromInclusive?: boolean;
    toInclusive?: boolean;
  };

  // Когда должны оцениваться условия правила.
  conditionAsOf?: Date;

  conditions: ApplicabilityCondition[];
  conditionMode: "ALL";

  status: "structured" | "manual_review" | "insufficient_source";
};
```

Условие MVP:

```ts
type ApplicabilityCondition =
  | {
      type: "date_comparison";
      fact: "contract_conclusion_date" | "event_date" | string;
      operator: "before" | "after" | "on_or_before" | "on_or_after";
      date: Date;
    }
  | {
      type: "fact_state";
      fact: string;
      asOf: Date;
      expected: "true" | "false";
    }
  | {
      type: "event_existence";
      eventType: string;
      asOf: Date;
      expected: "exists" | "does_not_exist";
    };
```

Это ограниченный формат для хранения и проверки простых условий. Он не является универсальным языком права и не должен автоматически исполнять произвольный текст закона.

### Неизвестные факты — отдельное состояние

При оценке условия факт должен иметь трёхзначное состояние:
- `true` — факт подтверждён;
- `false` — установлено обратное;
- `unknown` — сведений недостаточно или доказательства противоречивы.

`unknown` нельзя приравнивать к `false`. Если хотя бы один обязательный факт неизвестен, результат проверки правила должен быть `insufficient_facts` или `manual_review`, а не «условие не выполнено».

Рекомендуемый результат оценки:

```ts
type ApplicabilityEvaluation =
  | { result: "applicable"; satisfiedConditions: string[] }
  | { result: "not_applicable"; failedConditions: string[] }
  | { result: "insufficient_facts"; unknownConditions: string[] }
  | { result: "manual_review"; reason: string };
```

### Ограничения MVP

- Поддерживать ограниченный набор типов условий и логическое `ALL` (AND).
- Не реализовывать произвольные вложенные `AND/OR/NOT`, выражения, скрипты и универсальный Rule Engine.
- Если закон содержит сложное оценочное условие, неоднозначную формулировку или условие, которое нельзя надёжно структурировать, сохранять текст, locator и источник, ставить `manual_review`.
- Не выводить юридические факты из отсутствия данных.
- Сохранять исходный текст условия рядом со структурированным представлением.
- Все автоматические выводы должны быть трассируемы до конкретного источника и его фрагмента.

## 9. Временные координаты запроса

Запрос на правовой анализ должен различать:

1. `assessmentDate` — дата, на которую пользователь просит оценить правовое регулирование.
2. `legalFactDate` / даты фактов — дата заключения договора, события, исполнения обязательства и другие юридически значимые даты.
3. `conditionAsOf` — контрольная дата, на которую переходное положение требует проверить состояние факта.
4. `effectiveFrom/effectiveTo` — период юридического действия текста/изменения.
5. `relationPeriod` — период правоотношений или событий, на которые распространяется специальное правило.
6. `recordedAt` — когда система записала соответствующую информацию.

Не все эти даты обязательны для каждого запроса. Система должна запрашивать недостающую дату только тогда, когда без неё нельзя надёжно определить применимую норму. Не подменять одну временную координату другой.

## 10. Обязательная осторожность

Даже если условия `ApplicabilityRule` выполнены, это ещё не гарантирует итоговый правовой вывод. Могут иметь значение другие нормы, специальные исключения, фактические обстоятельства, судебное толкование и редакция акта на дату оценки.

Результат temporal retrieval должен показывать:
- применённую редакцию;
- временные основания;
- переходное правило и его источник;
- какие факты подтверждены;
- какие факты неизвестны;
- ограничения или необходимость юридической проверки.

## 11. Статус проверки

Логическая модель проверена на трёх показательных типах случаев:
- разные даты вступления в силу отдельных положений и отдельная дата применения;
- распространение положения на ранее возникшие правоотношения с ограниченным периодом;
- переходное правило, зависящее от нескольких юридических фактов на контрольную дату.

Это не доказывает полноту модели для всего российского законодательства. Статус остаётся `PROPOSED / TO_VALIDATE`; физическая схема БД и автоматическая интерпретация произвольных условий не утверждены.

# Retrieval Engine — обзор

**Статус:** PROPOSED  
**Версия:** 0.1

## 1. Назначение

Retrieval Engine предоставляет AI-функциям проекта проверяемые фрагменты нормативных актов, судебных актов и пользовательских документов с сохранением происхождения, контекста доступа и временной применимости.

Цель MVP — не универсальная поисковая платформа, а минимальная система для сквозных юридических сценариев.

## 2. Границы MVP

### Входит в первый вертикальный срез

- точный поиск нормативного акта и структурного положения по реквизитам;
- поиск нормативных положений по описанию юридической ситуации;
- структурное извлечение статей и частей;
- лексический и векторный поиск;
- объединение результатов гибридного поиска;
- фильтрация по доступу и временной применимости;
- сбор контекста и сохранение ссылок на первоисточники;
- тестирование качества retrieval отдельно от качества генерации.

### Не входит в обязательный первый срез

- отдельная graph database;
- универсальная юридическая онтология;
- multi-agent orchestration;
- обязательный Cross-Encoder;
- semantic chunking;
- сложный OCR для всех типов документов;
- полноценная blue-green инфраструктура индексов;
- отдельные микросервисы на каждый поисковый компонент.

Эти возможности могут появиться только при подтверждённой потребности.

## 3. Типы источников

Логически выделяются три области знаний:

1. `legal_norms` — нормативные акты;
2. `court_practice` — судебные акты;
3. `user_documents` — документы организации, клиента, дела или workspace.

Это логические категории и политики обработки, а не требование создавать отдельные базы данных или микросервисы.

## 4. Базовые потоки

### Точный поиск

`Query parsing → exact lookup → temporal validation → source response`

Для точного поиска по реквизитам не требуется запускать embeddings, RRF или reranking.

### Семантический / гибридный поиск

`Query understanding → lexical search + vector search → fusion → applicability/access filters → context building → answer generation`

Фактический порядок фильтров должен учитывать безопасность: ограничения доступа применяются на стороне сервера и БД до передачи фрагментов в модель. Временная применимость проверяется до формирования юридического контекста.

## 5. Архитектурные принципы

- **Provenance first:** каждый фрагмент должен иметь однозначную связь с источником и версией.
- **Temporal correctness:** поиск на дату не должен смешивать редакции.
- **Access isolation:** ACL нельзя принимать из пользовательского запроса как доверенный параметр.
- **Retrieval != legal reasoning:** ранжирование не доказывает юридическую применимость.
- **Explainability:** существенные выводы должны быть привязаны к проверяемым источникам.
- **Incremental complexity:** усложнять систему только после benchmark или появления обязательного сценария.
- **Replaceable providers:** embedding/OCR/LLM провайдеры подключаются через адаптеры, но универсальная платформа провайдеров не является целью этого документа.

## 6. Внешние зависимости и ограничения

- PostgreSQL и pgvector соответствуют ранее выбранному направлению проекта; точная конфигурация индексов требует benchmark.
- Конкретная embedding-модель остаётся открытой до тестирования.
- Выбор PostgreSQL FTS или ParadeDB BM25 требует сравнения качества, эксплуатации и лицензии.
- До закрытия compliance gates реальные клиентские данные не передаются внешним AI API.

# Retrieval Pipeline — точный и гибридный поиск

**Статус:** PROPOSED  
**Версия:** 0.1

## 1. Два разных режима

### Exact lookup

Для запросов с однозначными реквизитами:
`parse identifiers → structured lookup → temporal check → source response`

Exact lookup не должен зависеть от embedding-модели или качества векторного ранжирования.

### Hybrid retrieval

Для запросов, сформулированных естественным языком:
`query analysis → lexical retrieval + vector retrieval → fusion → filtering → context assembly`

## 2. Lexical retrieval

Кандидат для первого прототипа — PostgreSQL Full Text Search. ParadeDB BM25 рассматривается как альтернатива для benchmark.

Сравнивать нужно:
- качество на юридических запросах;
- поддержку русского языка и морфологии;
- фильтрацию и сортировку;
- эксплуатационную сложность;
- совместимость и лицензионные условия.

Не принимать решение только по синтетическим общим бенчмаркам.

## 3. Vector retrieval

pgvector — выбранное направление проекта. Конкретная embedding-модель, размерность, distance metric и параметры индекса должны быть проверены на тестовом корпусе.

Запрос и индексируемые тексты должны использовать совместимую модель, revision, инструкции и preprocessing.

## 4. Fusion

RRF — кандидат для объединения рангов lexical и vector retrieval. Он не делает результаты юридически применимыми и не заменяет temporal filtering.

На первом этапе достаточно двух источников retrieval. Дополнительные коллекции и веса добавлять только при подтверждённой необходимости.

## 5. Фильтры

- серверный ACL / tenant isolation;
- тип источника и область знаний;
- юрисдикция и предметная область, если известны;
- дата, на которую требуется правовая оценка;
- состояние и качество источника.

Фильтрация доступа должна выполняться до передачи контента в LLM. Нельзя сначала собрать чужие фрагменты, а затем просить модель не использовать их.

## 6. Context Builder

Минимальные обязанности:
- дедупликация совпадающих фрагментов;
- ограничение количества и объёма контекста;
- расширение дочернего фрагмента родительским контекстом при необходимости;
- сохранение точного source locator;
- сохранение версии и временных метаданных;
- исключение фрагментов, недоступных пользователю.

Parent expansion должен быть ограниченным и учитывать token budget.

## 7. Reranking

Cross-Encoder не обязателен до benchmark. Его добавление оправдано, если измерения показывают, что после fusion релевантные источники часто остаются ниже нерелевантных.

Reranker оценивает соответствие запросу, но не устанавливает юридическую силу, применимость или авторитетность источника.

## 8. Citation validation

Минимально проверять:
- что каждый source ID существует;
- что цитируемый фрагмент принадлежит указанному источнику и версии;
- что locator ведёт к правильному месту;
- что дата применимости соответствует задаче;
- что текст цитаты не был незаметно изменён.

Проверка существования ссылки не доказывает, что утверждение модели логически следует из источника. Claim-to-evidence / entailment evaluation — отдельный этап качества.

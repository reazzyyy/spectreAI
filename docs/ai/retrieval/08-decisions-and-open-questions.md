# Retrieval — решения, гипотезы и открытые вопросы

**Статус:** PROPOSED  
**Версия:** 0.2

## 1. Подтверждённый контекст проекта

Ниже приведён контекст, известный из ранее согласованных обсуждений. Сверять только с актуальным `docs/decisions-log.md`; этот файл не является источником официального статуса D/O. Сверка v0.2: `INTEGRATION-NOTES.md`.

- PostgreSQL выбран для основной БД.
- pgvector выбран как направление для векторного поиска (ранее отмечено D-018).
- Для MVP используется SyntheticAIProvider до закрытия применимых compliance gates.
- Реальные клиентские документы нельзя отправлять во внешние AI API до закрытия соответствующих требований.
- Для пользовательских данных обязательны серверная авторизация, изоляция tenant/workspace и RLS в MVP.

## 2. Предварительные технические гипотезы

| Область | Гипотеза | Статус |
|---|---|---|
| Lexical search | Сравнить PostgreSQL FTS и ParadeDB BM25 | TO_VALIDATE |

| Vector index | HNSW; exact search как baseline на малых корпусах | TO_VALIDATE |

| Graph DB | Не включать в MVP | DEFERRED |
| Semantic chunking | Не включать в MVP | DEFERRED |
| Blue-green index deployment | Отложить до доказанной потребности | DEFERRED |

### Temporal model
- Логическая модель `LegalProvisionTextVersion` + `AmendmentOperation` + `ApplicabilityRule` — PROPOSED / TO_VALIDATE; проверена на трёх показательных примерах, но не утверждена как полное покрытие российского законодательства.
- Для `ApplicabilityRule` предложен ограниченный контракт с датами, scope, источником, контрольной датой и условиями — PROPOSED.
- Трёхзначная оценка фактов (`true` / `false` / `unknown`) обязательна для безопасной обработки недостатка данных — PROPOSED.
- Универсальный Rule Engine не входит в MVP; сложные или оценочные условия переводятся в manual review — PROPOSED.

Этот документ не меняет статусы D/O/H, не назначает новые официальные идентификаторы и не закрывает вопросы. Когда вопрос требует решения владельца, он должен быть перенесён в действующий процесс управления решениями проекта после проверки отсутствия дубликата.

## 5. Следующий этап

В версии 0.2 временная модель получила предварительный логический контракт и три regression-кейса. Следующие действия:
1. сверить пакет с актуальными каноническими документами и `decisions-log.md`;
2. проверить юридические формулировки и источники кейсов с юристом/экспертом;
3. согласовать минимальный parser output для структурных locator и temporal metadata;
4. реализовать/смоделировать exact lookup с временным контекстом;
5. расширять temporal test set по мере появления новых типов переходных положений;
6. только после этого переходить к benchmark FTS/vector retrieval.

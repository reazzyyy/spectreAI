# Retrieval Evaluation — тестирование качества

**Статус:** PROPOSED  
**Версия:** 0.2

## 1. Цель

Измерять отдельно:
1. качество извлечения источников;
2. корректность временной и access-фильтрации;
3. качество ответа и привязки утверждений к источникам.

Нельзя считать хороший ответ доказательством хорошего retrieval без проверки исходной выдачи.

## 2. Начальный тестовый набор

Предлагаемый стартовый объём:
- 30 exact lookup запросов;
- 50 запросов на нормы по описанию ситуации;
- 50 запросов на судебную практику — после подключения корпуса;
- 20 синтетических/разрешённых договоров с экспертной разметкой — после реализации document flow;
- 10 комплексных временных кейсов.
- Отдельный минимальный temporal regression set из трёх кейсов, описанных в `09-temporal-evaluation-cases.md`.

Это начальный диагностический набор, а не статистически достаточная выборка для доказательства юридической надёжности.

## 3. Разметка

Для каждого запроса хранить:
- текст запроса;
- temporal context;
- ожидаемые релевантные источники;
- обязательные источники, если есть;
- допустимые дополнительные источники;
- нерелевантные/опасные результаты;
- ожидаемые locators;
- экспертное обоснование;
- версию корпуса и разметки.

## 4. Метрики retrieval

- Recall@k — доля ожидаемых источников, найденных в top-k;
- Precision@k — доля релевантных результатов в top-k;
- MRR — позиция первого релевантного результата;
- nDCG@k — качество ранжирования с градациями релевантности.

## 5. Метрики юридической корректности

- Temporal Accuracy — правильность выбора версии на заданную дату;
- Source/Locator Accuracy — соответствие ссылки источнику и месту;
- Citation Support — подтверждает ли источник конкретное утверждение;
- Unsupported Claim Rate — доля существенных неподтверждённых утверждений;
- Abstention Quality — корректно ли система сообщает о недостатке данных;
- ACL Leakage — количество случаев выдачи недоступного контента; целевое значение — ноль.

Для анализа договоров дополнительно:
- Risk Detection Recall;
- False Positive Rate;
- экспертная оценка обоснованности и полезности рекомендации.

## 6. Benchmark-план

Сравнить:
- PostgreSQL FTS и ParadeDB BM25;
- несколько подходящих размеров/версий embedding-модели;
- exact search и vector search как baseline;
- lexical + vector + RRF;
- RRF с Cross-Encoder только как дополнительный эксперимент.

Менять по одной группе факторов, фиксировать корпус, запросы, версии моделей и конфигурации.

## 7. Критерии выхода

До начала эксперимента установить пороги для конкретного сценария и класса ошибок. Не выбирать пороги задним числом под понравившийся результат.

Критические ошибки (утечка ACL, неверная редакция, ложный locator) должны анализироваться отдельно от усреднённых метрик.


## 8. Temporal regression tests — обязательные проверки

Для каждого кейса проверять не только выбранную редакцию, но и:
- дату вступления в силу;
- период правоотношений/событий, охватываемых переходным правилом;
- контрольную дату условий;
- источник и точный locator переходного положения;
- состояние фактов `true` / `false` / `unknown`;
- корректный отказ от автоматического вывода при недостатке фактов.

Нельзя считать тест пройденным, если система выбрала правильную редакцию случайно, но не может объяснить временное основание и применённое переходное правило.

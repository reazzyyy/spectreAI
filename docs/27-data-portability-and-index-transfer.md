# 27. Data Portability and Index Transfer

**Статус: PROPOSED.** Стратегия переноса разрешённого корпуса и подготовленного RAG-индекса между development, staging и production. Не заменяет канонические документы по хранению файлов, RAG, правовым источникам, удалению и deployment.

**Связанные документы:** `02-architecture.md`, `06-data-model.md`, `08-data-lifecycle-and-deletion.md`, `13-file-storage-and-document-processing.md`, `17-rag-and-knowledge-retrieval.md`, `18-legal-research-and-external-sources.md`, `23-deployment-and-infrastructure.md`, `28-index-build-manifest-and-reproducibility.md`, `29-corpus-export-import-runbook.md`, `30-portability-integrity-and-search-validation.md`, `security/data-classification.md`, `security/data-flow-and-data-inventory.md`.

## 1. Цель

Система должна позволять подготовить разрешённый корпус в одном окружении, экспортировать согласованный snapshot и восстановить его в другом без обязательного повторного парсинга и повторной генерации embeddings.

Сценарий:
1. Получить разрешённые источники.
2. Сохранить исходники, версии, извлечённый текст, структуру, chunks, embeddings и metadata.
3. Зафиксировать версии pipeline и checksums.
4. Создать согласованный snapshot.
5. Экспортировать БД и связанные бинарные объекты.
6. Проверить пакет.
7. Восстановить в целевом окружении.
8. Применить актуальный deletion journal.
9. Проверить целостность и retrieval quality.
10. Активировать корпус только после успешной проверки.

Переносимость означает сохранение логического содержимого, происхождения, связей, версий, embeddings и конфигурации обработки. Она не гарантирует побайтовую идентичность физических файлов PostgreSQL или одинаковую производительность на разном оборудовании.

## 2. Область действия

### 2.1 Входит в corpus snapshot
- идентификаторы и metadata источников;
- документы и редакции;
- даты публикации, получения и действия редакции, если достоверно известны;
- структурное дерево документа;
- extracted и normalized text;
- chunks и parent/child relationships;
- embeddings и сведения о модели;
- metadata для поиска и фильтрации;
- ссылки на оригинальные объекты;
- checksums, manifest и validation report.

### 2.2 Не включается по умолчанию
- пользовательские документы, договоры, переписка, OCR и прочий D3;
- чаты, промпты, ответы AI, workspace content;
- секреты D4, ключи, пароли, токены и `.env`;
- платные/лицензированные источники, если право на хранение и экспорт не подтверждено;
- логи и временные очереди задач, не относящиеся к snapshot.

Перенос публичного правового корпуса не является разрешением на экспорт любых данных приложения.

## 3. Обязательные ограничения проекта

- **D-014:** production-инфраструктура, основная БД и файловое хранилище размещаются в РФ. Учитывать staging, backups, logs, indexes, temporary exports и все копии.
- **D-018:** MVP использует PostgreSQL + `pgvector` и PostgreSQL full-text search.
- **D-019:** подтверждённо удалённые данные сразу становятся недоступны; очистка основной системы и производных данных — в пределах 24 часов.
- **D-020:** резервные копии хранятся 35 дней; после restore повторно применяется deletion journal.
- **D-022:** RPO ≤ 24 часа и RTO ≤ 8 часов — цели, подтверждаемые restore tests.
- **D-012/D-015/O-002:** до закрытия O-002 — только SyntheticAIProvider и synthetic data для внешних AI-вызовов. Перенос индекса не разрешает внешнюю передачу реальных документов или embeddings.
- **O-006:** разрешённые правовые источники, лицензии и способы получения остаются OPEN. Доступность URL или файла не доказывает право на скачивание, хранение, индексацию, экспорт или предоставление пользователям.
- **O-005:** сроки активного хранения контента требуют отдельной политики.

Классифицировать данные только по шкале D0–D4. Embeddings и производные от D3 защищать как минимум на уровне D3; не считать их автоматически анонимными.

## 4. Логическая архитектура snapshot

Перенос включает две согласованные части:

1. **Database snapshot:** реляционные данные, структура, chunks, embeddings, metadata и определения индексов.
2. **Object snapshot:** оригинальные бинарные объекты и иные файлы, на которые ссылается БД.

Обе части связываются единым `exportId` и manifest. Нельзя объявлять перенос завершённым, если восстановлена только БД или только object storage.

```text
Source environment
  PostgreSQL snapshot ----+
  Object snapshot --------+--> export package + manifest + checksums
                                      |
                                secure transfer
                                      |
                                      v
Target environment
  restore objects -> restore database -> integrity checks
                                      |
                              rebuild physical indexes
                                      |
                              retrieval regression tests
                                      |
                              activate imported corpus
```

## 5. Данные и физические индексы — не одно и то же

Различать:
- **данные:** текст, chunks, vectors, metadata, provenance;
- **логическую конфигурацию:** FTS configuration, embedding model, dimensions, distance metric, filters, ranking settings;
- **физические индексы:** B-tree, GIN, HNSW, IVFFlat и другие структуры PostgreSQL.

Данные и логическая конфигурация обязательны для переноса. Физические индексы могут быть восстановлены из backup или перестроены на target, если версии PostgreSQL/pgvector совместимы. Перестроение физического индекса не требует повторной генерации embeddings.

После перестроения нужно повторить retrieval regression tests. ANN top-K может немного отличаться при изменении версий движка, параметров индекса или search settings; абсолютное совпадение нельзя обещать без проверки.

## 6. Согласованность snapshot

Нельзя экспортировать metadata, chunks и файлы в разные моменты без фиксации соответствия.

Рекомендуемый порядок:
1. Создать `exportId`.
2. Зафиксировать scope: источники, документы и версии.
3. Зафиксировать snapshot boundary: timestamp, ingestion watermark или иной механизм.
4. Обеспечить согласованность данных на время экспорта (snapshot transaction, контролируемая пауза публикации новых версий или эквивалент).
5. Зафиксировать список объектов и checksums.
6. Экспортировать БД и связанные объекты.
7. Создать manifest.
8. Выполнить pre-transfer validation.
9. Возобновить ingestion, если он приостанавливался.

Конкретный механизм выбирается после проверки реализации. Не требуется останавливать всё приложение, если snapshot обеспечивает согласованность корпуса.

## 7. Полный и инкрементальный перенос

Для первой версии предпочтителен **full snapshot**. Incremental delta можно добавить после измерения объёмов и времени переноса.

Delta должна ссылаться на конкретный `baseExportId`, snapshot watermark и schema/manifest version. Запрещено применять delta к неизвестному или несовместимому базовому snapshot.

Если ingestion продолжается после snapshot, новые изменения не должны незаметно попадать в уже созданный пакет.

## 8. Совместимость и отказ

Импорт блокируется при:
- неизвестной версии manifest;
- несовместимой схеме БД или расширении pgvector;
- несовместимой размерности/модели embeddings;
- отсутствующих объектах или несовпадающих checksums;
- orphan references;
- неизвестном snapshot boundary;
- конфликте идентификаторов;
- неучтённых удалениях после snapshot;
- отсутствии разрешения на перенос источника/категории данных.

Нельзя незаметно преобразовывать текст, векторы, даты действия или provenance ради успешного импорта.

## 9. Идемпотентность и активация

Каждый импорт имеет уникальный `importId`. Повторная доставка объекта не создаёт дубликаты. Частичный импорт не становится активным.

Импортировать сначала в пустую БД, отдельную схему или изолированный namespace. Активировать только после технической и retrieval-валидации. Старый активный корпус не удалять до успешного переключения и проверки rollback-плана.

Механизм переключения (active pointer, schema swap, feature flag и т. п.) не выбран и не должен реализовываться без отдельного технического решения.

## 10. Удаление и временные копии

Экспорт/импорт не обходят D-019/D-020:
- не экспортировать уже удалённые или недоступные данные;
- фиксировать snapshot time и deletion watermark;
- перед активацией применять актуальный deletion journal;
- не допускать восстановления удалённых данных;
- учитывать export packages и временные копии в inventory и deletion procedures;
- не выводить срок хранения export package автоматически из 35-дневного срока backup retention.

## 11. Безопасность

- Хранить export packages только в закрытом и разрешённом контуре.
- Передавать по защищённому каналу.
- Не включать секреты в пакет.
- Не публиковать пакеты в GitHub artifacts/releases или публичных buckets.
- Проверять регион исходного/целевого хранилища и временных файлов.
- Экспорт/импорт доступны только уполномоченным операторам; permissions и approval workflow остаются OPEN.
- Не помещать содержимое документов, prompts, vectors и секреты в обычные логи.
- Не смешивать публичный правовой корпус и D3-пользовательские данные в одном пакете по умолчанию.

## 12. Этапы внедрения

**A. Audit:** сопоставить реальные Prisma models, object keys, PostgreSQL/pgvector versions, IDs, checksums и хранение extracted text.

**B. Synthetic proof:** реализовать тестовый экспорт/импорт только на synthetic corpus, проверить vectors без повторного вызова embedding provider.

**C. Approved legal corpus:** подключать реальные источники только после разрешения O-006 и проверки географии хранения.

**D. Optimization:** incremental export, resumable transfer и parallel copy — после измерения реальных объёмов.

## 13. Критерии готовности

- versioned manifest и export ID;
- согласованный snapshot boundary;
- полный object inventory и checksums;
- восстановлены документы, версии, структура, chunks, vectors и metadata;
- проверены counts и relationships;
- embeddings перенесены как сохранённые значения, без повторной генерации;
- FTS/vector indexes восстановлены или перестроены;
- deletion journal применён;
- retrieval regression suite пройдена;
- импорт не активируется при блокирующей ошибке;
- операции журналируются без содержимого и секретов.

## 14. OPEN-вопросы

- FILE-001: object storage provider.
- FILE-007: где хранить extracted text.
- Формат export package и manifest.
- Нужна ли incremental delta в MVP.
- Механизм snapshot при непрерывном ingestion.
- Кто может запускать/одобрять export/import.
- Срок хранения временных export packages.
- Источники, для которых экспорт разрешён (O-006).
- Нужны ли несколько одновременно доступных index generations.
- Версии PostgreSQL и pgvector для production.

Все варианты — PROPOSED, а не новые CONFIRMED решения.

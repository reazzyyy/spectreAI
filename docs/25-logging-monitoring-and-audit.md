# 25. Логирование, мониторинг и аудит

**Статус:** PROPOSED для tooling/метрик; **CONFIRMED остров:** техническая цель хранения аудита 1 год (**D-021**); admin-grant события с TTL ≤ 60 мин (**D-013/D-016**).  
**Файл:** `docs/25-logging-monitoring-and-audit.md`


## Подтверждённые правила аудита (D-021)

Целевой срок хранения аудита — 1 год, при условии юридической и договорной проверки до production. Не записывать в обычные логи содержимое документов, полные промпты/ответы, токены и секреты. Права на просмотр/экспорт аудита — **OPEN**.


> Технические решения, лимиты и сроки, не отмеченные CONFIRMED в `docs/decisions-log.md`, являются предложениями. Документ описывает целевое поведение системы, а не подтверждает реализацию.

## 1. Цель

Система должна позволять команде:

- находить и расследовать ошибки;
- понимать, на каком этапе возникла проблема: frontend, API, очередь задач, обработка документов, поиск или AI-провайдер;
- отслеживать задержки и доступность сервиса;
- контролировать расходы на модели;
- обнаруживать подозрительные действия;
- подтверждать, кто, когда и на каком основании получил доступ к конфиденциальным данным;
- расследовать инциденты, не раскрывая содержимое юридических документов в технических логах.

Главный принцип: **логи, метрики и аудит — разные механизмы, и каждый хранит только те данные, которые необходимы для своей задачи.**

## 2. Три механизма наблюдаемости

### 2.1. Технические логи

Нужны для диагностики работы приложения.

Примеры:
- API вернул ошибку при загрузке документа;
- задача обработки документа превысила таймаут;
- AI-провайдер вернул ошибку;
- worker не смог подключиться к Redis;
- запрос завершился с ошибкой валидации.

Технический лог описывает событие и его технический контекст, но не должен содержать текст документа, переписку с ИИ или секреты.

### 2.2. Метрики и мониторинг

Нужны для оценки состояния сервиса во времени.

Примеры:
- доля успешных запросов;
- среднее и 95-й перцентиль времени ответа;
- количество задач в очереди;
- количество ошибок AI-провайдеров;
- стоимость обработки запросов;
- доступное место в хранилище.

Метрики должны преимущественно содержать агрегированные значения, а не персональные данные или идентификаторы конкретных документов.

### 2.3. Аудит безопасности

Нужен для фиксации значимых действий пользователей и системы.

Примеры:
- пользователь получил доступ к организации;
- сотрудник изменил роль другого участника;
- администратор запросил доступ к содержимому рабочей области;
- уполномоченный сотрудник одобрил или отклонил запрос;
- был выдан временный доступ к содержимому;
- пользователь скачал документ;
- доступ к документу был отозван.

Аудит должен отвечать на вопросы: **кто совершил действие, что произошло, когда, над каким объектом и на каком основании.**

## 3. Архитектура

Предлагаемая схема:

```text
Next.js frontend
    |
    v
NestJS API ---------> Technical logs
    |                       |
    |                       v
    |                 Log collector
    |                       |
    v                       v
PostgreSQL             Log storage
    |
    +----> Audit events
    |
    +----> AI usage records
    |
    v
Redis / queue
    |
    v
Background workers ----> Technical logs
    |
    v
AI Gateway ------------> Provider metrics
    |
    v
Monitoring / alerts
```

Это логическая схема. Конкретный набор инструментов следует выбирать с учётом инфраструктуры, бюджета и требований к размещению данных.

### Предлагаемые компоненты

| Компонент | Назначение |
|---|---|
| NestJS structured logger | Структурированные логи backend |
| Request ID / Trace ID | Связь событий одного запроса |
| PostgreSQL | Аудит и учёт использования ИИ, если выбранная схема хранения это предусматривает |
| Metrics collector | Сбор технических метрик |
| Monitoring dashboard | Графики, состояние сервисов и очередей |
| Alerting | Уведомления об инцидентах |
| Error tracking | Группировка ошибок frontend и backend |
| Log storage | Централизованный поиск технических логов |

**Важно:** не нужно автоматически складывать все логи в PostgreSQL. Большие объёмы технических логов обычно удобнее хранить отдельно. Аудит и технические логи могут иметь разные права доступа и сроки хранения.

## 4. Структура технического лога

Логи должны быть структурированными, предпочтительно в JSON.

Пример:

```json
{
  "timestamp": "2026-10-27T12:00:00.000Z",
  "level": "error",
  "service": "api",
  "environment": "production",
  "event": "ai_job_failed",
  "requestId": "req_example",
  "traceId": "trace_example",
  "jobId": "job_example",
  "organizationId": "org_example",
  "errorCode": "AI_PROVIDER_TIMEOUT",
  "durationMs": 30000
}
```

Значения в примере условные. Реальные идентификаторы должны быть безопасными для использования в логах.

### Обязательные поля

- `timestamp` — время события в UTC;
- `level` — уровень логирования;
- `service` — компонент системы;
- `environment` — окружение;
- `event` — стабильное машинное название события;
- `requestId` — идентификатор запроса, если он существует;
- `traceId` — идентификатор трассировки, если она используется;
- `errorCode` — стабильный код ошибки, если событие связано с ошибкой.

Дополнительные поля добавляются только при необходимости.

### Уровни логирования

| Уровень | Для чего использовать |
|---|---|
| `debug` | Подробная диагностика разработки |
| `info` | Штатные значимые события |
| `warn` | Необычная ситуация, которая пока не нарушила работу |
| `error` | Ошибка отдельной операции |
| `fatal` | Критическая ошибка, из-за которой сервис или его важная часть не может продолжать работу |

В production уровень `debug` по умолчанию отключён или ограничен. Включать подробную диагностику на работающем сервисе можно только с контролем того, какие данные попадают в логи.

## 5. Что запрещено записывать в технические логи

По умолчанию нельзя записывать:

- полный текст юридического документа;
- полный текст переписки пользователя с ИИ;
- полные промпты и ответы модели;
- извлечённый текст PDF или DOCX;
- содержимое загружаемых файлов;
- пароли, токены авторизации и cookies;
- API-ключи и секреты;
- ссылки на скачивание с действующими токенами;
- персональные данные, не требующиеся для диагностики;
- полные тела запросов и ответов API без специального обоснования.

Необходимо избегать автоматического логирования всех заголовков HTTP и всех тел запросов.

### Обработка исключений

При возникновении ошибки нельзя без фильтрации записывать в лог объект исключения целиком, если он может содержать:

- запрос к AI-провайдеру;
- заголовки с авторизацией;
- текст документа;
- содержимое пользовательского сообщения;
- URL с секретными параметрами.

Нужно извлекать безопасные поля: класс ошибки, внутренний код, сервис, этап обработки, статус ответа и технический stack trace после проверки на чувствительные данные.

**Запрет на логирование не должен зависеть только от аккуратности разработчика.** Нужны общие правила маскирования, безопасные обёртки логгера и автоматические тесты.

## 6. Request ID и Trace ID

Каждый входящий HTTP-запрос должен иметь `requestId`.

Правила:

1. Если клиент прислал идентификатор корреляции, сервер проверяет его формат и длину.
2. Если идентификатор отсутствует или невалиден, сервер создаёт новый.
3. Идентификатор добавляется в контекст логирования.
4. В ответе API возвращается `requestId`, если это предусмотрено контрактом.
5. При запуске фоновой задачи сохраняется связь с исходным запросом.
6. Worker использует переданный контекст при обработке задачи.
7. При вызове AI Gateway идентификатор передаётся дальше во внутренний контекст.
8. Идентификаторы провайдера, если они доступны, сохраняются отдельно и не заменяют внутренние идентификаторы.

`requestId` связывает события одного HTTP-запроса. `traceId` может связывать целую цепочку операций, включая очередь и несколько сервисов.

Не следует использовать `requestId` как механизм авторизации: знание идентификатора не должно давать доступ к запросу или его результату.

## 7. Трассировка фоновых задач

Для AI Job необходимо фиксировать переходы состояний и длительность этапов.

Например:

```text
ai_job_queued
    -> ai_job_started
    -> document_retrieval_completed
    -> prompt_assembled
    -> ai_provider_request_started
    -> ai_provider_request_completed
    -> ai_job_completed
```

Это пример последовательности. Реальные события зависят от конкретного сценария.

Для каждого этапа желательно фиксировать:

- `jobId`;
- тип задачи;
- номер попытки;
- время начала и завершения;
- длительность;
- результат этапа;
- безопасный код ошибки;
- идентификатор провайдера и модели, если применимо;
- количество токенов и стоимость, если они известны.

Не нужно записывать полный контекст RAG, собранный промпт или содержимое ответа только ради диагностики.

## 8. Метрики доступности и производительности

На MVP следует контролировать как минимум следующие группы метрик.

### 8.1. API

- количество запросов;
- доля успешных запросов;
- количество ошибок по группам HTTP-статусов;
- время ответа: p50, p95, p99;
- частота таймаутов;
- частота ошибок авторизации и доступа;
- частота `429 Too Many Requests`.

### 8.2. AI Gateway

- количество запросов к каждому провайдеру и модели;
- доля успешных вызовов;
- доля таймаутов;
- задержка ответа;
- ошибки ограничения скорости;
- количество повторных попыток;
- количество отменённых вызовов;
- количество входных и выходных токенов, если доступно;
- оценка стоимости;
- расхождения между предварительной оценкой и фактическими расходами.

### 8.3. Фоновые задачи

- количество задач по состояниям;
- размер очереди;
- возраст самой старой ожидающей задачи;
- время обработки;
- количество повторных попыток;
- доля завершённых с ошибкой задач;
- количество зависших задач;
- доступность workers.

### 8.4. Обработка документов и RAG

- время извлечения текста;
- доля неудачных обработок;
- количество документов в очереди;
- время поиска;
- количество найденных фрагментов;
- доля запросов, для которых не найдено релевантных источников;
- время построения контекста;
- ошибки индексирования и удаления данных.

Технические метрики поиска не должны содержать тексты документов, запросы пользователей или содержимое найденных фрагментов.

### 8.5. Инфраструктура

- CPU и память;
- использование диска;
- свободное место;
- доступность PostgreSQL и Redis;
- соединения с базой;
- ошибки резервного копирования;
- состояние объектного хранилища;
- доступность внешних AI-провайдеров.

## 9. Мониторинг качества ответов ИИ

Успешный HTTP-запрос не означает, что ИИ дал хороший ответ.

Для оценки качества нужно отдельно отслеживать:

- долю ответов с корректными ссылками на источники;
- долю ответов, где заявленные ссылки действительно существуют;
- долю неудачных юридических поисков;
- долю ответов без достаточных подтверждений;
- ошибки формата структурированного результата;
- результаты регрессионных тестов моделей и промптов;
- пользовательские оценки, если такой механизм появится в продукте.

Эти показатели должны рассчитываться на тестовых наборах и допустимых обезличенных данных. Нельзя включать конфиденциальные документы клиентов в сторонние системы оценки без соответствующего правового и технического согласования.

Для юридического продукта особенно важно различать:

1. **Техническую успешность** — задача завершилась.
2. **Корректность структуры** — ответ соответствует ожидаемому формату.
3. **Качество источников** — ссылки существуют и подтверждают соответствующие утверждения.
4. **Юридическую точность** — вывод соответствует применимому праву и фактам задачи.

Последний пункт нельзя достоверно оценить только по техническим метрикам.

## 10. Учёт расходов на ИИ

Для каждого завершённого или частично завершённого вызова AI Gateway желательно фиксировать запись использования.

Предлагаемая структура `AIUsageRecord`:

- `id`;
- `organizationId`;
- `userId`, если применимо;
- `jobId`;
- `provider`;
- `model`;
- `operationType`;
- `inputTokens`, если доступны;
- `outputTokens`, если доступны;
- `cachedInputTokens`, если доступны;
- `estimatedCost`;
- `actualCost`, если провайдер предоставляет фактические данные;
- `currency`;
- `status`;
- `createdAt`.

Запись не должна содержать текст промпта или ответа.

### Требования

- различать фактические и расчётные расходы;
- сохранять версию тарифов или источник расчёта;
- учитывать повторные попытки;
- учитывать неуспешные вызовы, если они тарифицируются;
- не считать повторно одну и ту же запись использования при обработке события несколько раз;
- связывать расходы с организацией для последующего расчёта тарифов;
- не считать отсутствие данных о токенах нулевым расходом.

Пользовательские лимиты и коммерческие тарифы должны быть отдельной логикой. Мониторинг расходов не заменяет механизм ограничения расходов.

## 11. Аудит безопасности

### 11.1. Основные поля

Предлагаемая структура `AuditEvent`:

- `id`;
- `organizationId`;
- `actorUserId`, если действие совершил пользователь;
- `actorType` — пользователь, система или worker;
- `action`;
- `resourceType`;
- `resourceId`;
- `result` — успех или отказ;
- `reasonCode`, если применимо;
- `requestId`;
- `traceId`, если применимо;
- `createdAt`;
- `metadata` с ограниченным набором безопасных полей.

При необходимости добавляются идентификатор сессии, способ аутентификации или идентификатор административного запроса.

Аудит должен фиксировать фактический результат действия, а не только намерение его выполнить.

### 11.2. События, которые обязательно нужно аудировать

**Учётные записи и доступ:**
- вход и выход;
- неудачные попытки входа в агрегированном или ограниченном виде;
- создание и отзыв сессии;
- приглашение пользователя;
- изменение членства в организации;
- изменение ролей и разрешений;
- блокировка или удаление учётной записи.

**Организации и рабочие области:**
- создание и изменение организации;
- создание рабочей области;
- изменение состава участников;
- изменение политик доступа;
- выдача и отзыв разрешений.

**Документы:**
- загрузка;
- просмотр или скачивание в соответствии с утверждённой политикой аудита;
- изменение версии;
- архивирование;
- удаление;
- отказ в доступе к конфиденциальному ресурсу, если он значим для расследования.

**ИИ:**
- запуск значимой AI Job;
- отмена задачи;
- завершение с ошибкой;
- выполнение операции, связанной с передачей данных внешнему провайдеру;
- блокировка операции политикой конфиденциальности.

**Административный доступ к содержимому:**
- создание запроса на доступ;
- одобрение или отклонение;
- попытка самоодобрения;
- выдача ограниченного доступа;
- использование доступа;
- истечение срока;
- отзыв доступа.

### 11.3. Особое правило административного доступа

В соответствии с решениями D-006 и D-007:

- администратор организации не получает автоматического доступа к содержимому документов и чатов;
- запрос на доступ фиксируется отдельным событием;
- одобрение выполняет уполномоченный сотрудник;
- инициатор не может одобрить собственный запрос;
- доступ ограничивается согласованными объектами и сроком;
- фактическое использование выданного доступа фиксируется;
- после истечения срока или отзыва разрешение больше не действует.

Нельзя записывать в аудит само содержимое документа или чата, чтобы доказать факт доступа. Достаточно зафиксировать объект, действие, основание, результат и время.

## 12. Защита журнала аудита

Аудит имеет повышенную ценность при расследовании инцидентов, поэтому его нельзя без контроля изменять или удалять.

Предлагаемые требования:

- отдельные права на чтение аудита;
- запрет обычным пользователям на изменение записей;
- ограничение прав администраторов приложения;
- фиксация действий с самим журналом аудита;
- защита от незаметного изменения записей;
- резервное копирование;
- проверка целостности;
- контролируемое удаление по утверждённым правилам хранения.

Для MVP достаточно спроектировать журнал с ограниченными правами записи и изменения. Более сложную защиту от подмены — например, внешнее неизменяемое хранилище или криптографическую проверку цепочки событий — можно внедрять после оценки модели угроз.

**Важно:** отдельная таблица в PostgreSQL сама по себе не гарантирует неизменяемость аудита, если злоумышленник получил привилегированный доступ к базе.

## 13. Сроки хранения

Конкретные сроки должны быть утверждены отдельно с учётом законодательства, договоров с клиентами, целей обработки и модели угроз.

До утверждения сроков нельзя считать следующие значения финальной политикой.

| Категория | Предлагаемый подход |
|---|---|
| Технические логи | Короткий срок хранения, достаточный для диагностики |
| Ошибки и трассировки | Ограниченный срок, с минимизацией чувствительных данных |
| Аудит безопасности | Отдельный утверждённый срок с контролем доступа |
| Учёт расходов на ИИ | Срок, необходимый для биллинга, сверки и договорных обязательств |
| Метрики | Хранение агрегированных данных, при необходимости — более длительное |
| Данные инцидента | Продление хранения только по документированному основанию |

### Правила удаления

- удаление выполняется автоматически по политике;
- процесс удаления логируется без копирования удаляемых данных;
- резервные копии рассматриваются отдельно;
- доступ к старым журналам ограничивается;
- для юридически значимых событий сроки нельзя определять только удобством разработчиков.

## 14. Оповещения об инцидентах

Нужно настроить уведомления как минимум для следующих ситуаций:

| Событие | Уровень |
|---|---|
| API недоступен | Критический |
| Резкий рост серверных ошибок | Высокий |
| PostgreSQL недоступен | Критический |
| Очередь задач растёт и не обрабатывается | Высокий |
| AI-провайдер массово возвращает ошибки | Высокий |
| Неожиданный рост расходов на ИИ | Высокий |
| Заканчивается место на диске | Высокий |
| Не работает резервное копирование | Высокий |
| Массовые отказы в авторизации | Требует оценки |
| Попытка обхода изоляции организаций | Критический сигнал для расследования |
| Самоодобрение административного доступа | Критический сигнал безопасности |

Уведомления не должны включать тексты документов, промпты, ответы модели или секреты.

Пороговые значения необходимо определить после получения базовых данных о нагрузке. Для MVP допустимо начать с простых правил и уточнять их после пилота.

## 15. Интеграция с frontend

Frontend должен передавать или получать идентификаторы корреляции согласно API-контракту.

Для клиентского error tracking:

- фиксировать тип ошибки, маршрут и технический контекст;
- исключать содержимое полей с юридическими документами;
- не отправлять полные тексты сообщений;
- очищать URL от токенов и секретных параметров;
- не записывать содержимое форм;
- контролировать передачу данных внешнему поставщику мониторинга;
- не считать frontend-идентификаторы доказательством личности пользователя.

Пользовательский интерфейс должен показывать понятное сообщение и идентификатор ошибки, например:

> Не удалось обработать документ. Попробуйте ещё раз или обратитесь в поддержку, указав код ошибки.

Не следует показывать пользователю stack trace, внутренние адреса сервисов, названия таблиц или детали конфигурации.

## 16. Безопасность и разделение организаций

При проектировании мониторинга необходимо обеспечить:

- доступ к техническим логам только уполномоченным сотрудникам;
- ограничение доступа к деталям конкретных организаций;
- отсутствие текстов документов в метриках;
- запрет на выдачу содержимого аудита обычным пользователям;
- проверку прав при просмотре аудита через API;
- отсутствие доступа к данным другой организации через поиск по логам;
- контроль экспорта и скачивания логов;
- аудит действий сотрудников поддержки и эксплуатации, если они могут получить доступ к чувствительным данным.

Идентификатор организации в логе — полезный контекст, но сам по себе он не делает лог безопасным. Нельзя позволять пользователю получить технические логи организации только потому, что он знает её ID.

## 17. Тестирование

### Технические логи

- чувствительные заголовки не попадают в логи;
- исключения не раскрывают тела запросов;
- тексты документов и сообщений не записываются автоматически;
- request ID корректно создаётся и передаётся;
- ошибки не содержат API-ключей;
- stack trace фильтруется согласно принятой политике.

### Аудит

- успешное изменение прав создаёт событие;
- отказ в доступе фиксируется в предусмотренных случаях;
- инициатор не может одобрить собственный запрос на доступ;
- использование административного доступа аудируется;
- отзыв разрешения отражается в аудите;
- обычный пользователь не может изменять записи аудита;
- повторная доставка события не создаёт неконтролируемых дублей;
- сбой записи обязательного аудита не приводит к незаметному выполнению критической операции.

### Метрики и оповещения

- ошибки API попадают в метрики;
- сбои AI-провайдера отображаются отдельно;
- зависшая очередь обнаруживается;
- отказ резервного копирования вызывает уведомление;
- всплеск расходов на ИИ выявляется;
- мониторинг не раскрывает содержимое конфиденциальных данных.

Для критических операций нужно отдельно определить, когда отказ записи аудита должен блокировать действие. Нельзя применять один режим ко всем событиям: потеря необязательного диагностического лога и потеря записи о выдаче привилегированного доступа имеют разный уровень риска.

## 18. Критерии готовности MVP

Документ считается реализованным на уровне MVP, когда:

1. Backend и workers используют единый формат технических логов.
2. Все HTTP-запросы имеют request ID.
3. Длительные AI Jobs можно проследить от запуска до результата.
4. В логах нет текстов документов, секретов и полных промптов.
5. Основные показатели API, очереди и AI Gateway доступны для мониторинга.
6. Расходы на ИИ учитываются отдельно от технических логов.
7. Ключевые изменения прав доступа записываются в аудит.
8. Сценарий административного доступа полностью аудируется.
9. Настроены уведомления о критических сбоях.
10. Сроки хранения и доступ к логам определены политикой.
11. Права доступа к журналу аудита проверены тестами.
12. Сценарии утечки чувствительных данных через логи проверены автоматически.

## 20. Инструкция для Cursor

При реализации этого документа:

1. Сначала изучи существующие модули, схему БД, обработку ошибок и фоновые задачи.
2. Не добавляй новые библиотеки без проверки существующих зависимостей и совместимости.
3. Не меняй архитектуру целиком ради логирования.
4. Создай единый интерфейс структурированного логирования.
5. Добавь request ID и передачу контекста в фоновые задачи.
6. Введи маскирование чувствительных полей и тесты на утечки.
7. Реализуй аудит ключевых событий авторизации и изменения прав.
8. Обеспечь отдельную защиту административного доступа к содержимому.
9. Добавь учёт использования AI Gateway, не смешивая его с техническими логами.
10. Добавляй метрики и оповещения постепенно, начиная с критических сценариев.
11. Не записывай тексты документов, промптов и ответов модели для упрощения отладки.
12. Не принимай сроки хранения и инструменты из этого документа за окончательно утверждённые решения.
13. Не объявляй задачу завершённой, пока тесты безопасности и проверки отсутствия утечек не пройдены.

**Приоритет реализации:** безопасные логи и request ID → аудит доступа → трассировка AI Jobs → учёт расходов → метрики и оповещения → расширенная защита аудита.

# 10. AI Provider Integration — Интеграция AI-провайдеров

**Статус:** PROPOSED  
**Версия:** 0.1  
**Тип документа:** техническая спецификация  
**Приоритет:** высокий  
**Связанные документы:**
- `docs/02-architecture.md`
- `docs/06-data-model.md`
- `docs/07-access-control-matrix.md`
- `docs/08-data-lifecycle-and-deletion.md`
- `docs/09-threat-model.md`

## 1. Цель

Определить единый механизм работы приложения с AI-моделями для следующих сценариев MVP:

- chat — диалог с AI;
- docs — анализ и обработка документов;
- research — исследование с использованием источников;
- drafts — подготовка черновиков юридических документов;
- workspace — работа с материалами и контекстом рабочего пространства.

Интеграция должна обеспечивать:

1. Независимость бизнес-логики от конкретного поставщика модели.
2. Возможность подключать несколько провайдеров.
3. Возможность в будущем использовать собственные модели.
4. Единый формат сообщений, результатов и ошибок.
5. Контроль времени выполнения, количества токенов и стоимости.
6. Безопасную обработку конфиденциальных данных.
7. Поддержку потоковой генерации.
8. Наблюдаемость AI-задач и диагностику ошибок.
9. Управляемое переключение между моделями.
10. Возможность тестировать AI-сценарии без реальных платных API.

Документ описывает целевую архитектуру, а не утверждает, что интеграция уже реализована.

## 2. Основные архитектурные решения

### ADR-010-01. Единый внутренний интерфейс

**Статус:** PROPOSED.

Бизнес-логика обращается к внутреннему интерфейсу `AIProvider`, а не к SDK OpenAI, Anthropic, Google или другого поставщика напрямую.

### ADR-010-02. Адаптер на каждого провайдера

**Статус:** PROPOSED.

Каждый провайдер реализуется отдельным адаптером. Адаптер преобразует внутренний формат приложения в формат API провайдера и преобразует ответ обратно во внутренний формат.

### ADR-010-03. Выбор модели выполняется сервером

**Статус:** PROPOSED.

Клиент не может самостоятельно передать произвольный идентификатор провайдера или модели и тем самым обойти настройки организации, разрешённые модели или ограничения расходов.

### ADR-010-04. Провайдер не определяет права доступа

**Статус:** ACCEPTED как следствие `docs/07-access-control-matrix.md` и `docs/09-threat-model.md`.

Проверка доступа выполняется приложением до передачи контекста модели. Ответ модели не может расширять полномочия пользователя.

### ADR-010-05. Self-hosted модель — отдельная реализация интерфейса

**Статус:** PROPOSED.

В будущем собственная модель подключается как ещё один адаптер, а не как отдельная бизнес-архитектура.

### ADR-010-06. Синхронные и фоновые задачи используют общий AI-контур

**Статус:** PROPOSED.

Короткие запросы могут выполняться непосредственно в рамках HTTP-запроса с потоковой передачей ответа. Длительные исследования, массовый анализ документов и другие тяжёлые операции выполняются через очередь задач.

Конкретные ограничения по времени и размеру контекста определяются конфигурацией и нагрузочными испытаниями.

## 3. Термины

| Термин | Значение |
|---|---|
| Provider | Внешний поставщик AI API или собственный inference-сервис |
| Model | Конкретная модель, доступная через провайдера |
| Adapter | Компонент, переводящий внутренний контракт в API конкретного провайдера |
| AI Gateway | Внутренний слой, управляющий вызовами моделей |
| AI Task | Логическая задача пользователя: чат, анализ, research или генерация |
| AI Attempt | Одна попытка выполнения задачи через модель |
| Context | Подготовленные сообщения, документы и другие данные для модели |
| Token usage | Количество входных и выходных токенов по данным провайдера или оценке |
| Streaming | Передача результата по частям до завершения генерации |
| Fallback | Переход на альтернативную модель при определённых ошибках |
| Self-hosted inference | Запуск модели на инфраструктуре, контролируемой владельцем сервиса |

Важно различать `AI Task` и `AI Attempt`. Одна пользовательская задача может включать несколько попыток, например при временной ошибке сети. Для корректного учёта расходов каждая попытка должна учитываться отдельно.

## 4. Общая архитектура

```text
Frontend
   |
   v
Backend API
   |
   v
Use Case
(Chat / Document Analysis / Research / Draft)
   |
   v
Context Builder
   |-- проверка прав
   |-- загрузка разрешённых источников
   |-- сборка сообщений
   |-- ограничение контекста
   |
   v
AI Gateway
   |-- Model Router
   |-- Policy Checks
   |-- Usage Tracking
   |-- Timeout / Retry
   |
   v
AI Provider Adapter
   |-- Provider A
   |-- Provider B
   |-- Self-hosted Inference (future)
   |
   v
External API / Internal Inference
```

### 4.1. Ответственность компонентов

**Backend API**
- аутентифицирует пользователя;
- проверяет доступ к ресурсу;
- создаёт задачу;
- отдаёт результат или поток событий.

**Use Case**
- реализует бизнес-сценарий;
- определяет тип задачи;
- задаёт требования к результату;
- не зависит от SDK провайдера.

**Context Builder**
- собирает разрешённые материалы;
- ограничивает объём контекста;
- формирует структурированные входные данные;
- учитывает актуальные права доступа.

**AI Gateway**
- выбирает допустимую модель;
- применяет лимиты;
- вызывает адаптер;
- отслеживает попытки, ошибки и использование;
- нормализует результат.

**Provider Adapter**
- выполняет конкретный API-вызов;
- преобразует запрос;
- нормализует поток и финальный ответ;
- возвращает типизированные ошибки и метаданные использования.

**Usage Tracker**
- сохраняет данные о расходах;
- связывает расход с организацией, задачей и попыткой;
- не сохраняет полное конфиденциальное содержимое только ради учёта.

Названия условные. Их можно адаптировать под структуру проекта, но разделение ответственности необходимо сохранить.

### Правила организации кода

- `domain` не импортирует SDK конкретного провайдера.
- `application` работает с внутренними типами.
- `infrastructure/providers` содержит все специфичные API-интеграции.
- `pricing` хранит версионируемые сведения о тарифах.
- `testing` предоставляет тестовую реализацию провайдера.
- Конфигурация секретов не хранится в исходниках.
- Контроллеры не вызывают SDK провайдера напрямую.

## 6. Контракт провайдера

### 6.1. Общий интерфейс

Предлагаемый TypeScript-контракт:

```ts
export interface AIProvider {
  readonly providerId: string;

  generate(
    request: AIGenerateRequest,
    options: AICallOptions,
  ): Promise<AIGenerateResult>;

  stream(
    request: AIGenerateRequest,
    options: AICallOptions,
  ): AsyncIterable<AIStreamEvent>;

  getCapabilities(): ModelCapabilities;
}
```

`AIProvider` — внутренний контракт приложения. Он не обязан повторять интерфейс какого-либо конкретного SDK.

`generate` предназначен для получения полного результата.

`stream` возвращает последовательность событий. Конкретный адаптер преобразует события своего API в унифицированный формат.

`getCapabilities` сообщает о возможностях модели, но не заменяет серверную проверку политики.

### 6.2. Контракт запроса

```ts
export interface AIGenerateRequest {
  modelId: string;

  messages: AIMessage[];

  parameters?: {
    temperature?: number;
    maxOutputTokens?: number;
    topP?: number;
  };

  responseFormat?: {
    type: "text" | "json";
    schema?: Record<string, unknown>;
  };

  metadata: {
    taskId: string;
    attemptId: string;
    organizationId: string;
    userId: string;
    taskType:
      | "chat"
      | "document_analysis"
      | "research"
      | "draft";
  };
}
```

Метаданные предназначены для внутренней маршрутизации, аудита и учёта. Они не должны автоматически отправляться провайдеру.

Адаптер передаёт только поля, необходимые конкретному API. Идентификаторы пользователя и организации не включаются во внешний запрос без отдельной необходимости и утверждённой политики.

### 6.3. Контракт сообщения

```ts
export interface AIMessage {
  role: "system" | "user" | "assistant";

  content: AIContentPart[];
}

export type AIContentPart =
  | {
      type: "text";
      text: string;
    }
  | {
      type: "image";
      source: {
        type: "url" | "base64";
        value: string;
        mediaType?: string;
      };
    };
```

Для MVP можно начать только с текстового содержимого, если анализ изображений не входит в подтверждённый объём первой версии.

Поддержку изображений следует добавлять отдельно, с проверкой форматов, размеров и политики передачи файлов.

Не следует вводить собственный формат tool calls, аудио и других мультимодальных данных до появления конкретного сценария использования.

### 6.4. Контракт результата

```ts
export interface AIGenerateResult {
  content: string;

  finishReason:
    | "stop"
    | "length"
    | "content_filter"
    | "tool_call"
    | "unknown";

  usage: AIUsage;

  providerRequestId?: string;

  model: {
    providerId: string;
    modelId: string;
    modelVersion?: string;
  };
}
```

Внутренний `finishReason` не должен быть жёстко привязан к названиям, используемым одним провайдером. Адаптер преобразует исходные значения в этот контракт.

`providerRequestId` полезен для диагностики, но сам по себе не является секретом или подтверждением успешного результата.

## 7. Учёт токенов и расходов

### 7.1. Контракт использования

```ts
export interface AIUsage {
  inputTokens?: number;
  outputTokens?: number;
  totalTokens?: number;

  estimatedCost?: number;
  costCurrency?: string;

  source:
    | "provider_reported"
    | "estimated";
}
```

Не каждый API возвращает одинаковую детализацию использования. Некоторые данные могут быть недоступны при потоковой генерации или при аварийном завершении запроса.

Поэтому:
- неизвестное количество токенов не следует записывать как ноль;
- оценка не должна смешиваться с подтверждённым использованием;
- расчётная стоимость должна отличаться от фактически выставленного счёта;
- итоговые данные необходимо периодически сверять с отчётностью провайдера, если она доступна.

### 7.2. Формула расчёта

Для моделей с тарификацией по входным и выходным токенам:

\[
C =
\frac{T_{in} \cdot P_{in}}{10^6}
+
\frac{T_{out} \cdot P_{out}}{10^6}
\]

Где:
- \(T_{in}\) — входные токены;
- \(T_{out}\) — выходные токены;
- \(P_{in}\) — цена за миллион входных токенов;
- \(P_{out}\) — цена за миллион выходных токенов.

Это базовая формула, а не универсальный тарифный механизм. Некоторые провайдеры тарифицируют кэшированный ввод, изображения, инструменты, поиск, аудио или другие операции отдельно.

### 7.3. Каталог тарифов

Для каждого тарифа рекомендуется хранить:

- идентификатор провайдера;
- идентификатор модели;
- валюту;
- стоимость входных токенов;
- стоимость выходных токенов;
- дополнительные тарифные категории, если они есть;
- дату начала действия;
- дату окончания действия, если тариф изменён;
- источник тарифа;
- версию записи.

Стоимость не должна быть зашита в бизнес-логику.

### 7.4. Защита от неконтролируемых расходов

До запуска необходимо предусмотреть:
- лимит размера запроса;
- лимит выходных токенов;
- квоту на пользователя;
- квоту на организацию;
- ограничение параллельных задач;
- лимит повторных попыток;
- оповещение при превышении бюджета;
- возможность временно отключить конкретную модель.

**Важно:** лимит на число токенов не всегда равен лимиту стоимости. Например, один вызов может дополнительно тарифицироваться за инструменты или внешние операции.

## 8. Маршрутизация моделей

### 8.1. Назначение

Model Router определяет, какая модель может выполнить конкретную задачу с учётом:

- типа задачи;
- допустимости обработки данных;
- разрешённых моделей;
- возможностей модели;
- доступного контекста;
- ограничений по времени;
- лимитов расходов;
- доступности провайдера.

### 8.2. Внутренние профили

Рекомендуется использовать логические профили вместо прямой привязки бизнес-кода к названию модели.

Примеры:

- `chat-default`;
- `document-analysis`;
- `research`;
- `draft-generation`;
- `structured-output`.

Это внутренние имена, не реальные модели.

Пример конфигурации:

```ts
export interface ModelProfile {
  profileId: string;

  primary: {
    providerId: string;
    modelId: string;
  };

  fallback?: {
    providerId: string;
    modelId: string;
  };

  maxOutputTokens: number;
  timeoutMs: number;

  allowedTaskTypes: string[];

  enabled: boolean;
}
```

Конфигурация в этом примере намеренно упрощена. Перед production необходимо добавить ограничения по типам данных, доступности инструментов и допустимости внешней обработки.

### 8.3. Правила маршрутизации

1. Клиент передаёт тип операции или логический профиль, но не получает право выбирать произвольный провайдер.
2. Backend проверяет, разрешён ли профиль для организации и типа задачи.
3. Проверяется допустимость передачи данных выбранному провайдеру.
4. Выбирается конкретная модель.
5. Выполняется запрос с заданными лимитами.
6. Фиксируются результат, использование и ошибки.
7. При необходимости выполняется контролируемый fallback.

### 8.4. Fallback

Переход на другую модель разрешается только при заранее определённых условиях.

Допустимые причины:
- временная ошибка провайдера;
- сетевой сбой;
- ограничение скорости;
- подтверждённая недоступность модели.

Не следует автоматически переключаться на другую модель, если:
- провайдер отклонил запрос из-за политики безопасности;
- запрос содержит запрещённые данные;
- превышена квота организации;
- модель не поддерживает необходимый формат;
- ошибка связана с отсутствием прав.

При повторной отправке необходимо учитывать риск двойной тарификации и неопределённости результата первой попытки.

**Критически важно:** fallback не должен менять политику обработки данных. Если организации запрещена передача документов провайдеру B, отказ провайдера A не даёт права отправить эти документы провайдеру B.

## 9. Потоковая генерация

### 9.1. Общая схема

Для чата рекомендуется поддержать streaming, чтобы пользователь мог видеть ответ по мере генерации.

```text
Frontend
   |
   | POST /api/v1/ai/chat
   v
Backend
   |
   | Проверка прав и контекста
   v
AI Gateway
   |
   | Вызов адаптера
   v
Provider API
   |
   | Частичные события
   v
Provider Adapter
   |
   | Нормализованные события
   v
Backend → Frontend
```

Для первого варианта можно использовать SSE (Server-Sent Events), если выбранная инфраструктура поддерживает стабильные длительные HTTP-соединения. WebSocket не требуется только ради потокового текста.

### 9.2. Формат событий

Предлагаемые внутренние события:

```ts
export type AIStreamEvent =
  | {
      type: "message_start";
      taskId: string;
    }
  | {
      type: "text_delta";
      text: string;
    }
  | {
      type: "usage";
      usage: AIUsage;
    }
  | {
      type: "message_complete";
      finishReason: string;
    }
  | {
      type: "error";
      code: string;
      retryable: boolean;
    };
```

События адаптера могут поступать в другом порядке или с другой детализацией. Gateway обязан нормализовать их.

Не каждый провайдер отдаёт usage до окончания генерации. Если данные появляются только в финальном событии, это необходимо учитывать.

### 9.3. Правила streaming

- Backend проверяет права до начала генерации.
- Токены и внутренние секреты никогда не передаются клиенту.
- Ошибка не должна раскрывать детали инфраструктуры.
- Клиентское отключение обрабатывается отдельно от ошибки провайдера.
- При обрыве соединения система определяет, продолжать ли генерацию или отменять её.
- Результат сохраняется в согласованном формате.
- Незавершённый ответ не помечается как успешный.
- Система не должна создавать повторную платную генерацию только потому, что клиент повторил HTTP-запрос.

Для длительных задач с очередью и возобновлением прогресса может потребоваться отдельный механизм получения статуса. Его контракт необходимо определить вместе с API задач.

## 10. Таймауты, повторы и ошибки

### 10.1. Классификация ошибок

Предлагаемый внутренний набор:

```ts
export type AIErrorCode =
  | "PROVIDER_UNAVAILABLE"
  | "PROVIDER_RATE_LIMITED"
  | "PROVIDER_TIMEOUT"
  | "INVALID_PROVIDER_REQUEST"
  | "MODEL_NOT_AVAILABLE"
  | "CONTEXT_TOO_LARGE"
  | "OUTPUT_LIMIT_REACHED"
  | "CONTENT_REJECTED"
  | "POLICY_VIOLATION"
  | "QUOTA_EXCEEDED"
  | "CANCELLED"
  | "UNKNOWN";
```

Адаптер преобразует ошибки конкретного SDK в этот внутренний набор. Дополнительные поля могут сохраняться для диагностики, если они не содержат секретов.

### 10.2. Повторные попытки

Автоматические повторы допустимы только для ошибок, которые признаны временными и безопасными для повторного вызова.

Рекомендуется:
- ограничивать число попыток;
- использовать экспоненциальную задержку с jitter;
- учитывать `Retry-After`, если он поддерживается;
- задавать общий deadline операции;
- исключать повторы для ошибок валидации и политик;
- отдельно учитывать каждую попытку в usage.

Для генерации текста нельзя считать любой повтор безвредным: первая попытка могла быть выполнена и тарифицирована, даже если клиент не получил ответ.

### 10.3. Идемпотентность

Повторный запрос пользователя и повторный вызов провайдера — разные события.

Рекомендуется:
- создавать внутренний `taskId`;
- использовать ключ идемпотентности для создания задачи, если он поддерживается приложением;
- сохранять идентификатор попытки;
- не создавать дублирующую задачу при повторной отправке того же запроса;
- не считать поддержку idempotency key у провайдера гарантированной без проверки его API.

### 10.4. Таймауты

Для каждой модели задаются:
- таймаут соединения;
- таймаут ожидания первого токена, если применимо;
- максимальная длительность генерации;
- общий deadline задачи.

Численные значения необходимо определить нагрузочными испытаниями и по документации выбранного провайдера.

## 11. Конфиденциальность и подготовка контекста

### 11.1. Контекст формируется сервером

Контекст нельзя принимать от frontend как произвольный набор документов и сразу передавать модели.

Backend должен:
1. определить инициатора;
2. проверить организацию и рабочее пространство;
3. проверить доступ к каждому источнику;
4. загрузить только разрешённые материалы;
5. ограничить размер контекста;
6. определить допустимого провайдера;
7. выполнить политику передачи данных;
8. записать необходимые метаданные задачи.

### 11.2. Минимизация данных

Внешней модели передаются только данные, необходимые для выполнения запроса.

Например, при анализе одного договора не нужно автоматически включать все документы организации или всю историю чатов.

### 11.3. Разделение доверенных и недоверенных данных

Системные инструкции, запрос пользователя и содержимое документов должны быть логически разделены.

Однако такое разделение в промпте само по себе не является достаточной защитой от prompt injection. Реальная защита обеспечивается серверными ACL, ограничением инструментов и контролем внешних действий.

### 11.4. Запрет несанкционированной передачи

До завершения оценки провайдера и утверждения политики обработки реальные конфиденциальные документы не используются в интеграционных тестах с внешней моделью.

В dev/test используются синтетические или должным образом обезличенные данные.

## 12. Учёт AI-задач и попыток

### 12.1. Логическая модель

Рекомендуется использовать сущности, описанные в `docs/06-data-model.md`:

- `AIJob`;
- `AIJobInput`;
- `AIJobResult`;
- `AIProviderConfiguration`.

При необходимости уточнить физическую схему, можно выделить отдельную сущность `AIJobAttempt` для каждой попытки вызова провайдера.

### 12.2. Жизненный цикл задачи

Предлагаемые статусы:

```text
created
   |
   v
queued
   |
   v
running
   |---------> completed
   |---------> failed
   |---------> cancelled
   |---------> timed_out
```

Для streaming следует дополнительно определить, как представляется частично полученный результат и может ли он быть восстановлен после обрыва.

### 12.3. Данные попытки

Рекомендуемые поля:
- `id`;
- `jobId`;
- `attemptNumber`;
- `providerId`;
- `modelId`;
- `startedAt`;
- `completedAt`;
- `status`;
- `errorCode`;
- `inputTokens`;
- `outputTokens`;
- `estimatedCost`;
- `costCurrency`;
- `providerRequestId`;
- `createdAt`.

Необходимо определить политику хранения исходных промптов. По умолчанию полное содержимое конфиденциального запроса не следует дублировать в таблице технических попыток без отдельной причины и правил хранения.

## 13. Конфигурация провайдеров

### 13.1. Разделение настроек

Рекомендуется разделить:

**Секретная конфигурация**
- API-ключи;
- токены доступа;
- адреса закрытых inference-сервисов, если они чувствительны;
- credentials.

**Несекретная конфигурация**
- внутренний ID провайдера;
- поддерживаемые модели;
- таймауты;
- лимиты;
- профили задач;
- доступность;
- версия каталога тарифов.

Секреты не должны попадать в frontend, логи или репозиторий.

### 13.2. Пример конфигурации

```ts
export interface AIProviderConfiguration {
  providerId: string;
  enabled: boolean;

  endpoint?: string;

  models: Array<{
    modelId: string;
    enabled: boolean;
    capabilities: ModelCapabilities;
  }>;

  timeoutMs: number;
  maxRetries: number;
}
```

API-ключ не включён в этот интерфейс намеренно. Секреты должны поступать через отдельный механизм конфигурации.

### 13.3. Переключение провайдера

Переключение должно происходить через конфигурацию и маршрутизацию, а не через изменение кода бизнес-сценария.

Перед переключением необходимо проверить:
- совместимость контракта;
- качество результата;
- доступный контекст;
- поддержку streaming;
- структурированный вывод;
- тарифы;
- правила хранения данных;
- лимиты и ошибки;
- поведение при отмене.

Совпадение названия функции в двух API не означает одинаковое поведение моделей.

## 14. Возможности модели

### 14.1. Контракт возможностей

```ts
export interface ModelCapabilities {
  streaming: boolean;
  jsonMode: boolean;
  structuredOutput: boolean;
  toolCalling: boolean;
  vision: boolean;

  maxInputTokens?: number;
  maxOutputTokens?: number;
}
```

Эти свойства нужны для маршрутизации, но могут зависеть от конкретной версии модели и режима API.

### 14.2. Проверка возможностей

Перед вызовом необходимо проверить, поддерживает ли выбранная модель:
- требуемый формат ответа;
- максимальный размер контекста;
- потоковую генерацию;
- необходимые инструменты;
- мультимодальный ввод, если он используется.

Если возможности не подтверждены, система должна отказать или использовать заранее разрешённый совместимый профиль.

## 15. Структурированные ответы

Для некоторых операций нужен не свободный текст, а структурированный результат.

Например, анализ договора может возвращать список пунктов, рисков и ссылок на источники.

Предлагаемый внутренний подход:

```ts
export interface StructuredAIResult<T> {
  data: T;
  validation: {
    schemaValid: boolean;
    errors: string[];
  };
}
```

Правила:
1. Использовать runtime-валидацию ответа.
2. Не считать JSON корректным только потому, что он успешно распарсился.
3. Проверять типы, обязательные поля и ограничения.
4. Проверять ссылки на источники отдельно от структуры.
5. Не использовать непроверенные значения модели для изменения прав, удаления или отправки данных.
6. Если результат не прошёл валидацию, сохранять контролируемую ошибку и при необходимости выполнять ограниченный повторный запрос.

Для проекта можно использовать Zod на границе AI-ответа, если он принят как стандарт backend.

## 16. Тестирование без реальных провайдеров

### 16.1. Fake AI Provider

Нужно создать тестовую реализацию `AIProvider`, которая умеет:
- возвращать заранее заданный ответ;
- генерировать потоковые события;
- задерживать ответ;
- возвращать временные ошибки;
- возвращать ошибки валидации;
- имитировать превышение лимита;
- имитировать частичный ответ;
- возвращать заданные данные usage.

Это позволит тестировать бизнес-логику без сети и расходов.

### 16.2. Контрактные тесты

Каждый адаптер должен проходить единый набор тестов:
- корректная нормализация ответа;
- корректная обработка пустого результата;
- преобразование ошибок;
- таймаут;
- streaming;
- usage;
- отмена, если поддерживается;
- некорректный ответ провайдера;
- отсутствие секретов в ошибках.

### 16.3. Интеграционные тесты

Для каждого реального провайдера нужны ограниченные тесты, проверяющие:
- соединение;
- корректность запроса;
- получение ответа;
- нормализацию метаданных;
- работу с лимитами;
- поведение при ошибках.

Реальные интеграционные тесты должны использовать синтетические данные и ограниченный бюджет.

## 17. Наблюдаемость

### 17.1. Метрики

Рекомендуется отслеживать:
- количество задач;
- количество успешных и неуспешных попыток;
- длительность полного запроса;
- время до первого токена;
- длительность генерации;
- количество входных и выходных токенов;
- оценочную стоимость;
- количество таймаутов;
- ошибки rate limit;
- число повторных попыток;
- долю fallback;
- размер очереди.

### 17.2. Корреляция событий

Логи, AI-задачи и попытки должны связываться внутренними идентификаторами, например `taskId`, `attemptId` и `requestId`.

При этом нельзя использовать полные промпты и документы как средство корреляции.

### 17.3. Сигналы для оповещений

Необходимо предусмотреть оповещения при:
- резком увеличении расходов;
- росте ошибок провайдера;
- накоплении очереди;
- массовых таймаутах;
- необычном числе повторных попыток;
- внезапном росте использования отдельной модели.

Пороговые значения устанавливаются после появления базовой статистики.

## 18. Self-hosted модели в будущем

### 18.1. Целевая схема

```text
AI Gateway
   |
   v
Self-hosted Adapter
   |
   v
Inference API
   |
   v
Model Server
   |
   v
Model Weights
```

Внутренний контракт `AIProvider` остаётся прежним.

### 18.2. Что потребуется дополнительно

Собственная модель потребует отдельных решений по:
- GPU и памяти;
- серверу inference;
- параллельным запросам;
- очередям и батчингу;
- ограничениям контекста;
- обновлению моделей;
- мониторингу качества;
- масштабированию;
- изоляции сетевого доступа;
- стоимости инфраструктуры;
- резервному сценарию при отказе сервера.

Self-hosting не означает нулевую стоимость. Вместо оплаты каждого вызова провайдеру возникают расходы на оборудование, аренду GPU, электричество, эксплуатацию, обновления и резервирование.

### 18.3. Ограничение

Единый интерфейс снижает стоимость миграции, но не делает модели взаимозаменяемыми полностью. Разные модели отличаются качеством юридического анализа, форматами, поддержкой инструментов, скоростью, ограничениями контекста и поведением на сложных запросах.

После смены модели необходимы повторные функциональные и качественные тесты.

## 19. План реализации

### Этап 1. Базовый контракт
- определить внутренние типы;
- определить интерфейс `AIProvider`;
- реализовать `FakeAIProvider`;
- создать базовые контрактные тесты.

### Этап 2. AI Gateway
- реализовать маршрутизацию;
- подключить конфигурацию моделей;
- добавить таймауты и нормализацию ошибок;
- реализовать учёт попыток и usage.

### Этап 3. Первый реальный адаптер
- выбрать провайдера после технической и правовой оценки;
- реализовать генерацию;
- реализовать streaming, если он нужен для первого сценария;
- проверить лимиты, таймауты и ошибки.

### Этап 4. Интеграция с бизнес-сценариями
- подключить chat;
- подключить document analysis;
- подключить drafts;
- подключить research после определения правил работы с внешними источниками.

### Этап 5. Контроль стоимости и безопасности
- настроить квоты;
- добавить метрики;
- проверить политику передачи данных;
- проверить отсутствие конфиденциального содержимого в логах;
- провести нагрузочные испытания.

### Этап 6. Дополнительные модели
- подключить второй провайдер только при наличии практической необходимости;
- проверить fallback;
- проверить совместимость результатов;
- подготовить интерфейс для self-hosted inference.

Не требуется подключать несколько платных провайдеров одновременно в самом начале. Первый адаптер и качественная архитектурная граница важнее количества интеграций.

## 20. Критерии приёмки

Интеграция считается готовой к дальнейшему подключению продуктовых сценариев, если:

- [ ] Бизнес-логика не импортирует SDK провайдера напрямую.
- [ ] Существует единый внутренний контракт.
- [ ] Есть Fake AI Provider.
- [ ] Ошибки преобразуются в единый формат.
- [ ] Настроены таймауты и ограниченные повторы.
- [ ] У каждой попытки есть идентификатор и статус.
- [ ] Usage не смешивает подтверждённые данные с оценочными.
- [ ] Стоимость рассчитывается на основании версионируемого каталога тарифов.
- [ ] Выбор модели выполняется сервером.
- [ ] Передача данных учитывает утверждённую политику провайдера.
- [ ] Контекст проходит проверку прав до передачи модели.
- [ ] Технические логи не содержат секреты и полные конфиденциальные промпты по умолчанию.
- [ ] Ошибки провайдера не раскрывают внутренние детали клиенту.
- [ ] Интеграцию можно тестировать без реального API.
- [ ] Предусмотрен путь подключения self-hosted модели через отдельный адаптер.

## 22. Итог

AI-интеграция должна быть отдельным внутренним слоем, который контролирует выбор модели, контекст, права доступа, ошибки, потоковую генерацию и расходы.

Основные правила:
1. Бизнес-сценарии не зависят от SDK провайдера.
2. Каждый провайдер подключается через адаптер.
3. Выбор модели и разрешение на передачу данных выполняются сервером.
4. Контекст формируется только из разрешённых ресурсов.
5. Расходы учитываются на уровне отдельных попыток.
6. Повторные вызовы ограничены и контролируются.
7. Все ошибки нормализуются.
8. Self-hosted inference подключается через тот же внутренний контракт.
9. Совместимость интерфейса не заменяет проверку качества и безопасности модели.
10. Реальные юридические документы не передаются внешнему провайдеру до утверждения политики обработки и необходимых договорных условий.

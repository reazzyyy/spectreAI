**Файл:** `docs/13-file-storage-and-document-processing.md`

**Статус:** основные форматы и лимиты подтверждены решениями D-010 и D-017; конкретный OCR-движок остаётся гипотезой H-002.

**Приоритет:** высокий.

## Подтверждённые ограничения MVP (D-010, D-017)

- Допустимые входные форматы: PDF, DOCX, TXT.
- Максимальный размер одного файла: 25 МБ.
- Максимум 10 файлов в одной операции.
- Не принимать архивы, исполняемые файлы, макросодержащие форматы и защищённые паролем документы. Проверять реальный тип содержимого, а не только расширение.
- Сканированные PDF допустимы при успешной OCR-обработке. OCRmyPDF + Tesseract — гипотеза до тестирования, не зафиксированная технология.

## 1. Цель

Определить архитектуру загрузки, хранения, обработки и удаления документов в AI-сервисе для юристов.

Система должна поддерживать:

- загрузку юридических документов;
- безопасное хранение оригиналов;
- извлечение текста из PDF и DOCX;
- обработку сканированных документов через OCR;
- сохранение метаданных;
- подготовку документов к полнотекстовому поиску и RAG;
- отображение статуса обработки;
- повторную обработку при ошибках;
- удаление оригиналов и всех производных данных;
- проверку доступа при каждом чтении или скачивании.

Основной принцип: **файл, его текст, фрагменты, эмбеддинги и результаты обработки представляют собой разные технические данные, но должны сохранять единые ограничения доступа.**

## 2. Границы документа

Документ описывает инфраструктуру файлов и обработку содержимого.

Не входит в его задачи:

- проектирование интерфейса редактора документов;
- реализация юридического анализа текста;
- выбор конкретной LLM;
- окончательный дизайн RAG;
- правила хранения юридических данных, которые должны быть утверждены юристами и ответственными за безопасность;
- гарантированная поддержка любого формата документа.

Эти вопросы рассматриваются в отдельных документах.

## 3. Архитектура

Предлагаемая схема:

    Next.js frontend
        |
        v
    NestJS API
        |
        +---- PostgreSQL
        |       |
        |       +---- метаданные документов
        |       +---- статусы обработки
        |       +---- права и связи
        |
        +---- Private Object Storage
        |       |
        |       +---- оригиналы
        |       +---- производные файлы
        |
        +---- Job Queue
                |
                v
          Document Worker
                |
                +---- проверка файла
                +---- извлечение текста
                +---- OCR при необходимости
                +---- нормализация
                +---- подготовка фрагментов
                +---- индексация
                +---- обновление статуса

Это логическая схема, а не требование создавать отдельный микросервис для каждого этапа.

На первом этапе API и worker могут находиться в одном репозитории и использовать общие типы и контракты. При этом обработка тяжёлых файлов не должна выполняться непосредственно внутри HTTP-запроса.

### 3.1. Компоненты

**Frontend на Next.js**

Отвечает за выбор файла, отправку, отображение прогресса, ошибок и результата обработки.

**Backend на NestJS**

Отвечает за аутентификацию, проверку разрешений, регистрацию документа, создание задач, выдачу доступа к файлу и управление жизненным циклом.

**PostgreSQL**

Хранит метаданные, связи с организациями и рабочими пространствами, статусы, версии и информацию об обработке.

**Private Object Storage**

Хранит бинарные данные. Предпочтительно S3-совместимое объектное хранилище с закрытым доступом. Конкретный провайдер выбирается отдельно.

**Очередь задач**

Позволяет обрабатывать большие документы асинхронно, повторять временно неудачные операции и ограничивать нагрузку.

**Document Worker**

Извлекает текст и готовит документ к поиску. Worker должен иметь ограниченные права и не должен получать произвольный доступ ко всем данным организации.

## 4. Поддерживаемые форматы

### 4.1. Форматы MVP

Предлагаемый список:

| Формат | Поддержка | Обработка |
|---|---|---|
| PDF с текстовым слоем | Да | Извлечение текста |
| PDF со сканами | Да, через OCR | Распознавание страниц |
| DOCX | Да | Извлечение текста и структуры |
| TXT | Да | Чтение текста |
| DOC | Не гарантируется | Отдельно решить |
| XLSX | Не входит в базовый MVP | Возможное расширение |
| PPTX | Не входит в базовый MVP | Возможное расширение |
| Изображения | Опционально | OCR |
| Архивы ZIP/RAR | Нет в базовом MVP | Отклонять |

Форматы должны определяться не только по расширению файла. Проверяются MIME-тип, сигнатура содержимого и возможность безопасной обработки.

Файл `document.pdf.exe` не должен считаться PDF только потому, что его имя содержит `.pdf`.

### 4.2. Ограничения MVP

Подтверждённые лимиты и дополнительные параметры:

- максимальный размер файла — 25 МБ (D-010);
- максимальное число файлов в одной операции — 10 (D-017);
- максимальное количество страниц PDF — 300 (предложенный технический лимит, требует тестирования);
- ограничение на количество символов извлечённого текста;
- тайм-аут обработки;
- лимит параллельных задач на пользователя и организацию.

Лимиты 25 МБ и 10 файлов подтверждены. Ограничение 300 страниц, объём извлечённого текста, тайм-ауты и параллелизм — технические ограничения, которые нужно подтвердить нагрузочными и security-тестами на синтетических/обезличенных материалах.

Ограничения применяются как при загрузке, так и при обработке. Нельзя полагаться исключительно на проверку frontend.

## 5. Модель данных

В `docs/06-data-model.md` уже предусмотрены `Document`, `DocumentVersion`, `DocumentExtraction`, `DocumentChunk` и `Embedding`.

Здесь уточняется их ответственность.

### 5.1. Document

Логический документ в продукте.

Предлагаемые поля:

- `id`;
- `organizationId`;
- `workspaceId`;
- `uploadedByUserId`;
- `title`;
- `status`;
- `currentVersionId`;
- `createdAt`;
- `updatedAt`;
- `deletedAt`.

`Document` представляет документ в интерфейсе и системе прав, а не обязательно один конкретный бинарный файл.

### 5.2. DocumentVersion

Конкретная версия содержимого.

Предлагаемые поля:

- `id`;
- `documentId`;
- `versionNumber`;
- `storageKey`;
- `originalFilename`;
- `detectedMimeType`;
- `fileSizeBytes`;
- `sha256`;
- `uploadedByUserId`;
- `createdAt`;
- `status`.

`storageKey` — внутренний ключ объекта в хранилище. Он не является публичной ссылкой.

Версия должна сохранять сведения об исходном файле, даже если название документа в интерфейсе изменено.

### 5.3. DocumentExtraction

Результат извлечения содержимого.

Предлагаемые поля:

- `id`;
- `documentVersionId`;
- `extractor`;
- `extractorVersion`;
- `status`;
- `pageCount`;
- `extractedTextStorageKey` или другой выбранный способ хранения текста;
- `textLength`;
- `language`;
- `errorCode`;
- `createdAt`;
- `completedAt`.

Большой извлечённый текст необязательно хранить непосредственно в основной таблице PostgreSQL. Выбор между БД и закрытым объектным хранилищем зависит от объёма, требований поиска, резервного копирования и удаления.

### 5.4. DocumentChunk

Фрагмент текста, подготовленный для поиска и RAG.

Предлагаемые поля:

- `id`;
- `documentId`;
- `documentVersionId`;
- `extractionId`;
- `chunkIndex`;
- `pageStart`;
- `pageEnd`;
- `text` либо ссылка на защищённое хранение текста;
- `tokenCount`;
- `createdAt`.

Каждый фрагмент должен быть однозначно связан с версией оригинального документа.

### 5.5. Embedding

Векторное представление фрагмента.

Предлагаемые поля:

- `id`;
- `chunkId`;
- `model`;
- `modelVersion`;
- `dimensions`;
- `status`;
- `createdAt`.

Для MVP подтверждён PostgreSQL + `pgvector` (D-018).

Эмбеддинги тоже являются производными конфиденциальными данными. Нельзя считать их обезличенными только потому, что они не выглядят как обычный текст.

### 5.6. Ограничения целостности

Необходимо обеспечить:

- принадлежность версии конкретному документу;
- принадлежность документа организации и рабочему пространству;
- уникальность `versionNumber` внутри документа;
- уникальность `chunkIndex` в пределах выбранной версии и извлечения;
- отсутствие активных дочерних данных у окончательно удалённого документа;
- согласованность статуса документа и статусов его обработки.

Если файл заменён новой версией, старые фрагменты и эмбеддинги не должны незаметно использоваться как актуальное содержимое.

## 6. Жизненный цикл документа

Предлагаемые статусы:

- `uploaded` — загрузка завершена, файл зарегистрирован;
- `pending_scan` — ожидает проверки;
- `processing` — выполняется извлечение или подготовка;
- `ready` — обработка завершена, документ доступен для поддерживаемых операций;
- `processing_failed` — обработка завершилась ошибкой;
- `archived` — документ архивирован и не используется как активный;
- `deletion_pending` — выполняется удаление;
- `deleted` — удаление завершено в пределах принятой политики.

Не все этапы обязательно должны быть отдельными публичными статусами. Внутренние статусы отдельных задач можно хранить отдельно.

### 6.1. Допустимые переходы

Примерная схема:

    uploaded
       |
       v
    pending_scan
       |
       v
    processing
       |
       +----> ready
       |
       +----> processing_failed
                    |
                    v
                 processing

Из любого активного состояния может начаться удаление:

    active_state -> deletion_pending -> deleted

Архивирование должно быть отдельной операцией, если продукту важно сохранять документ, но исключать его из стандартного списка или поиска.

### 6.2. Когда документ доступен

Документ может участвовать в AI-операциях только после успешного завершения обязательных этапов обработки.

Если извлечение текста завершилось ошибкой, система не должна создавать видимость, что документ полностью обработан.

При этом оригинал может оставаться доступным для скачивания пользователю, если он имеет необходимые права и документ не заблокирован проверкой безопасности.

## 7. Процесс загрузки

### 7.1. Предварительная проверка

Перед созданием документа backend проверяет:

- действующую сессию;
- право пользователя добавлять документы в выбранное рабочее пространство;
- принадлежность пространства организации;
- квоты и ограничения пользователя;
- допустимость формата;
- размер файла;
- лимит параллельных загрузок.

Идентификаторы организации и рабочего пространства из запроса не считаются доказательством доступа.

### 7.2. Рекомендуемый сценарий

1. Frontend отправляет запрос на создание загрузки.
2. Backend проверяет пользователя и права на целевое пространство.
3. Backend создаёт запись документа или загрузочной операции.
4. Файл передаётся в закрытое хранилище через backend либо временный подписанный URL.
5. Backend подтверждает завершение загрузки.
6. Система проверяет фактический размер, тип и целостность файла.
7. Документ получает статус `pending_scan`.
8. Создаётся задача обработки.
9. Frontend получает идентификатор документа и текущий статус.

Для небольшого MVP допустима загрузка через NestJS. Подписанные URL можно добавить для масштабирования, если будет реализована безопасная проверка их назначения, срока действия и прав.

### 7.3. Частично загруженные файлы

Незавершённые загрузки должны иметь ограниченный срок жизни.

Система должна уметь обнаруживать и удалять временные объекты, которые не были подтверждены как полноценные версии документа.

Повторный запрос завершения загрузки должен обрабатываться идемпотентно.

### 7.4. Контроль целостности

После получения файла вычисляется криптографический хеш, например SHA-256.

Он используется для контроля целостности, диагностики и выявления повторяющихся объектов в пределах разрешённого контекста.

Совпадение хеша не должно автоматически давать пользователю доступ к ранее загруженному объекту другого пользователя или организации.

Межорганизационная дедупликация не включается в MVP без отдельного анализа приватности и безопасности.

## 8. Безопасное файловое хранилище

### 8.1. Основные требования

- bucket или контейнер закрыт для публичного доступа;
- файлы недоступны по постоянным публичным URL;
- доступ выдаётся только после проверки прав;
- ключи хранения генерируются сервером;
- пользовательское имя файла не используется как ключ объекта;
- учётные данные хранилища не попадают в frontend;
- права сервисного аккаунта ограничены необходимыми операциями;
- транспорт защищён TLS;
- резервное копирование и удаление описаны отдельно.

### 8.2. Формирование ключей

Пример внутренней структуры:

    organizations/{organizationId}/documents/{documentId}/versions/{versionId}/original

Это пример логической организации объектов. Реальные ключи не должны использоваться для самостоятельной авторизации.

Знание `storageKey` не предоставляет доступ к файлу.

### 8.3. Скачивание

Предлагаемый endpoint:

`GET /api/v1/documents/{documentId}/download`

Backend должен:

1. Проверить сессию.
2. Найти документ.
3. Проверить организацию и членство.
4. Проверить право скачивания.
5. Проверить статус документа и версии.
6. Выдать поток файла или короткоживущий подписанный URL.

Если используется подписанный URL, он должен иметь короткий срок действия и ограничивать доступ к конкретному объекту.

Нельзя возвращать URL до проверки разрешений.

Для конфиденциальных документов необходимо предотвращать утечки через общие кэши, стороннюю аналитику и журналы запросов.

### 8.4. Заголовки ответа

При выдаче файла необходимо корректно устанавливать:

- `Content-Type` на основании проверенного типа;
- `Content-Disposition` с безопасным именем;
- `X-Content-Type-Options: nosniff`.

Для особо чувствительных сценариев следует использовать подходящую политику `Cache-Control`, например `private, no-store`.

Нельзя вставлять исходное имя файла в HTTP-заголовок без безопасного кодирования.

## 9. Проверка безопасности файла

Перед извлечением содержимого файл проходит проверку.

Минимальный набор:

- проверка расширения;
- проверка MIME-типа;
- проверка сигнатуры;
- ограничение размера;
- ограничение числа страниц и сложности обработки;
- выявление повреждённых или некорректных файлов;
- антивирусная проверка, если доступно подходящее средство;
- ограничения на архивы и вложенные объекты.

Если файл подозрителен, его обработка должна быть остановлена или изолирована.

Необходимо учитывать ZIP-бомбы и другие конструкции, которые могут вызвать чрезмерное потребление памяти или диска.

Обработчики PDF и офисных документов должны работать с ограничениями CPU, памяти, времени и прав доступа.

Не следует запускать офисные документы с активным содержимым или исполнять макросы ради извлечения текста.

Если проверка безопасности недоступна или завершилась ошибкой, политика должна явно определять, можно ли продолжить обработку. Для production безопасный вариант по умолчанию — не переводить файл в `ready`, пока обязательная проверка не завершена.

## 10. Извлечение текста

### 10.1. Общий принцип

Извлечение текста должно быть отдельным этапом, который можно повторить без повторной загрузки оригинала.

В результате желательно получить:

- текст;
- границы страниц;
- структуру абзацев;
- заголовки, если их удалось определить;
- метаданные извлечения;
- сведения об ошибках и качестве результата.

Необходимо сохранять связь извлечённого текста с конкретной версией документа.

### 10.2. PDF

Для PDF с текстовым слоем используется текстовый экстрактор.

Нужно учитывать:

- отсутствие текста на отдельных страницах;
- неправильный порядок чтения колонок;
- таблицы;
- переносы строк;
- колонтитулы;
- повторяющиеся заголовки;
- некорректное отображение символов;
- документы с нестандартной кодировкой или шрифтами.

Извлечённый текст может отличаться от визуального содержимого. Поэтому для юридических документов нельзя считать автоматическое извлечение безошибочным.

### 10.3. OCR

Если PDF состоит из изображений или текстовый слой отсутствует, используется OCR.

Результат OCR должен по возможности включать:

- распознанный текст;
- номер страницы;
- координаты блоков или строк, если движок их предоставляет;
- показатели уверенности распознавания, если они доступны.

При низком качестве распознавания нужно показывать пользователю предупреждение или статус частичной обработки.

Нельзя незаметно подменять плохо распознанный оригинал предположительно восстановленным текстом.

### 10.4. DOCX

Обработка DOCX должна учитывать:

- обычные абзацы;
- заголовки;
- таблицы;
- списки;
- колонтитулы, если они нужны;
- сноски и комментарии, если поддержка предусмотрена;
- порядок чтения.

Сложная вёрстка может не сохраняться полностью при извлечении текста. Оригинал остаётся источником визуально точного содержимого.

### 10.5. Нормализация

Нормализация должна улучшать поиск, не разрушая исходные данные.

Допустимые операции могут включать:

- приведение переносов строк к единому формату;
- устранение технических артефактов извлечения;
- удаление явно повторяющихся колонтитулов, если это безопасно;
- нормализацию пробелов;
- сохранение абзацев и границ разделов.

Нельзя удалять значимые юридические различия, номера пунктов, суммы, даты, обозначения сторон или знаки препинания без обоснования.

Желательно сохранять исходный результат извлечения и отдельное нормализованное представление.

## 11. Подготовка к поиску и RAG

### 11.1. Принцип фрагментации

После извлечения текста документ делится на фрагменты — chunks.

Фрагментация должна по возможности учитывать:

- границы абзацев;
- заголовки;
- нумерацию пунктов и подпунктов;
- границы страниц;
- структуру таблиц;
- объём фрагмента в токенах;
- контекст, необходимый для понимания положения.

Не следует разрезать юридический пункт посередине только ради фиксированного размера.

### 11.2. Начальные параметры

Предлагаемые стартовые значения для экспериментов:

- целевой размер фрагмента: 500–800 токенов;
- перекрытие соседних фрагментов: 50–100 токенов;
- размер и перекрытие настраиваются отдельно для разных типов документов.

Эти значения не являются универсально оптимальными. Их нужно проверять на наборе юридических документов и задачах поиска.

### 11.3. Метаданные фрагмента

Каждый фрагмент должен сохранять:

- `organizationId`;
- `workspaceId`, если применимо;
- `documentId`;
- `documentVersionId`;
- номер фрагмента;
- диапазон страниц, если доступен;
- заголовок или путь по структуре документа, если определён;
- идентификатор извлечения;
- статус версии документа.

Метаданные должны позволять сформировать ссылку на исходный документ и, насколько возможно, на конкретную страницу или раздел.

### 11.4. Эмбеддинги

Эмбеддинги создаются для выбранных фрагментов с использованием согласованной embedding-модели.

Необходимо сохранять идентификатор модели и её версию, чтобы можно было отслеживать несовместимость и выполнять переиндексацию.

Если модель или размерность изменились, старые векторы нельзя незаметно смешивать с новыми без проверки совместимости.

### 11.5. Права доступа при поиске

Поисковый индекс не является источником прав доступа.

До передачи найденных фрагментов в LLM backend обязан проверить, что пользователь имеет право читать соответствующие документы в текущем контексте.

Фильтрация по организации и рабочему пространству должна выполняться на серверной стороне и быть частью запроса к поиску, а не только постобработкой на frontend.

Недостаточно отфильтровать результаты после того, как чужой текст уже был передан модели.

### 11.6. Изоляция организаций

Запросы поиска и retrieval должны учитывать организацию, рабочее пространство и другие ограничения доступа.

Нельзя допускать, чтобы запрос в одной организации возвращал фрагменты другой организации из-за совпадения терминов или близости векторов.

Кэш поиска должен учитывать пользователя или эквивалентный контекст полномочий, а также идентификаторы и версии доступных данных.

## 12. Защита от инструкций внутри документов

Юридические документы могут содержать текст, который внешне выглядит как инструкция для ИИ, например требование игнорировать предыдущие правила или раскрыть другие материалы.

Содержимое документа следует рассматривать как недоверенные данные, а не как системные инструкции.

Требования:

- не помещать извлечённый текст в системный prompt как доверенные инструкции;
- явно разделять системные инструкции и цитируемый документ;
- ограничивать действия модели разрешениями backend;
- не разрешать документу самостоятельно менять права пользователя;
- не выполнять команды или инструменты только потому, что они упомянуты в документе;
- проверять доступ к каждому ресурсу отдельно от содержания документа.

Prompt injection нельзя полностью устранить одной текстовой инструкцией модели. Необходимы ограничения на уровне архитектуры и доступных инструментов.

## 13. Асинхронная обработка

### 13.1. Почему нужна очередь

Извлечение текста и OCR могут занимать значительное время.

HTTP-запрос не должен ждать завершения всей обработки большого документа. Backend регистрирует задачу и возвращает её идентификатор.

Предлагаемые endpoints:

- `POST /api/v1/documents` — создать документ и инициировать загрузку;
- `POST /api/v1/documents/{documentId}/process` — запросить обработку, если такой отдельный endpoint необходим;
- `GET /api/v1/documents/{documentId}` — получить статус;
- `GET /api/v1/documents/{documentId}/processing-status` — получить подробный статус обработки, если он нужен интерфейсу.

Точный контракт следует согласовать с `docs/11-api-conventions.md`, чтобы не создавать дублирующие способы запуска задач.

### 13.2. Повторные попытки

Повторять можно временные ошибки, например кратковременную недоступность хранилища.

Не следует бесконечно повторять:

- неподдерживаемый формат;
- превышение допустимого размера;
- повреждённый файл;
- ошибку валидации, требующую изменения входных данных.

Предусмотреть:

- ограниченное число попыток;
- задержку между повторениями;
- отдельный статус окончательной ошибки;
- диагностический `errorCode`;
- возможность безопасного ручного повторного запуска.

### 13.3. Идемпотентность

Повторная доставка одной задачи не должна создавать дублирующиеся фрагменты или эмбеддинги.

Для каждой операции обработки нужен стабильный идентификатор и механизм определения уже выполненной работы.

При повторной обработке новой версии необходимо гарантировать, что фрагменты разных версий не смешиваются.

### 13.4. Конкурентная обработка

Необходимо ограничивать:

- количество задач на worker;
- число параллельных OCR-операций;
- потребление памяти;
- суммарную нагрузку на организацию;
- длительность обработки одного документа.

Система должна сохранять работоспособность API, даже если поступило много тяжёлых документов.

## 14. Замена версии документа

Если пользователь загружает обновлённую редакцию:

1. Создаётся новая версия.
2. Оригинал старой версии сохраняется в соответствии с политикой хранения.
3. Новая версия проходит проверку и обработку.
4. Фрагменты и эмбеддинги связываются с новой версией.
5. После успешной обработки обновляется `currentVersionId`.
6. Поиск по актуальному документу использует новую версию.
7. Старая версия не должна незаметно выдаваться как актуальная.

Если новая версия не прошла обработку, политика должна определить, остаётся ли старая версия текущей.

Предварительное предложение: не менять `currentVersionId`, пока новая версия не прошла обязательную обработку. При этом пользователь должен видеть, что новая редакция ещё обрабатывается.

История версий не должна позволять обходить текущие ограничения доступа.

## 15. Удаление документов

Удаление описано подробно в `docs/08-data-lifecycle-and-deletion.md`.

В контексте файлов необходимо удалять или делать недоступными:

- оригиналы;
- старые версии;
- извлечённый текст;
- OCR-результаты;
- chunks;
- embeddings;
- поисковые индексы;
- временные файлы;
- кэшированные результаты;
- незавершённые задачи;
- ссылки и производные данные, которые позволяют восстановить содержимое.

### 15.1. Немедленное ограничение доступа

После подтверждения удаления документ сразу перестаёт быть доступным для новых пользовательских операций.

Физическое удаление из всех хранилищ может завершаться асинхронно, но статус `deletion_pending` должен запрещать чтение, скачивание, поиск и использование документа в новых AI-задачах.

### 15.2. Удаление из очередей

Если задача уже выполняется, система должна:

- попытаться отменить её;
- проверить статус документа перед сохранением результата;
- не публиковать результат обработки после удаления;
- очистить временные файлы;
- записать ошибку или результат отмены.

Проверка нужна не только при постановке задачи в очередь, но и перед публикацией результата.

### 15.3. Резервные копии

Удаление из основной БД и объектного хранилища не означает немедленного исчезновения данных из резервных копий.

Политика резервных копий должна определять сроки хранения, восстановление и повторное применение удалений после восстановления.

Эти правила должны быть согласованы с документом жизненного цикла данных и юридическими обязательствами продукта.

## 16. Конфиденциальность и внешние сервисы

При использовании внешнего OCR, моделей или других сервисов содержимое документа может передаваться за пределы инфраструктуры.

До такой передачи нужно определить:

- какие данные передаются;
- в какой регион;
- кто является поставщиком;
- какие условия хранения и использования данных действуют;
- используется ли содержимое для обучения;
- как обрабатываются журналы провайдера;
- каковы условия удаления и сроки хранения;
- какие договорные и правовые требования применяются.

Для MVP нельзя считать любой внешний сервис автоматически подходящим для юридической тайны или иных конфиденциальных данных.

До согласования провайдера, условий обработки и допустимости передачи реальные конфиденциальные документы не должны отправляться ему по умолчанию.

Система должна позволять отключать внешний OCR или обработку через конкретного провайдера для соответствующих категорий данных.

## 17. Наблюдаемость и диагностика

Для каждой обработки желательно фиксировать:

- `documentId`;
- `documentVersionId`;
- `jobId`;
- этап обработки;
- время начала и окончания;
- продолжительность этапа;
- размер файла;
- число страниц;
- число символов или токенов;
- количество попыток;
- безопасный код ошибки;
- версию экстрактора или OCR.

Не записывать в обычные логи полный текст юридического документа.

Полезные метрики:

- количество ожидающих задач;
- время ожидания в очереди;
- доля успешной обработки;
- доля ошибок по формату;
- среднее время обработки;
- количество повторных попыток;
- количество задач, превысивших тайм-аут;
- объём временных объектов;
- количество документов в `deletion_pending`.

Для диагностики должны быть доступны технические метаданные без автоматического раскрытия содержимого сотрудникам поддержки или администраторам.

## 18. Требования к тестированию

### Загрузка и хранилище

- Нельзя загрузить файл в чужое рабочее пространство.
- Нельзя обойти лимит размера подменой заголовка.
- Файл с поддельным расширением отклоняется.
- Публичный доступ к оригиналу отсутствует.
- Знание UUID документа или ключа хранения не предоставляет доступ.
- Незавершённые загрузки очищаются.

### Извлечение

- Текстовый PDF обрабатывается корректно.
- Сканированный PDF направляется на OCR.
- DOCX с таблицами обрабатывается согласно поддерживаемому контракту.
- Повреждённый файл получает понятный статус ошибки.
- Превышение лимита страниц корректно обрабатывается.
- Повторная задача не создаёт дублирующиеся chunks.

### Авторизация и поиск

- Фрагменты недоступного документа не передаются в LLM.
- Поиск не возвращает данные другой организации.
- Изменение UUID не позволяет читать чужой документ.
- Кэш не раскрывает результат другому пользователю.
- Отзыв членства прекращает доступ к документу.
- Отзыв временного разрешения прекращает доступ к содержимому.

### Удаление

- После начала удаления скачивание блокируется.
- Удалённый документ не попадает в новые AI-задачи.
- Завершившаяся после удаления задача не публикует результат.
- Фрагменты и эмбеддинги удаляются по установленной политике.
- После восстановления резервной копии применяются необходимые правила повторного удаления.

### Отказы и нагрузка

- Недоступность object storage не приводит к повреждению записи документа.
- Worker может перезапуститься без потери корректности данных.
- Переполненная очередь не блокирует основные API.
- Тайм-аут OCR корректно обрабатывается.
- Повторные запросы загрузки и обработки не создают дублирующие сущности.

## 19. Критерии готовности

Перед завершением реализации необходимо подтвердить:

- поддерживаемые форматы и лимиты;
- закрытое файловое хранилище;
- проверку прав на загрузку и скачивание;
- безопасную обработку файлов;
- асинхронную обработку;
- извлечение текста и сохранение связи с оригиналом;
- OCR для согласованных сценариев;
- версионирование;
- подготовку к поиску и RAG;
- изоляцию организаций;
- удаление производных данных;
- повторные попытки и обработку ошибок;
- мониторинг очереди;
- интеграционные тесты;
- политику передачи содержимого внешним сервисам.

## 21. Инструкции для AI-агентов

При реализации обработки документов AI-агент обязан:

1. Проверять связанные архитектурные документы.
2. Не делать объектное хранилище публичным ради простоты интеграции.
3. Не считать UUID или `storageKey` разрешением на доступ.
4. Проверять права до чтения и передачи содержимого.
5. Не передавать текст недоступного документа внешней модели.
6. Не хранить полное содержимое юридических документов в обычных логах.
7. Не запускать тяжёлую обработку непосредственно в HTTP-запросе.
8. Не допускать повторной обработки к созданию дубликатов.
9. Не использовать старые фрагменты как актуальную версию документа без проверки.
10. При удалении блокировать доступ немедленно, даже если физическое удаление асинхронно.
11. Не утверждать, что OCR или извлечение текста полностью точны.
12. Не отправлять конфиденциальные документы внешним провайдерам до утверждения политики обработки.
13. Не считать архитектурные предложения реализованными без соответствующего кода и тестов.

**Важно:** этот документ определяет предлагаемую архитектуру. Перед production необходимо проверить её реализацию, безопасность файловых обработчиков, правила хранения данных и условия использования внешних сервисов.

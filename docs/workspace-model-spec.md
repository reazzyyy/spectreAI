Выбранная модель принята за основу спецификации:

- Проект — самостоятельное рабочее пространство с чатами, документами, исследованиями и черновиками.
- Привязка проекта к клиенту необязательна.
- Поддерживаются личные рабочие пространства и общие проекты команды.
- Данные принадлежат организации либо личному пространству в рамках предусмотренной модели доступа.
- Количество проектов не ограничивается продуктовым лимитом на уровне MVP; фактическая техническая ёмкость определяется инфраструктурой.

Главное архитектурное решение: ввести отдельную сущность Workspace, не подменяя её существующей сущностью Matter. Client останется карточкой клиента, а Matter — юридическим делом, которое при необходимости связывается с рабочим пространством.

Ниже разделены уже подтверждённые решения, предлагаемые изменения и вопросы, которые нельзя считать утверждёнными без дополнительного решения.

## 1. Сопоставление с существующей документацией

В ранее согласованной архитектуре уже предусмотрены Next.js, NestJS, PostgreSQL, Prisma, Redis/BullMQ, Client и Matter, а также изоляция данных и серверная авторизация. Поэтому новую концепцию можно реализовать без перестройки основного стека.

| Область | Текущее состояние | Что меняем |
|---|---|---|
| Organization | Подтверждена | Без изменений |
| Client | Подтверждена для MVP | Без изменений, связь с проектом необязательна |
| Matter | Подтверждена для MVP | Сохраняем как юридическое дело |
| Workspace | Отдельная сущность не подтверждена как схема БД | Добавляем в модель данных (детали — PROPOSED) |
| Личные пространства | Смешанная модель только что выбрана | Добавляем владельца и правила личного доступа |
| Общие проекты | Смешанная модель только что выбрана | Добавляем членство и права на уровне проекта |
| Чаты, файлы, исследования, черновики | Функции MVP предусмотрены | Определяем их обязательную связь с пространством |
| Доступ администратора к содержимому | Уже согласовано ограничение | Сохраняем отдельное одобрение доступа |
| ИИ-провайдер | OpenAI API выбран, модель не определена | Сохраняем сменный адаптер и SyntheticAIProvider до завершения проверки передачи данных |

**Статус:** это сопоставление с ранее зафиксированными решениями. Ниже — спецификация предлагаемых изменений, а не утверждение, что канонические файлы уже отредактированы.

## 2. Целевая модель данных

Предлагаемая структура связей для MVP:

```text
Organization
  └── Workspace (PERSONAL | TEAM)
        ├── Chat → Message
        ├── Document
        ├── Research
        └── Draft

Client  (независимо)
Matter  (независимо; связь с Workspace — 0..1 в MVP-предложении)
```

Все дочерние данные наследуют контекст доступа рабочего пространства.

Дополнительно сохраняются две независимые сущности:

- Client — клиент юридической фирмы.
- Matter — юридическое дело, связанное с клиентом необязательно.

### Предлагаемые связи

| Связь | Кардинальность MVP |
|---|---|
| Organization → Workspace | Один ко многим |
| User → личные Workspace | Один ко многим |
| Workspace → участники | Один ко многим через таблицу членства |
| Workspace → Client | Ноль или один клиент |
| Workspace → Matter | Ноль или одно дело |
| Workspace → Chat | Один ко многим |
| Chat → Message | Один ко многим |
| Workspace → Document | Один ко многим |
| Workspace → Research | Один ко многим |
| Workspace → Draft | Один ко многим |

Последние связи — предлагаемая модель реализации, а не уже утверждённая схема БД.

### Почему личные пространства тоже должны иметь organizationId?

Для MVP предлагается создавать их внутри организации, к которой относится пользователь. Это упрощает изоляцию данных, аудит, удаление и работу с корпоративными политиками. `ownerUserId` определяет владельца, а `visibility` — тип пространства. Личное пространство при этом не становится доступным всем сотрудникам организации.

Отдельный режим для пользователей без организации следует рассматривать как отдельное продуктовое решение.

## 3. Спецификация backend

### 3.1. Сущность Workspace

Предлагаемая схема Prisma (концептуальный фрагмент; адаптировать к принятому в проекте формату ID и именованию):

```prisma
enum WorkspaceVisibility {
  PERSONAL
  TEAM
}

enum WorkspaceStatus {
  ACTIVE
  ARCHIVED
}

model Workspace {
  id             String              @id @default(cuid())
  organizationId String
  ownerUserId    String
  name           String              @db.VarChar(160)
  description    String?             @db.VarChar(2000)
  visibility     WorkspaceVisibility @default(PERSONAL)
  status         WorkspaceStatus     @default(ACTIVE)

  clientId       String?
  matterId       String?

  createdAt      DateTime            @default(now())
  updatedAt      DateTime            @updatedAt
  archivedAt     DateTime?

  members        WorkspaceMember[]

  @@index([organizationId, status, updatedAt])
  @@index([organizationId, ownerUserId, status])
  @@index([organizationId, clientId])
  @@index([organizationId, matterId])
}

model WorkspaceMember {
  workspaceId String
  userId      String
  role        WorkspaceMemberRole
  createdAt   DateTime @default(now())

  workspace   Workspace @relation(
    fields: [workspaceId],
    references: [id],
    onDelete: Cascade
  )

  @@id([workspaceId, userId])
  @@index([userId])
}

enum WorkspaceMemberRole {
  EDITOR
  VIEWER
}
```

Это концептуальный фрагмент схемы. Перед внедрением нужно добавить внешние ключи и проверки принадлежности `organizationId`, `ownerUserId`, `clientId` и `matterId` одной допустимой области доступа. В показанном фрагменте эти проверки ещё не реализованы.

Рекомендации к реализации:

- Использовать `cuid()` или текущий принятый в проекте формат ID, не смешивать разные стратегии. *(Сейчас в scaffold Prisma — UUID.)*
- Все даты хранить в UTC, отображать с учётом часового пояса пользователя.
- `ownerUserId` не изменяется обычным редактированием.
- PERSONAL — доступ владельца; TEAM — доступ владельца и добавленных участников.
- Не предоставлять доступ к личному пространству автоматически при назначении роли администратора организации.
- Удаление и архивирование разделить: архивирование сохраняет данные, удаление запускает регламентированную очистку.

### 3.2. Что добавить к существующим моделям

| Модель | Обязательные изменения |
|---|---|
| Chat | `workspaceId`, идентификатор организации и метаданные владельца/создателя |
| Message | `chatId`, автор, время создания; доступ проверяется через чат и пространство |
| Document | `workspaceId`, `organizationId`, `uploadedBy`, `storageKey`, статус обработки |
| Research | `workspaceId`, автор, статус, источники и результаты |
| Draft | `workspaceId`, автор, содержимое или ссылка на версию, история изменений |
| AIJob | `workspaceId`, `organizationId`, тип задачи, статус, безопасная ссылка на исходный объект |
| DocumentChunk / векторные записи | `organizationId`, `workspaceId`, `documentId` и сведения о версии документа |

Если Research, Draft или DocumentChunk пока отсутствуют, это новые модели, а не миграция существующих таблиц.

### 3.3. Изоляция данных

Для каждого чтения и изменения сервер должен проверять:

1. Пользователь аутентифицирован.
2. Пользователь имеет членство в организации.
3. Рабочее пространство принадлежит допустимой организации.
4. Пользователь имеет доступ к пространству с учётом PERSONAL / TEAM.
5. Пользователь имеет право выполнить конкретное действие.
6. Все связанные документы, чаты, дела и клиенты принадлежат допустимой области доступа.

Недопустимо полагаться на переданный клиентом `organizationId` или скрытие кнопок во frontend.

Для PostgreSQL следует рассмотреть Row-Level Security как дополнительный уровень защиты. При этом RLS не заменяет проверку бизнес-прав в NestJS: особенно для командных ролей, одобрений административного доступа и фоновых задач.

### 3.4. API для MVP

Базовый REST-контракт:

| Метод | Endpoint | Назначение |
|---|---|---|
| GET | `/api/v1/workspaces` | Список доступных пространств |
| POST | `/api/v1/workspaces` | Создать пространство |
| GET | `/api/v1/workspaces/:id` | Получить карточку |
| PATCH | `/api/v1/workspaces/:id` | Изменить название, описание, видимость |
| POST | `/api/v1/workspaces/:id/archive` | Архивировать |
| POST | `/api/v1/workspaces/:id/restore` | Восстановить |
| DELETE | `/api/v1/workspaces/:id` | Запросить удаление |
| GET | `/api/v1/workspaces/:id/members` | Получить список участников |
| POST | `/api/v1/workspaces/:id/members` | Добавить участника |
| PATCH | `/api/v1/workspaces/:id/members/:userId` | Изменить роль |
| DELETE | `/api/v1/workspaces/:id/members/:userId` | Удалить участника |

Для списка нужны серверные пагинация, поиск и сортировка. Рекомендуемый стартовый размер страницы — 20 записей. Это параметр API, а не ограничение общего количества проектов.

Для DELETE и приглашений потребуется дополнительный контракт с подтверждением, обработкой зависимостей и проверкой прав. Простое удаление строки не должно приводить к потере связанных данных без предусмотренного процесса очистки.

### 3.5. Правила доступа

Рекомендуемая матрица разрешений для первой версии:

| Действие | Владелец личного | Участник команды | Администратор организации |
|---|---|---|---|
| Просматривать личное пространство | Да | Нет | Нет |
| Просматривать командное пространство | Да | Если добавлен | Нет автоматически |
| Редактировать проект | Да | По роли | Нет автоматически |
| Добавлять участников | — | Нет по умолчанию | По отдельному разрешению |
| Управлять пользователями организации | Нет | Нет | Да |
| Читать содержимое по административному запросу | По обычным правам | По обычным правам | Только после одобрения |

Важные условия:

- VIEWER может читать доступное содержимое, но не редактировать его.
- EDITOR может создавать и редактировать материалы, если не запрещено отдельными правилами.
- Добавление участника в проект не даёт ему доступ к другим пространствам организации.
- Организационный администратор не получает автоматически доступ к чатам, документам и результатам исследований.
- Административный доступ к содержимому оформляется запросом с причиной и областью доступа, с обязательным одобрением другого уполномоченного сотрудника. Самосогласование запрещено.
- Для временного административного доступа сохраняется ранее согласованный TTL — 60 минут. Использование, одобрение и отзыв должны аудироваться.

Назначение роли администратора и право читать пользовательский контент — разные полномочия.

## 4. Точная спецификация для Figma

### 4.1. Основная навигация

В левом сайдбаре предлагаемый порядок:

- НейроЮрист Спектр
- Поиск по рабочим пространствам… (Ctrl K)
- Создать проект
- Недавние
- Личные пространства *(числа в макете условные)*
- Проекты команды
- Клиенты
- Юридические дела
- Настройки организации

«Клиенты» и «Юридические дела» — отдельные справочники. Это позволяет находить карточку клиента независимо от количества его проектов, а также создавать проекты без клиента.

### 4.2. Экран списка проектов

Отдельный экран Workspaces / Overview.

Обязательные элементы:

- Поиск по названию.
- Фильтры по видимости, статусу, клиенту и участию.
- Сортировка по последнему обновлению, названию и дате создания.
- Пагинация или постепенная подгрузка.
- Контекстное меню: переименовать, изменить видимость, архивировать.
- Состояния загрузки, ошибки, пустого результата и отсутствия проектов.
- Счётчики, если они показываются, рассчитываются по доступным пользователю данным.

Данные и счётчики должны поступать из API, а не быть фиксированными значениями макета.

### 4.3. Модальное окно создания

Название: Create workspace.

| Поле | Тип | Обязательность |
|---|---|---|
| Название проекта | Текст, до 160 символов | Обязательно |
| Описание | Текст, до 2000 символов | Необязательно |
| Тип пространства | Личное / Командное | Обязательно |
| Клиент | Поиск по справочнику | Необязательно |
| Юридическое дело | Поиск по справочнику | Необязательно |

Логика:

1. По умолчанию выбирается личное пространство, если это соответствует текущему разделу.
2. При выборе командного пространства отображается пояснение о доступе участников.
3. Список клиентов и дел содержит только записи, доступные пользователю.
4. Если клиент не выбран, проект создаётся без него.
5. При ошибке API введённые значения сохраняются в форме.
6. После успешного создания пользователь попадает внутрь проекта.

Пока не добавлять в MVP сложные настройки доступа, группы пользователей и произвольные ACL. Достаточно личного/командного режима и ролей EDITOR / VIEWER с серверной проверкой.

### 4.4. Экран рабочего пространства

Вкладки: Чаты, Документы, Исследования, Черновики. Основная зона — продолжение работы / ввод вопроса.

Рекомендуемые состояния экрана:

- Нет чатов — предложение начать первый диалог.
- Документы обрабатываются — статус и прогресс.
- Ошибка обработки — причина в безопасной для пользователя формулировке и повторный запуск, если допустим.
- Нет доступа — сообщение без раскрытия существования скрытых проектов.
- Проект архивирован — режим чтения или доступные действия согласно политике архивации.
- Проект удаляется — отдельное состояние процесса очистки.

Не показывать общую историю чатов организации внутри проекта по умолчанию. Чат должен принадлежать одному Workspace; перенос или копирование между пространствами — отдельная операция с проверкой доступа.

## 5. Особые требования к ИИ и поиску

Каждый AI-запрос должен формироваться в контексте выбранного рабочего пространства. Backend обязан:

1. Проверить права пользователя на Workspace.
2. Выбрать только разрешённые чаты, документы и источники.
3. Ограничить полнотекстовый поиск и pgvector-запросы тем же контекстом.
4. Проверить принадлежность всех файлов и результатов задаче.
5. Создать AIJob со статусом `queued`, затем обрабатывать задачу через Redis/BullMQ.
6. Возвращать результат только пользователям, которым разрешён доступ к соответствующему пространству.

Та же проверка нужна в фоновых задачах, повторных запусках, кэше, обработке документов и получении статуса AIJob. Нельзя считать, что авторизация в момент создания задания автоматически разрешает выдачу результата в будущем.

До завершения правовой, договорной и security-проверки передачи данных в OpenAI API сохраняется ранее принятое ограничение: используется `SyntheticAIProvider` и синтетические данные. Реальные клиентские документы не отправляются.

При удалении проекта нужно учесть все связанные сущности, включая векторные индексы, файлы, фоновые задачи и кэш. Срок очистки основных систем — до 24 часов, резервные копии — 35 дней; аудит не должен содержать тексты документов и промптов.

## 7. Критерии приёмки

Функциональность можно считать готовой к MVP, когда выполняются следующие условия.

- [ ] Пользователь может создать любое количество проектов без установленного продуктового лимита.
- [ ] Создание проекта без клиента работает корректно.
- [ ] Пользователь может создавать личные и командные пространства.
- [ ] Личное пространство недоступно другим сотрудникам без предусмотренного разрешения.
- [ ] Участник командного пространства получает только назначенные ему права.
- [ ] Запросы списка, поиска, фильтрации и пагинации не раскрывают чужие проекты.
- [ ] Нельзя получить документ, чат, черновик или результат AIJob другого пространства через прямой ID.
- [ ] Нельзя подменить `organizationId`, `workspaceId` или `documentId` в запросе и получить чужие данные.
- [ ] Поиск по тексту и векторный поиск не возвращают фрагменты из неразрешённых пространств.
- [ ] Администратор организации не получает доступ к содержимому автоматически.
- [ ] Одобрение административного доступа другим уполномоченным сотрудником и TTL 60 минут проверяются на backend.
- [ ] Архивирование не удаляет данные; удаление запускает согласованный процесс очистки.
- [ ] Фоновые задачи не выдают результат пользователю, потерявшему доступ к пространству.
- [ ] Миграции не нарушают существующие Client, Matter, документы и пользовательские данные.

## 8. Что осталось утвердить до реализации

Эти решения **не следует** выдавать за уже подтверждённые:

1. Несколько юридических дел в одном пространстве. В предложенной MVP-схеме у пространства максимум одно связанное дело. Если один проект должен объединять несколько дел, нужна связь многие-ко-многим.
2. Передача владения личным пространством. Что происходит, когда сотрудник увольняется или теряет членство в организации?
3. Удаление командного проекта. Кто может запросить удаление и требуется ли подтверждение другого сотрудника?
4. Приглашение участников. Кто имеет право добавлять и удалять участников?
5. Тарифные ограничения. Сейчас не установлено, будут ли они зависеть от числа проектов, объёма файлов или использования ИИ.
6. Внешние пользователи. Нужны ли совместные пространства для клиентов юридической фирмы? В текущую MVP-спецификацию они не включены.

Рекомендация: не блокировать Figma из-за тарифов и масштабирования, но зафиксировать первые четыре вопроса как решения, обязательные перед финализацией backend.

## Итог

Для проекта следует ввести Workspace как центральную сущность контекста работы ИИ, оставить Client и Matter отдельными сущностями и реализовать смешанный режим доступа через владельца, видимость и членство. Это даёт возможность вести множество проектов, не смешивая документы, чаты и исследования, и сохраняет согласованные требования к конфиденциальности.

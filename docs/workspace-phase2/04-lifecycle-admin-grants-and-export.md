# Workspace Phase 2 — lifecycle, admin grant и целевой экспорт

**Статус:** правила Workspace lifecycle и admin grant согласованы; экспорт описывается, реализация отложена (W-017, O-009 остаётся OPEN).  
**Связанные документы:** `DECISIONS-ADDENDUM.md`, `docs/07-access-control-matrix.md`, `docs/08-data-lifecycle-and-deletion.md`, `docs/25-logging-monitoring-and-audit.md`.

## 1. Workspace lifecycle

### 1.1 Состояния

Предлагаемый набор состояний:

| Статус | Значение |
|---|---|
| `ACTIVE` | Обычная работа |
| `ARCHIVED` | Сохранено, но исключено из активной работы |
| `PENDING_DELETION` | Создан запрос удаления, ожидается независимое подтверждение |
| `DELETING` | Удаление подтверждено; обычный доступ закрыт; идёт очистка |
| `DELETED` | Очистка завершена, остаётся только минимальная audit/tombstone запись при необходимости |

Не вводить `DELETED` как физическое удаление строки, если это нарушает аудит/целостность; определить tombstone подход в соответствии с D-019/D-020.

### 1.2 Архивирование

Архивирование — обратимая альтернатива удалению.

- Workspace перестаёт показываться среди активных по умолчанию.
- Контент и связи сохраняются.
- Доступ к чтению может сохраняться для ранее уполномоченных участников, если продуктовая политика не требует read-only; редактирование/создание блокируются.
- Восстановить может Workspace Owner или Org Admin в пределах полномочий.
- Архивирование не запускает удаление документов, chunks, embeddings, сообщений или AI results.
- События archive/restore аудируются.

Точное поведение archived Workspace (read-only для участников или только для Owner) — техническая UX-деталь, которую Cursor должен обозначить как proposal и не менять без согласования, если от неё зависит доступ.

### 1.3 Удаление — два независимых этапа

**Этап 1 — запрос удаления**
- Инициатор: Workspace Owner или Org Admin.
- Создаётся запись запроса, фиксируются requester, причина, workspace, время.
- Запрос не удаляет данные.
- Система запрашивает второе независимое подтверждение.
- Предлагаемый безопасный режим: после запроса запретить новые записи/изменения в Workspace до решения; чтение оставить существующим уполномоченным участникам. Это proposal, не отдельное подтверждённое правило.

**Этап 2 — независимое подтверждение**
- Подтверждающий не может совпадать с requester.
- Подтверждающий должен быть уполномочен на удаление в данной Organization/Workspace.
- Точный permission model для confirmer — отдельная техническая деталь, не создавать новую глобальную роль без решения.
- При отсутствии независимого подтверждающего удаление не выполняется.
- При отклонении запрос закрывается, Workspace возвращается в предыдущее состояние.

**После подтверждения**
- Немедленно установить `DELETING`/deletion tombstone и запретить обычный доступ.
- Запустить D-019 purge workflow.
- Очистить primary DB content, original files, extracted text, OCR output, chunks, embeddings, search indexes, caches, temporary files, derived AI outputs and managed exports в пределах 24 часов.
- Учитывать AI jobs: отменить queued/running где возможно; не выдавать результаты удаляемого Workspace.
- Backups сохраняются 35 дней по D-020; restore обязан повторно применить deletion journal.
- Audit хранит только минимальные метаданные операции, не содержимое.

**Критически важно:** «отложенное физическое удаление» не означает произвольный grace period после второго подтверждения. D-019 уже требует очистить основную систему и производные данные в пределах 24 часов после подтверждённого удаления. Если пользователь хочет более длинный период ожидания, это новое продуктовое решение, которое конфликтует с D-019 и требует отдельного согласования.

### 1.4 Второе подтверждение

Безопасное предложение для MVP:
- если запросил Workspace Owner — подтверждает Org Admin или другой назначенный уполномоченный;
- если запросил Org Admin — подтверждает Workspace Owner либо другой независимый Org Admin с соответствующим полномочием;
- requester никогда не подтверждает собственный запрос;
- если второго уполномоченного нет, использовать archive вместо удаления.

Это proposal; не кодировать конкретную матрицу confirmer до согласования. Не подменять `admin_grant:approve` разрешением на удаление: это разные полномочия.

## 2. Потеря членства и передача владения

### 2.1 Revoke membership

При отзыве Organization membership:
- новые запросы пользователя запрещены сразу;
- существующие сессии для Organization перестают работать;
- RLS context и NestJS authorization должны отказать в доступе;
- поисковые запросы, download, chat, AI context и job result повторно проверяют membership;
- данные не удаляются автоматически.

При удалении из одного TEAM Workspace остальные участники продолжают работу, а данные автора сохраняются.

### 2.2 Передача TEAM Workspace

- Передача — явная операция.
- Новый владелец должен иметь active OrganizationMembership.
- Смена owner и проверка нового owner выполняются транзакционно.
- Аудировать прежнего owner, нового owner, инициатора и время.
- Старый owner теряет owner privileges; если он остаётся участником, ему назначается EDITOR/VIEWER отдельно.

### 2.3 PERSONAL Workspace

- Не передавать автоматически при увольнении.
- Workspace и данные остаются в Organization.
- Доступ бывшего сотрудника прекращается.
- Передача другому сотруднику — отдельное решение с audit trail.
- Передача ownership не открывает личные чаты автоматически.
- Приватные чаты ушедшего пользователя сохраняются согласно retention policy, но не становятся автоматически доступными новому owner или Org Admin.
- Для доступа к таким чатам требуется явно определённое основание и scope; не обходить D-007.

## 3. Admin content grant

### 3.1 Назначение

Admin grant — исключительный временный read-only доступ Org Admin к конкретному Workspace для документированной административной причины.

Он не является постоянной ролью и не изменяет membership.

### 3.2 Запрос

Обязательные поля:
- requester (из доверенной Session, не из body);
- organizationId (из ActorContext);
- workspaceId;
- reason;
- requestedAt;
- requestedScope;
- status.

Минимальный scope MVP: `content:read` на конкретный Workspace. Более узкий scope — предпочтителен. Не выдавать доступ ко всей Organization.

### 3.3 Одобрение

- Одобряет только специально назначенный `admin_grant:approve` (D-016).
- Право назначает Organization Owner.
- Approver — другой пользователь; self-approval запрещён.
- Approver должен иметь активное членство и permission на момент одобрения.
- Отсутствие approver, timeout, ошибка или молчание не означают одобрение.
- Нет break-glass в MVP.
- Событие approve/reject фиксируется в AuditLog.

### 3.4 Срок и права

- Максимальный TTL — 60 минут (D-013).
- Продление запрещено (W-016); нужен новый request и новое approval.
- Досрочный revoke доступен уполномоченному лицу/системе по установленному процессу.
- Только read-only.
- Не разрешает edit, delete, export, share, transfer ownership, admin role change или передачу данных внешнему AI.
- Каждый запрос к содержимому повторно проверяет active grant, scope, expiry и revoke status.
- Кэш не должен сохранять доступ после expiry/revoke.
- Доступ через поиск, previews, download, attachments, AI context и background jobs должен отдельно проверяться; grant не расширяет права на действия, которые явно не входят в scope.
- Для каждого использования grant записывать audit event с grantId, actor, workspace/resource, action, timestamp, result.

### 3.5 Notifications

Получатели и каналы уведомлений при запросе/одобрении/отклонении/отзыве остаются O-010. До решения обеспечить audit trail; не придумывать обязательный email/push канал.

## 4. Экспорт — целевая спецификация, не MVP

### 4.1 Статус

Экспорт необходимо учитывать в продуктовой и технической документации, но не реализовывать в MVP. O-009 остаётся OPEN до отдельного утверждения форматов, прав, лимитов, юридических условий и retention экспортированных копий.

### 4.2 Предлагаемая матрица форматов

| Объект | Предлагаемый формат | Статус |
|---|---|---|
| Документ | Original + PDF preview; преобразование DOCX/PDF — по типу источника | PROPOSED |
| Черновик | DOCX, PDF | PROPOSED |
| Исследование | PDF | PROPOSED |
| Чат | PDF, DOCX | PROPOSED |
| Несколько выбранных документов | ZIP с оригиналами/представлениями | PROPOSED |
| Полный Workspace | Отдельный архивный/export package с manifest | PROPOSED, требует отдельного дизайна |

Экспорт не должен молча включать приватные чаты, документы вне scope, внешние источники с ограничениями лицензии или данные, на которые инициатор не имеет прав.

### 4.3 Права и ограничения — требования к будущему дизайну

До реализации требуется определить:
- кто может экспортировать: OWNER / EDITOR / VIEWER / Org Admin с grant;
- распространяется ли export permission на собственные документы или весь Workspace;
- разрешён ли export приватного чата его создателем;
- можно ли Org Admin экспортировать при наличии read-only grant (предлагаемый ответ: нет);
- допустимые форматы и размер ZIP;
- watermarks / metadata / manifest;
- срок хранения временных export files;
- шифрование и доставка;
- предотвращение публичных ссылок;
- поведение при удалении исходного Workspace;
- юридические ограничения на источники Legal Research.

### 4.4 Аудит будущего экспорта

Каждый экспорт должен фиксировать:
- actor;
- organizationId;
- workspaceId;
- export scope;
- типы объектов и количество;
- формат;
- время начала/завершения;
- результат/ошибку;
- идентификатор операции.

Не логировать содержимое, полный текст чата, документы, prompts, signed URLs или секреты.

Экспортированные файлы должны храниться в приватном storage и иметь короткоживущие ссылки, если такой способ доставки будет утверждён. Не создавать публичные URL.

### 4.5 Запрет до закрытия O-009

Пока O-009 открыт, Cursor не реализует export endpoints, UI, ZIP jobs или временное export storage. Допускается только подготовить architecture extension points, если это не создаёт неиспользуемую сложность и не меняет текущие контракты.

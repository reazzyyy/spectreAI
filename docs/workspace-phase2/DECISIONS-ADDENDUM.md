# Addendum: согласованные решения Workspace Phase 2

**Дата:** 2026-11-03  
**Статус:** `CONFIRMED` для решений, явно перечисленных ниже.  
**Назначение:** аддитивная запись решений, принятых при обсуждении фазы 2. Нормативные формулировки **W-001–W-020** перенесены в `docs/decisions-log.md` (2026-11-03). Этот файл сохраняет трассировку к вопросам A/B/C и границы PROPOSED.

## 1. Ворота A — модель Workspace

| ID | Вопрос | Подтверждённое решение |
|---|---|---|
| W-001 | A1 | Workspace — самостоятельная сущность, не заменяет Matter. |
| W-002 | A2 | В MVP поддерживаются личные (`PERSONAL`) и командные (`TEAM`) пространства. |
| W-003 | A3 | Связь Workspace ↔ Matter — M:N. Одно пространство может быть связано с несколькими делами, одно дело — с несколькими пространствами. |
| W-004 | A4 | Связь с Client необязательна. В MVP спецификация исходит из `0..1 Client` на Workspace; если понадобится несколько клиентов на одно пространство, это отдельное решение. |
| W-005 | A5/A7 | Содержимое читают участники Workspace. Org Admin не получает автоматического доступа; временное чтение возможно только через одобренный admin grant. |
| W-006 | A6 | Используются роли Workspace `OWNER`, `EDITOR`, `VIEWER`. |
| W-007 | A9 | Поддерживаются личные и общие чаты внутри Workspace. |
| W-008 | A8 | Участниками командного Workspace управляют Workspace Owner и Org Admin с разными полномочиями. Owner управляет своим пространством; Org Admin управляет членством/доступом в пределах полномочий организации. Управление участниками не даёт права читать содержимое. |
| W-009 | A10 | При потере членства/увольнении доступ пользователя прекращается немедленно; данные не удаляются автоматически. Личное пространство сохраняется для решения/передачи. Командное пространство продолжает работать. Уход Owner требует передачи владения. Передача не раскрывает личные чаты автоматически. |
| W-010 | A11 | Запросить удаление командного Workspace могут Workspace Owner или Org Admin. Требуется второе независимое подтверждение. Архивирование — альтернатива удалению. После финального подтверждения действует D-019: немедленная недоступность и очистка основной системы/производных данных в пределах 24 часов. |

### Уточнение A5/A7

В ходе обсуждения пользователь первоначально выбрал для A5 `участники + Org Admin read-only`, но затем явно выбрал вариант 2 для A7 — доступ Org Admin только через `admin_grant`. Итоговое согласованное поведение — W-005: **только участники по обычным правам, плюс отдельное исключение admin grant**. Никакого постоянного read-only доступа Org Admin нет.

Это не отменяет и не меняет D-006/D-007. Напротив, итог соответствует им.

## 2. Ворота B — вход и первые пользователи

| ID | Вопрос | Подтверждённое решение |
|---|---|---|
| W-011 | B1 | MVP использует Email + Password + Organization ID. Organization ID — контекст выбора организации, но не доказательство полномочий. |
| W-012 | B2 | Первую организацию и первого Owner создают через seed/контролируемый bootstrap. Дальнейшее добавление сотрудников — по приглашению Owner; свободная публичная регистрация не входит в MVP. |
| W-013 | B3 | MFA и SSO не входят в MVP; рассматриваются после MVP. |
| W-014 | B4 | CSRF-защиту реализовать отдельным техническим срезом до добавления следующих mutating-форм и массовых изменяющих endpoints. Cookie-based mutating endpoints не должны появляться без согласованной CSRF-защиты. |

## 3. Ворота C — безопасность и дополнительные возможности

| ID | Вопрос | Подтверждённое решение |
|---|---|---|
| W-015 | C1 | `admin_grant:approve` получают только специально назначенные уполномоченные участники. Самосогласование запрещено. |
| W-016 | C2 | Продление admin grant запрещено. Для дополнительного времени требуется новый запрос и новое одобрение. |
| W-017 | C3 | Экспорт описывается как целевая возможность, но не реализуется в MVP. Детальные права, форматы, лимиты и юридические условия остаются в O-009 до отдельного закрытия. |
| W-018 | C4 | Гостевые/внешние пользователи клиентов не входят в MVP. |
| W-019 | C5 | Тарифные лимиты на количество Workspace/файлов/AI в MVP не вводятся. Технические лимиты, rate limiting, защита от злоупотреблений и контроль ресурсов обязательны. |
| W-020 | C6 | PostgreSQL Row-Level Security (RLS) включается в MVP. RLS обязателен как дополнительный уровень защиты tenant/workspace данных и не заменяет NestJS authorization. |

## 4. Сохранённые ранее подтверждённые решения

Этот addendum не меняет:

- D-006/D-007 — администратор не имеет автоматического доступа к содержимому; нужен запрос и независимое одобрение.
- D-013/D-016 — TTL admin grant не более 60 минут; одобряет независимый участник с `admin_grant:approve`, назначаемым Owner; без согласующего доступ не выдаётся.
- D-019/D-020 — очистка после подтверждённого удаления ≤24 часов; backups 35 дней и replay deletion journal при restore.
- D-021 — целевой срок хранения аудита 1 год с проверкой до production.
- D-008/D-009/D-010/D-011/D-012/D-014/D-015/D-017/D-018/D-022/D-023 — стек, Client/Matter, лимиты файлов, статусы AIJob, Synthetic AI до O-002, размещение в РФ, OpenAI как целевой provider, pgvector/FTS, RPO/RTO и FSD остаются без изменений.

## 5. Открытые детали, которые нельзя изобретать

Следующие технические/продуктовые детали не были отдельно подтверждены и требуют явного обозначения `PROPOSED` либо отдельного вопроса:

1. Точный срок действия приглашения и правила повторной отправки.
2. Точный набор Organization roles и матрица полномочий Owner/Admin за пределами уже описанного.
3. Уточнение прав EDITOR на удаление чужого контента.
4. Поведение передачи личного Workspace и судьба личных чатов ушедшего пользователя.
5. Конкретная реализация второго подтверждения удаления и кто именно может подтвердить, если requester — единственный Owner/Admin.
6. Полный перечень форматов/прав экспорта и юридические основания (O-009).
7. Политика уведомлений при запросе/одобрении/отзыве admin grant (O-010).
8. Физическая реализация RLS helper functions, DB roles, bootstrap/auth access и worker contexts после проверки текущего Prisma/PostgreSQL setup.
9. Нужен ли Workspace-level RLS на все content tables сверх обязательной tenant isolation.
10. Точный CSRF механизм (double-submit cookie, synchronizer token, Origin/Referer validation) после анализа доменной схемы и текущей auth реализации.

Не превращать эти детали в `CONFIRMED` без решения владельца продукта.

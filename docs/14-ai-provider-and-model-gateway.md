# 14. AI-провайдеры и единый шлюз моделей

**Файл:** `docs/14-ai-provider-and-model-gateway.md`

**Статус:** базовый внешний провайдер OpenAI API подтверждён (D-015); конкретная модель и разрешение обработки реальных клиентских данных остаются OPEN.

**Приоритет:** критический для AI-функциональности.

**Связанные документы:**

## Подтверждённый выбор провайдера (D-012, D-015)

OpenAI API является целевым внешним провайдером; конкретная модель остаётся открытым выбором. Все вызовы должны идти через внутренний gateway/adapter, чтобы менять модель без изменения бизнес-логики. До завершения проверки договорных условий, режима обработки данных и правомерности передачи данных использовать только `SyntheticAIProvider` с синтетическими данными. Размещение приложения в РФ не означает, что данные, отправленные в OpenAI API, остаются в РФ.

## 1. Цель

Создать единый внутренний интерфейс для работы приложения с языковыми моделями, embedding-моделями и другими AI-компонентами.

Приложение не должно напрямую обращаться к конкретному API-провайдера из бизнес-логики.

Вместо этого все AI-операции проходят через внутренний слой — AI Gateway.

Gateway отвечает за:

- выбор провайдера и модели;
- единый контракт запросов и ответов;
- передачу контекста;
- обработку ошибок и тайм-аутов;
- повторные попытки;
- потоковую генерацию;
- учёт потребления;
- ограничения расходов;
- управление доступом к провайдерам;
- логирование технических метаданных;
- возможность в будущем использовать модели на собственной инфраструктуре.

Главная цель: **заменить или добавить провайдера без переписывания бизнес-логики продукта**.

При этом одинаковый API не гарантирует одинаковое качество ответов, стоимость или поддержку всех возможностей. Эти различия должны учитываться явно.

## 2. Архитектура

Предлагаемая схема:

    Next.js frontend
          |
          v
      NestJS API
          |
          v
    AI Application Services
          |
          +---- Chat Service
          +---- Document Analysis Service
          +---- Draft Service
          +---- Research Service
          +---- Embedding Service
          |
          v
       AI Gateway
          |
          +---- Provider Registry
          +---- Routing Policy
          +---- Model Adapter
          +---- Usage Metering
          +---- Cost Calculator
          +---- Retry / Timeout Policy
          +---- Safety / Data Policy
          |
          +---- External Provider A
          +---- External Provider B
          +---- Self-hosted Model
          +---- Embedding Provider

AI Gateway — внутренний модуль backend, а не отдельный публичный API для пользователей.

На первом этапе его можно реализовать внутри NestJS-приложения. Вынос в отдельный сервис имеет смысл только при реальной необходимости независимого масштабирования или изоляции.

## 3. Базовые принципы

### 3.1. Бизнес-логика не зависит от SDK провайдера

Нельзя импортировать SDK конкретного провайдера в сервисы чата, документов или юридического исследования.

Взаимодействие с провайдером должно происходить только через адаптер.

### 3.2. Провайдер не выбирается frontend

Frontend не должен самостоятельно решать, куда отправлять юридический документ.

Он отправляет бизнес-запрос в наш backend. Backend определяет допустимого провайдера и модель согласно настройкам организации, политике конфиденциальности и техническим возможностям.

Нельзя позволять клиенту подменить провайдера или передать произвольный URL для обращения к модели.

### 3.3. Конфиденциальность имеет приоритет над маршрутизацией

Выбор провайдера должен учитывать класс данных и допустимость передачи содержимого.

Если для документа запрещена внешняя передача, Gateway не должен направлять его внешнему API даже при наличии подходящей модели.

Если допустимого маршрута нет, система должна завершить операцию понятной ошибкой, а не незаметно использовать запрещённого провайдера.

### 3.4. Учёт потребления отделён от расчёта цены

Количество токенов, фактическая стоимость поставщика, внутренняя себестоимость и цена для клиента — разные величины.

Они должны храниться и рассчитываться раздельно.

### 3.5. Нельзя предполагать, что все модели взаимозаменяемы

Разные модели могут поддерживать разные возможности:

- текстовую генерацию;
- структурированный JSON-вывод;
- потоковую генерацию;
- работу с изображениями;
- вызов инструментов;
- эмбеддинги;
- заданный контекстный размер.

Gateway обязан учитывать возможности модели перед запуском операции.

## 4. Основные сущности

### 4.1. AIProvider

Логический поставщик AI-возможностей.

Примеры категорий:

- внешний API;
- собственный inference-сервер;
- отдельный сервис эмбеддингов.

Предлагаемые поля:

- `id`;
- `name`;
- `providerType`;
- `status`;
- `createdAt`;
- `updatedAt`.

Пример `providerType`:

- `external_api`;
- `self_hosted`;
- `embedding_service`.

Это внутренняя классификация, а не список конкретных коммерческих продуктов.

### 4.2. AIProviderConfiguration

Конфигурация подключения к провайдеру.

Предлагаемые поля:

- `id`;
- `providerId`;
- `environment`;
- `baseUrl`, если применимо;
- `secretReference`;
- `status`;
- `createdAt`;
- `updatedAt`.

API-ключи не должны храниться в обычной таблице в открытом виде.

`secretReference` — ссылка на секрет в хранилище секретов или другой утверждённый механизм. Если на старте используется переменная окружения, она должна поступать через защищённую конфигурацию deployment, а не храниться в Git.

### 4.3. AIModel

Модель с определёнными техническими возможностями.

Предлагаемые поля:

- `id`;
- `providerId`;
- `externalModelId`;
- `displayName`;
- `modelType`;
- `capabilities`;
- `contextWindow`;
- `maxOutputTokens`;
- `status`.

`externalModelId` — идентификатор модели у конкретного провайдера.

Нельзя считать его глобально уникальным без контекста провайдера.

Типы модели могут включать:

- `chat`;
- `embedding`;
- `reranking`;
- `vision`.

Окончательный набор зависит от фактически используемых компонентов.

### 4.4. AIRoutingPolicy

Политика выбора допустимого маршрута.

Она может учитывать:

- назначение операции;
- организацию;
- класс данных;
- разрешённые провайдеры;
- требуемые возможности;
- лимиты расходов;
- доступность провайдера.

Не следует предоставлять обычному пользователю возможность обходить ограничения конфиденциальности через настройки модели.

### 4.5. AIJob

Задача AI-операции.

Предлагаемые поля:

- `id`;
- `organizationId`;
- `requestedByUserId`;
- `workspaceId`;
- `operationType`;
- `providerId`;
- `modelId`;
- `status`;
- `idempotencyKey`;
- `createdAt`;
- `startedAt`;
- `completedAt`;
- `errorCode`.

Если задача создаётся от имени пользователя, нужно сохранять контекст инициатора для аудита и повторной проверки прав.

### 4.6. AIUsageRecord

Запись о потреблении ресурсов.

Предлагаемые поля:

- `id`;
- `aiJobId`;
- `organizationId`;
- `providerId`;
- `modelId`;
- `inputTokens`;
- `outputTokens`;
- `cachedInputTokens`, если применимо;
- `reasoningTokens`, если провайдер предоставляет эту метрику;
- `estimatedCost`;
- `actualProviderCost`;
- `currency`;
- `usageSource`;
- `createdAt`.

Некоторые поля могут отсутствовать у конкретного провайдера. Система должна различать фактические значения, оценочные значения и неизвестные значения.

## 5. Контракт AI Gateway

Внутренний Gateway должен предоставлять единый интерфейс для AI-операций.

Концептуальный пример:

    interface AIProviderAdapter {
      generateText(
        request: GenerateTextRequest
      ): Promise<GenerateTextResult>;

      streamText?(
        request: GenerateTextRequest
      ): AsyncIterable<GenerateTextEvent>;

      generateEmbedding?(
        request: GenerateEmbeddingRequest
      ): Promise<GenerateEmbeddingResult>;
    }

Это иллюстрация интерфейса, а не окончательная реализация TypeScript.

Фактический контракт следует адаптировать под SDK выбранных провайдеров и требования проекта.

### 5.1. Входной запрос

Унифицированный запрос может содержать:

- `operationId`;
- `operationType`;
- `modelId` или допустимые требования к модели;
- `messages`;
- `systemInstructions`;
- `responseFormat`;
- `maxOutputTokens`;
- `temperature`, если поддерживается;
- `timeout`;
- `metadata`.

Контекст организации, пользователя и разрешений формируется сервером.

Нельзя позволять frontend передавать произвольный системный prompt, способный отключить внутренние ограничения безопасности.

### 5.2. Результат

Унифицированный результат должен включать:

- текст или структурированный результат;
- идентификатор фактически использованной модели;
- идентификатор провайдера;
- метаданные потребления, если доступны;
- идентификатор запроса провайдера, если он безопасен для хранения;
- сведения о завершении генерации.

Нельзя возвращать секреты или внутреннюю инфраструктурную конфигурацию.

### 5.3. Ошибки

Gateway должен преобразовывать ошибки конкретных SDK в единый внутренний набор кодов.

Предлагаемые категории:

- `AI_PROVIDER_UNAVAILABLE`;
- `AI_PROVIDER_TIMEOUT`;
- `AI_RATE_LIMITED`;
- `AI_QUOTA_EXCEEDED`;
- `AI_MODEL_UNAVAILABLE`;
- `AI_UNSUPPORTED_CAPABILITY`;
- `AI_INVALID_RESPONSE`;
- `AI_CONTENT_POLICY_BLOCKED`;
- `AI_DATA_POLICY_BLOCKED`;
- `AI_REQUEST_TOO_LARGE`;
- `AI_CANCELLED`;
- `AI_UNKNOWN_ERROR`.

Публичные сообщения должны быть безопасными и понятными. Технические детали сохраняются в защищённых логах.

## 6. Адаптеры провайдеров

Для каждого поставщика создаётся отдельный адаптер.

Пример структуры:

    src/
      modules/
        ai/
          application/
            ai-gateway.service.ts
            model-routing.service.ts
            usage-metering.service.ts
            cost-calculator.service.ts
          domain/
            ai-provider.adapter.ts
            ai.types.ts
            ai.errors.ts
          infrastructure/
            providers/
              provider-a.adapter.ts
              provider-b.adapter.ts
              self-hosted.adapter.ts

Это ориентировочная структура. Её нужно согласовать с фактической архитектурой проекта.

Адаптер отвечает за:

- преобразование внутреннего запроса в формат поставщика;
- выполнение API-вызова;
- преобразование ответа;
- извлечение usage-метрик;
- преобразование ошибок;
- поддержку возможностей конкретной модели;
- корректную обработку отмены и тайм-аутов.

Адаптер не должен самостоятельно решать, имеет ли пользователь право читать передаваемый документ. Это проверяется до вызова Gateway.

### 6.1. Изоляция SDK

Зависимость от SDK должна оставаться внутри адаптера.

Если провайдер изменит формат API или SDK, изменения должны затронуть минимальное количество модулей.

### 6.2. Возможности моделей

Перед вызовом необходимо проверять, поддерживает ли модель требуемую операцию.

Например, модель для генерации текста не должна автоматически использоваться для получения эмбеддингов.

Нельзя предполагать, что все модели поддерживают JSON mode, tool calling, изображения или потоковый ответ.

## 7. Выбор провайдера и модели

### 7.1. Порядок принятия решения

Рекомендуемый порядок:

1. Определить тип операции.
2. Получить разрешённый контекст данных.
3. Определить требования конфиденциальности.
4. Получить список разрешённых провайдеров.
5. Отфильтровать модели по необходимым возможностям.
6. Проверить доступность и лимиты.
7. Выбрать маршрут согласно политике.
8. Зафиксировать выбор в AIJob.
9. Выполнить запрос.
10. Сохранить результат и usage-метрики.

### 7.2. Конфигурация организации

В будущем организация может настраивать:

- разрешённые модели;
- доступные операции;
- лимит расходов;
- допустимые провайдеры;
- ограничения передачи документов.

Однако эти настройки не должны позволять обычному администратору отключать обязательные требования безопасности платформы.

### 7.3. Fallback

При недоступности провайдера можно использовать резервную модель только при соблюдении всех условий:

- модель поддерживает необходимую операцию;
- она разрешена политикой данных;
- она соответствует установленным ограничениям;
- её стоимость допустима;
- смена модели не нарушает требования к качеству или формату ответа.

Нельзя незаметно переключаться на внешний API, если исходная операция должна выполняться исключительно на собственной инфраструктуре.

Если подходящего маршрута нет, операция завершается ошибкой с возможностью безопасного повтора.

### 7.4. Версионирование маршрута

Для каждой задачи нужно фиксировать фактически использованные провайдера и модель.

Это необходимо для:

- воспроизводимости диагностики;
- сравнения качества;
- анализа себестоимости;
- расследования ошибок;
- оценки изменений после переключения модели.

## 8. Работа с конфиденциальными данными

### 8.1. Политика передачи

До передачи содержимого внешнему провайдеру система должна определить, разрешена ли такая передача для соответствующей операции и класса данных.

Проверка выполняется на backend, а не на frontend.

### 8.2. Режимы обработки

Предлагается предусмотреть следующие логические режимы:

- `external_allowed` — внешняя обработка разрешена;
- `self_hosted_only` — допустима только собственная инфраструктура;
- `restricted` — обработка запрещена без отдельного решения или дополнительного разрешения.

Это предварительные обозначения. Окончательные правила классификации данных необходимо согласовать отдельно.

### 8.3. Запрет обхода политики

Если документ имеет ограничение `self_hosted_only`, Gateway не должен отправлять его внешнему провайдеру даже при:

- тайм-ауте собственного сервера;
- высокой очереди;
- отсутствии подходящей модели;
- достижении лимита собственной инфраструктуры.

В этом случае задача ожидает, отклоняется или завершается безопасной ошибкой согласно продуктовой политике.

### 8.4. Минимизация передаваемых данных

В запрос следует включать только необходимый контекст.

Не нужно отправлять:

- весь документ, если достаточно отдельных фрагментов;
- документы из других рабочих пространств;
- историю переписки, не относящуюся к текущей задаче;
- внутренние данные организации, не требуемые для ответа;
- пользовательские идентификаторы и другие метаданные, которые не нужны провайдеру.

Перед запуском AI-задачи backend повторно проверяет доступ к каждому документу и фрагменту, включённому в контекст.

### 8.5. Внешние провайдеры

Перед production необходимо проверить условия конкретного провайдера:

- регион обработки;
- хранение запросов и ответов;
- использование данных для обучения;
- сроки удаления;
- обработку технических логов;
- доступ сотрудников провайдера;
- договорные условия;
- применимые требования российского законодательства и конфиденциальности.

Сам факт использования API не означает автоматически, что данные безопасны для передачи.

## 9. Учёт токенов и стоимости

### 9.1. Разделять виды стоимости

Система должна различать:

1. Фактическую стоимость у провайдера.
2. Оценочную стоимость, рассчитанную до запроса.
3. Внутреннюю себестоимость собственной инфраструктуры.
4. Стоимость для клиента по тарифу продукта.

Эти значения нельзя хранить в одном поле с неоднозначным названием `cost`.

### 9.2. До запуска запроса

По возможности оцениваются:

- входные токены;
- максимальные выходные токены;
- ожидаемая стоимость;
- доступный бюджет организации;
- ограничения на одну операцию.

Для оценки могут использоваться токенизатор модели, статистика предыдущих запросов и тарифная конфигурация.

Оценка не гарантирует фактическую стоимость.

### 9.3. После ответа

Если провайдер возвращает usage-метрики, они сохраняются вместе с результатом операции.

Если usage недоступен, система может использовать оценку, но должна помечать её как оценочную.

Нельзя записывать оценочную стоимость в поле фактической стоимости.

### 9.4. Цены моделей

Тарифы провайдеров могут меняться.

Цены не следует зашивать в бизнес-логику в нескольких местах.

Рекомендуется хранить конфигурацию тарифов с периодом действия и версией, например:

- провайдер;
- модель;
- тип тарифицируемого ресурса;
- цена за единицу;
- валюта;
- дата начала действия;
- дата окончания действия, если применимо.

Для исторических отчётов необходимо сохранять сведения, позволяющие понять, по какой тарифной конфигурации рассчитана стоимость.

### 9.5. Лимиты расходов

Предусмотреть ограничения:

- на одну AI-операцию;
- на пользователя;
- на организацию;
- на период;
- на параллельные задачи.

Перед запуском дорогой операции система проверяет доступный лимит.

При этом необходимо учитывать конкурентные запросы: несколько одновременных задач не должны каждая независимо считать один и тот же остаток бюджета доступным для расходования.

Для этого требуется атомарное резервирование бюджета или другой согласованный механизм контроля.

### 9.6. Неопределённость стоимости

Если провайдер не возвращает фактическую стоимость, система не должна выдавать расчётную сумму за подтверждённый счёт поставщика.

В интерфейсе можно показывать оценку или внутренний расход с соответствующим обозначением.

---

## 10. Тарифы и монетизация

AI Gateway не должен быть жёстко привязан к одной бизнес-модели тарификации.

Возможные модели продукта:

- фиксированная ежемесячная плата;
- лимит включённых AI-операций;
- лимит потребления;
- платные дополнительные пакеты;
- корпоративные тарифы с отдельными лимитами.

Внутренний учёт потребления должен быть достаточно подробным, чтобы поддерживать эти модели в будущем.

При этом **техническое потребление не равно автоматически сумме, которую следует выставить клиенту**. Продуктовая тарификация определяется отдельно.

### 10.1. Рекомендация для MVP

На старте:

- собирать usage-метрики с первой AI-операции;
- рассчитывать внутреннюю себестоимость;
- установить защитные лимиты;
- не обязательно показывать пользователю стоимость каждого токена;
- не внедрять сложный биллинг, пока не подтверждена бизнес-модель.

Это позволит понять реальную экономику сервиса до принятия окончательного решения о тарифах.

---

## 11. Потоковая генерация

Для длинных ответов можно использовать потоковую передачу результата через SSE.

Внутренний Gateway преобразует поток конкретного провайдера в единый формат событий.

Предлагаемые типы событий:

- `generation.started`;
- `generation.delta`;
- `generation.completed`;
- `generation.failed`;
- `generation.cancelled`.

Конкретные имена необходимо согласовать с контрактом frontend.

Требования:

- проверить права до начала генерации;
- не раскрывать внутренние события провайдера;
- корректно обрабатывать разрыв соединения;
- ограничивать длительность генерации;
- фиксировать итоговый статус задачи;
- сохранять usage-метрики, когда они доступны;
- не считать обрыв соединения гарантированной отменой генерации у провайдера.

Если клиент отключился, backend должен выполнить предусмотренную политику: отменить задачу, если это возможно и допустимо, либо продолжить её с ограничениями.

---

## 12. Тайм-ауты, повторы и ошибки

### 12.1. Тайм-ауты

Для каждого типа операции должны быть определены допустимые тайм-ауты.

Короткая генерация ответа и обработка большого документа могут требовать разных значений.

Тайм-аут API-вызова не должен приводить к бесконечно работающей фоновой задаче.

### 12.2. Повторные попытки

Повтор допустим для временных ошибок, если повтор не приводит к неконтролируемым расходам или дублированию действий.

Нельзя автоматически повторять бесконечно:

- запросы с неверными параметрами;
- запрещённые политикой операции;
- превышение пользовательской квоты;
- неподдерживаемые возможности;
- постоянные ошибки авторизации у провайдера.

При повторе необходимо учитывать, что первый запрос мог быть принят провайдером и тарифицирован, даже если ответ не дошёл до приложения.

### 12.3. Идемпотентность

У каждой логической AI-операции должен быть идентификатор.

Повторная отправка клиентского запроса не должна случайно создавать несколько одинаковых задач.

Однако идемпотентность на стороне нашего API не гарантирует, что внешний провайдер поддерживает идемпотентность генерации. Это необходимо учитывать отдельно.

### 12.4. Отмена

При отмене задачи:

- фиксируется статус;
- по возможности отправляется отмена провайдеру;
- новые результаты не публикуются после окончательной отмены;
- учитывается возможность того, что часть расходов уже возникла;
- сохраняется безопасная техническая информация для диагностики.

## 13. Собственные модели и инфраструктура

### 13.1. Цель

Архитектура должна позволять подключить модель, работающую на собственном сервере, через тот же внутренний контракт.

Бизнес-логика не должна зависеть от того, выполняется ли запрос:

- у внешнего провайдера;
- на собственном GPU-сервере;
- в отдельном inference-сервисе.

### 13.2. Self-hosted adapter

Для собственной инфраструктуры создаётся отдельный адаптер.

Он отвечает за:

- вызов внутреннего inference API;
- тайм-ауты;
- обработку ошибок;
- преобразование ответов;
- метрики потребления;
- контроль доступности;
- ограничение нагрузки.

Inference-сервис не должен быть публично доступен без необходимости.

Доступ к нему осуществляется через защищённую внутреннюю сеть или другой утверждённый механизм.

### 13.3. Собственная инфраструктура не бесплатна

При self-hosting не оплачиваются токены внешнему поставщику, если модель действительно выполняется на собственном оборудовании без внешнего тарифицируемого API.

Однако остаются затраты на:

- сервер и GPU;
- электроэнергию;
- аренду стойки или дата-центра;
- обслуживание;
- резервирование;
- мониторинг;
- обновление моделей;
- эксплуатацию и безопасность;
- простой оборудования;
- инженерную поддержку.

Стоимость собственной генерации необходимо учитывать отдельно от API-тарификации.

### 13.4. Переключение между провайдерами

Переход на собственную модель не должен требовать переписывать:

- бизнес-логику чата;
- управление документами;
- авторизацию;
- историю переписки;
- учёт организаций;
- систему разрешений;
- основной API frontend.

Могут потребоваться изменения в конфигурации, адаптере, маршрутизации и тестах качества.

Необходимо учитывать, что собственная модель может хуже справляться с отдельными юридическими задачами. Поэтому маршрутизация должна основываться не только на доступности, но и на проверенной пригодности модели.

---

## 14. Безопасность Gateway

Обязательные требования:

- API-ключи доступны только backend;
- секреты не хранятся в Git;
- произвольные пользовательские `baseUrl` запрещены;
- внешние вызовы ограничены разрешённым списком провайдеров;
- тайм-ауты обязательны;
- максимальные размеры входа и выхода ограничены;
- запросы и ответы не записываются полностью в обычные логи;
- каждый запрос связан с `AIJob`;
- доступ к AI-результатам повторно проверяется;
- провайдер не может менять права пользователя;
- ошибки провайдера не раскрывают секреты и внутренние адреса;
- конфигурация провайдера изменяется только уполномоченным субъектом;
- отключение провайдера предотвращает новые запросы согласно установленной политике.

### 14.1. SSRF и произвольные адреса

Не принимать от клиента адрес API-провайдера.

Если для self-hosted или корпоративной конфигурации необходим `baseUrl`, он задаётся только доверенным администратором платформы или защищённой конфигурацией.

Адрес должен проверяться по утверждённому списку. Нельзя допускать, чтобы пользователь направил Gateway на внутренние служебные адреса или произвольные серверы.

### 14.2. Ограничение полномочий

Gateway должен получать только те данные, которые необходимы для выполнения операции.

Он не должен самостоятельно запрашивать произвольные документы по текстовой команде модели.

Если в будущем появится tool calling, каждое действие инструмента должно проходить отдельную серверную проверку полномочий.

## 15. Наблюдаемость

Для AIJob рекомендуется сохранять:

- `jobId`;
- `organizationId`;
- `requestedByUserId`;
- тип операции;
- выбранные провайдера и модель;
- статус;
- длительность;
- число попыток;
- токены входа и выхода, если доступны;
- оценочную и фактическую стоимость;
- безопасный код ошибки;
- `requestId`.

Полный юридический документ и полную переписку нельзя записывать в технические логи по умолчанию.

Основные метрики:

- число запросов по провайдерам;
- доля успешных операций;
- доля тайм-аутов;
- время до первого токена;
- полная длительность генерации;
- потребление токенов;
- стоимость;
- частота повторов;
- длина очереди;
- количество отказов по лимитам;
- количество блокировок по политике данных.

Это позволит сравнивать провайдеров по стоимости, задержке и надёжности.

## 16. Тестирование

### Контракт и адаптеры

- Каждый адаптер проходит одинаковый набор контрактных тестов.
- Ошибки провайдера преобразуются в согласованные внутренние коды.
- Неподдерживаемая возможность приводит к предсказуемой ошибке.
- Секреты не попадают в ответы и логи.

### Маршрутизация

- Выбирается только разрешённая модель.
- Запрещённые внешние маршруты блокируются.
- Fallback не обходит ограничения конфиденциальности.
- Отключённая модель не используется для новых задач.
- Выбор провайдера фиксируется в задаче.

### Расходы

- Сохраняются usage-метрики.
- Оценочная стоимость отличается от фактической.
- Превышение лимита обрабатывается корректно.
- Параллельные запросы не обходят бюджетный лимит.
- Ошибка после отправки запроса не приводит к бесконтрольным повторам.

### Конфиденциальность

- Чужие документы не включаются в контекст.
- Недоступные фрагменты не передаются модели.
- Внешний провайдер не вызывается при запрещённом режиме данных.
- AI-результат недоступен после отзыва соответствующих прав.

### Отказы

- Тайм-аут не оставляет бесконечно работающую задачу.
- Отмена обрабатывается корректно.
- Повторный запрос не создаёт неконтролируемые дубликаты.
- Недоступность одного провайдера не приводит к использованию запрещённого резервного маршрута.

## 17. Критерии готовности

Перед завершением реализации необходимо подтвердить:

- существует единый интерфейс AI Gateway;
- SDK провайдеров изолированы адаптерами;
- конфигурация провайдеров централизована;
- секреты защищены;
- выбор модели учитывает возможности и политику данных;
- AIJob фиксирует маршрут и состояние;
- расходы и usage учитываются;
- есть ограничения на расходы и параллелизм;
- повторы и тайм-ауты контролируются;
- результаты и контекст защищены проверками доступа;
- self-hosted адаптер можно добавить без изменения бизнес-логики;
- тесты проверяют основные сценарии;
- реальные условия передачи юридических данных внешним сервисам согласованы до production.

## 19. Инструкции для AI-агентов

При реализации AI Gateway агент обязан:

1. Проверять связанные документы перед внесением изменений.
2. Не вызывать SDK провайдера напрямую из бизнес-сервисов.
3. Не помещать API-ключи во frontend, репозиторий или логи.
4. Не принимать произвольный адрес провайдера от клиента.
5. Не передавать документы до проверки прав и политики обработки.
6. Не переключаться на запрещённый провайдер при ошибке.
7. Не считать оценочную стоимость фактическим расходом.
8. Не запускать бесконечные повторы.
9. Не предполагать одинаковые возможности и качество всех моделей.
10. Не считать self-hosting бесплатным.
11. Не предоставлять модели полномочия backend только на основании её текста или вызова инструмента.
12. Не утверждать, что адаптер, биллинг или защита реализованы, пока они не подтверждены кодом и тестами.

**Важно:** документ задаёт целевую архитектуру. Выбор конкретных провайдеров, модели, тарифы, инфраструктура и допустимость передачи конфиденциальных данных требуют отдельных решений.
